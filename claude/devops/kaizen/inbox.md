## 2026-07-25 — `docker run` is stdout-clean: all CLI status/pull output goes to stderr, so `docker run -i --rm` is a safe transport for a stdio MCP server
- **Evidence:** `docker run --rm alpine:3.19 echo HELLO 2>/dev/null` printed exactly `HELLO` on stdout even though the image was absent and the run emitted `Unable to find image 'alpine:3.19' locally` + the whole layer-pull progress — all of it on stderr. Round-trip check: `printf 'x\n' | docker run -i --rm alpine:3.20 cat 2>/dev/null` → stdout exactly 1 byte, nothing injected. Docker 29.6.1, native Linux engine under WSL2. Corollary: any wrapper script around `docker run` on an MCP stdio path must redirect *its own* output (and any `docker build` it triggers) to stderr explicitly — docker is not the leak, the wrapper would be.
- **Context:** designing the containerization of the repo's `cpg` stdio MCP server, where the central feasibility question was whether wrapping the process in `docker run -i` could corrupt the JSON-RPC stream.
- **Suggested home:** knowledge base (containerizing stdio/MCP processes) — it is the fact that makes "MCP server in a container" viable at all, and it is not obvious from the Docker docs.

## 2026-07-26 — A fully-cached BuildKit `docker build` still makes a registry round trip for `FROM` metadata; only the *image store* (not the build cache) prevents it, and a BuildKit build never populates the image store
- **Evidence:** Docker 29.6.1 / buildx 0.35.0. On a warm build where every layer reported `CACHED`/`DONE 0.0s`, `--progress=plain` showed exactly one live step: `[internal] load metadata for docker.io/library/python:3.12-slim` → `DONE 0.5s` — i.e. essentially the whole 0.54–0.65 s build was a Docker Hub call. After `docker pull python:3.12-slim`, that same step became `DONE 0.0s` and the build fell to 0.31–0.34 s. The trap underneath it: after a *successful* cold BuildKit build of that same image, `docker images python` was still **empty** — BuildKit populated only the build cache, so "I built it, therefore it's local" is false for `FROM` resolution. Corollary: `docker build` is **not** an offline-safe operation to put on any hot path (session start, CI step, launch wrapper) unless the base image was explicitly `docker pull`ed into the image store or pinned by digest. `docker image inspect` by contrast is 0.05 s and never contacts a registry.
- **Context:** deciding whether a launch wrapper for a containerized stdio MCP server could run a cached `docker build` on every start as a staleness check; this measurement is what disqualified it in favour of a content-hash image tag gated by `docker image inspect`.
- **Suggested home:** knowledge base (Docker/BuildKit behaviour) — it silently breaks the common "warm builds are offline / free" assumption, and the image-store-vs-build-cache distinction is not visible from `docker build`'s own output.

## 2026-07-26 — In a container whose PID 1 is `python`, `SIGTERM` is silently ignored; `--init` is required, not defensive
- **Evidence:** `docker run -d <img> python -c "time.sleep(300)"` then `docker kill --signal=TERM` → container still `running` 3 s later and still `running` a minute later (PID 1 gets no default signal dispositions, and CPython installs a handler only for `SIGINT`). Identical run with `--init` → `exited`, `ExitCode 143`. Two further measurements on the orphan question: `SIGKILL`ing the `docker run -i` **client** while PID 1 *ignores* stdin leaves the container `running` indefinitely (true orphan), but when PID 1 is genuinely blocked reading stdin, the same client `SIGKILL` breaks the attach stream → the process sees EOF → exits → `--rm` reaps it within 2 s. So the only orphan path is a *wedged* process not reading stdin, and `--init` closes it one step earlier. `--label <k>=<v>` on the run is the only way to enumerate such survivors afterwards (`docker ps -a --filter label=…`), since `--name` is unusable when concurrent launches are possible.
- **Context:** designing container lifecycle for a one-shot `docker run -i --rm` stdio process supervised by a harness whose shutdown sequence is close-stdin → SIGTERM → SIGKILL.
- **Suggested home:** knowledge base (container lifecycle) — "add `--init`" is common advice usually justified by zombie reaping; the sharper and more surprising reason is that an interpreter as PID 1 ignores `SIGTERM` outright, which turns a graceful-stop step into a no-op.

## 2026-07-26 — A `docker build` whose client is killed mid-flight keeps its completed layers, so an interrupted build resumes rather than restarting
- **Evidence:** a `--no-cache` build `SIGKILL`ed at the client at t=4 s (mid `pip install`); the very next build reported layers 6–8 `CACHED` and re-ran only the interrupted `pip install` step. So repeated attempts converge monotonically instead of starting from zero.

## 2026-07-26 — Docker's bare `-e VAR` form does not fall through to the image's `ENV`; with `VAR` unset in the caller's environment it *deletes* the variable in the container
- **Evidence:** Docker 29.6.1. Image built with `ENV FALKORDB_HOST=host.docker.internal`. Three runs of `python -c "print(os.environ.get('FALKORDB_HOST'))"`: (a) **no `-e` flag** → `host.docker.internal` (image ENV applies); (b) `env -u FALKORDB_HOST docker run -e FALKORDB_HOST …` → **`None`** — the image's ENV is *removed*, not preserved; (c) `FALKORDB_HOST=x docker run -e FALKORDB_HOST …` → `x`. The CLI reference sentence *"If no `=` is provided and that variable isn't exported in your local environment, the variable is unset in the container"* is literal — "unset in the container" means unset, **not** "the image default applies". Consequence: the common `-e VAR1 -e VAR2 …` pass-through idiom silently defeats every image `ENV` default it names, and the application then falls back to its own in-code default. Safe form is to build the argument list conditionally: `for v in …; do [ -n "${!v+set}" ] && ARGS+=(-e "$v=${!v}"); done`.
- **Context:** containerizing a stdio MCP server whose image ENV existed precisely so an ad-hoc `docker run` would reach the DB on the host; the wrapper's unconditional `-e FALKORDB_HOST` clobbered it and the server silently tried `127.0.0.1`, i.e. the container itself. A design review had accepted the "else the image ENV default applies" reading while quoting the doc sentence that contradicts it.
- **Suggested home:** knowledge base (Docker CLI behaviour) — it is a documented-but-easily-misread sentence that turns an image default into a null, and the failure mode is a wrong value rather than an error.

## 2026-07-26 — The FastMCP/`mcp` 1.28.x stdin-EOF response loss is a *race*, not "the last reply": it can eat more than one trailing reply, and it is more likely through `docker run -i` than on the host
- **Evidence:** same server, same probe shapes, replies counted on stdout. (1) 5-message probe (`initialize`, `notifications/initialized`, `tools/list`, `tools/call`, trailing `ping`) through `docker run -i --rm`: ids 1/2/3 always arrived, id 4 (the ping) never did — consistent with the known "last reply is lost" note. (2) But a 6-message probe (`initialize`, 4 `tools/call`s, trailing `ping`) lost **two** replies — the 4th `tools/call` (id 5, an `EXPLAIN`, i.e. the slowest) *and* the ping. (3) A 4-message probe repeated 5× on each path: host venv delivered all three replies in 3/5 runs, the container in only 1/5. So the loss is timing-dependent — whatever has not flushed when EOF tears the anyio session down is discarded, and the extra `docker run` attach-teardown latency widens the window. Practical rule: pad with at least one throwaway trailing message, assert **only** on the substantive ids, and never assert on the padding or on a fixed total.
- **Context:** implementing a container launch path whose verification step had been specified as "expect all four responses", which would have false-alarmed on a healthy run; and an earlier capture of the same gotcha (`claude/coder/kaizen/inbox.md`) states it as deterministically the last reply.
- **Suggested home:** knowledge base (MCP stdio testing) — it refines an existing entry that overstates the rule as deterministic, and the "assert on ids you need, not on a count" habit is what makes stdio MCP probes reliable.

## 2026-07-26 — `claude mcp list` is a genuine out-of-band verifier for an edited `.mcp.json`, and it settles which env var owns the MCP startup budget
- **Evidence:** Claude Code 2.1.220. `claude mcp list` spawns a **fresh** process that re-reads `.mcp.json` and actually health-checks each server, so an edit to the launch command can be proven **without restarting the current session** (which cannot see the change — stdio servers are not reconnected): immediately after switching the `cpg` entry from `run.sh` to `docker-run.sh` it reported `cpg: bash -c exec "$CLAUDE_PROJECT_DIR/cpg/mcp/docker-run.sh" - ✔ Connected`, while the in-session tool was still served by the pre-edit process. It also answers the startup-timeout ambiguity in one command each, where the official env-var *reference table* and the prose pages disagree: `MCP_TIMEOUT=1 claude mcp list` → `✘ Failed to connect — MCP server "cpg" connection timed out after 1ms`, whereas `MCP_CONNECT_TIMEOUT_MS=1 claude mcp list` → `✔ Connected`. So **`MCP_TIMEOUT` is the connection/startup budget** (30 s default) and `MCP_CONNECT_TIMEOUT_MS` does not bind unless `MCP_CONNECTION_NONBLOCKING=0` or the server sets `alwaysLoad: true`.
- **Context:** verifying a containerized MCP launch path when the only documented proof ("restart the session, check `/mcp`") is unavailable to the agent making the edit, and needing to document the right knob for a slow first build.
- **Suggested home:** knowledge base (Claude Code MCP) — both halves are cheap, repeatable checks that replace an assumption and a session restart; the `MCP_TIMEOUT` result also contradicts a published reference table, so it is worth recording with the version number.

## 2026-07-26 — A `docker build` whose changed inputs touch no COPYed layer produces the SAME image ID, so the new tag shows up in `docker image ls` with the OLD `CreatedSince` — which reads as "my build did nothing"
- **Evidence:** Docker 29.6.1, BuildKit. A multi-stage Dockerfile whose `runtime` target COPYs only `requirements.txt` + `server.py`, with the test suite COPYed in the `test` target. Editing a file under `tests/` moved a content-hash image tag (`ba910c48571d` → `3f825c8afe4f`); `build.sh` then ran a real build (BuildKit output showed `[test 4/5] COPY tests tests DONE 0.0s` and a fresh `exporting to image`). Afterwards `docker image ls` listed `cpg-mcp:3f825c8afe4f` as **"18 hours ago"**, i.e. older than the build that had just created it, and `docker image inspect cpg-mcp:ba910c48571d cpg-mcp:3f825c8afe4f --format '{{.RepoTags}} {{.Id}}'` returned **one identical `sha256:3a1820…` with both tags plus `:dev` on it**. The new "image" is just a second tag on the pre-existing one, because every layer the `runtime` target actually contains was unchanged; `CreatedSince` is the image's creation time, not the tag's. The `test` target, which does COPY the changed files, did get a genuinely new ID.
- **Context:** re-verifying a content-hash-tagged MCP server image after a test-only edit, where the whole point of the check was "did the tag move and is there an image behind it" — the stale-looking timestamp invites the conclusion that the rebuild silently no-opped, and `docker image ls` alone cannot distinguish "identical result, re-tagged" from "nothing built".
- **Suggested home:** knowledge base (Docker image identity) — the reusable rules are (a) verify a rebuild by image **ID**, never by `CreatedSince`, and (b) a content hash over inputs that a given target does not COPY will keep re-deriving the same image under new tags, which is a real argument for scoping such a hash per target.

## 2026-08-09 — `set -euo pipefail` turns a benign "downstream reader closed early" into a script-killing SIGPIPE, and hides the difference between that and a real error
- **Evidence:** Bash 5.x on Linux. A NUL-separated producer/consumer idiom (`while IFS= read -r -d '' x; do ...; done < <(producer)`) where the consumer legitimately returns early on a match (documented pattern in `cpg/mcp/build.sh`'s `_in_nul_set`, added specifically to avoid this). Two distinct failure modes, both reproduced directly:
  (1) `x="$(seq 1 100000 | head -n1)"` under `set -euo pipefail` prints the assignment's result and then **the whole script exits (rc=141)** before the next line runs — a bare `var="$(pipeline)"` assignment is NOT exempt from `errexit` the way an `if`/`while`/`&&`/`||` condition is, so a `pipefail`-surfaced SIGPIPE from a downstream `head`/early-return silently kills the script with no diagnostic.
  (2) Wrapping the same pattern in `if ! ( producer | consumer ); then …fi` avoids the abort (conditions are errexit-exempt) but then **mis-attributes the SIGPIPE'd pipeline's non-zero exit status to "the producer failed"** — indistinguishable, by exit code alone, from a genuine producer error (e.g. `find` hitting a permission-denied subtree). Confirmed by reproducing a false positive: a completely healthy tree reported a fabricated "'find' failed" on every invocation, with **no underlying `find:` stderr line**, purely because a consumer (`_in_nul_set`) matched on the first item and closed its end of the pipe while the producer (`find | sort -z`) was still writing later output.
  Fix that resolved both: judge failure by whether the producer **wrote anything to a captured stderr file** (`2>"$errfile"`; `[ -s "$errfile" ]`), never by exit code, and keep every expression that could carry a SIGPIPE-tainted status inside an `if !`/`if ! var=$(...)` so errexit can never fire on it.
- **Context:** hardening `cpg/mcp/image-tag.sh`'s content-hash file enumeration (a `find`-based walk consumed, sometimes partially, by multiple callers) to hard-fail on a genuinely unreadable subtree instead of silently hashing a truncated tree as valid — mid-fix, the naive "check the pipeline's exit code" approach appeared to work in isolation but broke under the codebase's own real early-exit consumer.
- **Suggested home:** knowledge base (Bash scripting) — the reusable rules are (a) under `pipefail`, a legitimate early-exiting consumer of a producer|producer pipe WILL make an upstream stage exit non-zero via SIGPIPE, indistinguishable from a real failure by exit code alone; (b) a bare `var="$(pipeline)"` assignment is not errexit-exempt and can silently kill the whole script on exactly this SIGPIPE, where the same expression inside an `if` would not; (c) when a pipe may be read partially by design, judge the producer's success by captured stderr content, not by exit status.
