## 2026-08-16 — `META_DATA` (and `FILE`/`TYPE`/`NAMESPACE`) are absent from both live pysrc2cpg-built graphs, despite being listed in cpg-model.md's node-label vocabulary
- **Evidence:** `MATCH (n:META_DATA) RETURN n` → 0 rows on both `cpg_falkorchat` and `cpg_salesperson`, via `mcp__cypher__query`. `CALL db.labels()` on `cpg_falkorchat` returned exactly 20 labels (`CpgNode`, `METHOD`, `CALL`, `LOCAL`, `MODIFIER`, `LITERAL`, `IDENTIFIER`, `FIELD_IDENTIFIER`, `BLOCK`, `METHOD_RETURN`, `METHOD_PARAMETER_OUT`, `CONTROL_STRUCTURE`, `METHOD_PARAMETER_IN`, `UNKNOWN`, `METHOD_REF`, `TYPE_DECL`, `RETURN`, `IMPORT`, `TYPE_REF`, `MEMBER`) — none of `META_DATA`, `FILE`, `TYPE`, `NAMESPACE`/`NAMESPACE_BLOCK` appear, though `skills/joern-cpg/references/cpg-model.md`'s "Node labels you'll see most" list includes all of them.
- **Context:** designing the cpg-agent-adoption freshness-marker feature (`docs/plans/cpg-agent-adoption-graph.md`) — was evaluating whether to hook a build-timestamp property onto the existing `META_DATA` node vs. a dedicated node; had to rule out `META_DATA` empirically before designing around it.
- **Suggested home:** knowledge base (`skills/joern-cpg/references/cpg-model.md`) — the "Node labels you'll see most" list reads as "always present" but is apparently frontend/export-configuration-dependent (likely `pysrc2cpg` + default `--repr cpg` specific); worth a one-line caveat there ("confirmed absent on `pysrc2cpg`/`cpg_falkorchat`/`cpg_salesperson`, 2026-08-16") so a future producer doesn't assume `META_DATA` is a safe anchor without checking first, the way this task almost did.

## 2026-08-16 — `GRAPH.EXPLAIN` (unlike `GRAPH.QUERY`/`GRAPH.RO_QUERY`) refuses to run against a graph key that doesn't exist yet — it cannot be used to syntax-check a write query with no prior graph
- **Evidence:** `redis-cli GRAPH.EXPLAIN cpg_stamp_syntax_check "MERGE (b:CpgBuildInfo) SET ..."` against a never-created graph key → `ERR Invalid graph operation on empty key`, for a syntactically valid Cypher statement. Confirmed the key was never materialized by the attempt (`GRAPH.LIST` afterward doesn't show it) — so this isn't the same "querying a non-existent graph materializes it" gotcha `cpg-analysis/SKILL.md` §1 already documents for `GRAPH.QUERY`; `EXPLAIN` just hard-fails instead.
- **Context:** implementing the `cpg-agent-adoption` freshness-marker stamping step in `skills/joern-cpg/scripts/pipeline.sh` (U4a) — wanted to syntax-verify the generated `MERGE (b:CpgBuildInfo) SET ...` Cypher string without running a real pipeline build or mutating a live graph. `GRAPH.EXPLAIN` was the first thing tried and doesn't work for this without an existing graph; `GRAPH.RO_QUERY` against an *existing* graph worked instead — it parses the write query first and only then rejects it for being a write ("graph.RO_QUERY is to be executed only on read-only queries"), which is enough to prove the Cypher parses without persisting anything.
- **Suggested home:** knowledge base (`falkordb-quirks.md`) — a reusable technique worth recording: to syntax-check a *write* Cypher string with zero side effects, run it via `GRAPH.RO_QUERY` against any existing graph (not necessarily the target one) and confirm the rejection reason is "read-only queries only," not a parse error; `GRAPH.EXPLAIN` is not a substitute unless the target graph already exists.

## 2026-08-17 — `pipeline.sh`'s exit code can read as failure (1) even when the run fully succeeded, if the caller wraps it in `| tee <file>` and the tee target's parent dir doesn't exist yet at pipe-start
- **Evidence:** Ran `skills/joern-cpg/scripts/pipeline.sh "$SRC" --graph cpg_falkorchat --language pythonsrc --workdir /tmp/cpg-work/falkorchat --load --verify-prefix tests/ 2>&1 | tee /tmp/cpg-work/pipeline-run.log` as a background job. Captured output began with `tee: /tmp/cpg-work/pipeline-run.log: No such file or directory` (tee opens its target immediately, racing `pipeline.sh`'s own `mkdir -p "$WORKDIR"` a few lines into the script) — yet the full run completed correctly downstream: `2583/2583 statements ok, 0 failed`, `verify OK — 1672 METHOD nodes with FILENAME STARTS WITH 'tests/'`, and the freshness-marker stamp echoed successfully. The overall backgrounded command still reported `[exited with code 1]`, because with no `pipefail`, the pipeline's exit status is `tee`'s (which failed to open its one file), not `pipeline.sh`'s (which was 0). Confirmed after the fact: `redis-cli GRAPH.QUERY cpg_falkorchat "MATCH (b:CpgBuildInfo) RETURN count(b)"` → 1, node/edge counts matched the transform step's reported numbers exactly, and `/tmp/cpg-work/pipeline-run.log` never actually got created on disk (only the harness's own background-task output capture had the full log).
- **Context:** C-409 — rebuilding `cpg_falkorchat` through `joern-cpg` so it picks up the `:CpgBuildInfo` freshness marker. A caller (the orchestrating agent) independently checked FalkorDB mid-run and reasonably escalated on seeing zero marker rows plus an ambiguous status message; the real answer was "still running," and once it finished, the marker and counts were all correct.
- **Suggested home:** knowledge base (`skills/joern-cpg/SKILL.md`, near the `--load` usage example) — either mkdir the tee target's directory before invoking `pipeline.sh`, or (simpler) don't tee at all and rely on the harness's own captured background-task output, which this pattern already provides. Worth a one-line caution so a future run doesn't misread a `tee`-caused nonzero exit as a pipeline failure.

## 2026-08-16 — `falkor-chat`'s `StepRun` audit trail is decoupled from `Step` nodes by design — deleting a workflow snapshot's `Step`/`WorkflowDefSnapshot` nodes cannot orphan or corrupt `StepRun` history, only the live `AT_STEP` position pointer
- **Evidence:** `server/falkorchat/repository.py:1371-1388` (`advance` write path) does `MATCH (r:WorkflowRun {runId:$runId})-[atRel:AT_STEP]->(cur:Step) ... CREATE (sr:StepRun {stepRunId:$stepRunId, stepKey: cur.key, ...})` — `cur.key` is read once and copied as a plain string property onto the new `StepRun` node; no edge is ever created from `StepRun` to `Step`. `StepRun` only has edges to `WorkflowRun` (`HAS_STEP_RUN`, `LAST_STEP_RUN`) and to `Message` (`PRODUCED`, :1510). Confirmed live: deleted `ws:acme`'s entire `triage@v1` `WorkflowDefSnapshot` + its 3 `Step` nodes via `DETACH DELETE` (task: resync `triage@v1` snapshot after a K-027 config edit) while 7 `WorkflowRun`s (`defKey:'triage'`) remained in the graph, undisturbed and still queryable by `runId`/`status` afterward — only their `OF_DEF`/`AT_STEP` edges were removed by the cascade.
- **Context:** graph-dba task to drop-and-rematerialize `ws:acme`'s stale `triage@v1` snapshot (K-027 item 2's `requiredTools` config landing). Needed to reason about blast radius before running `DETACH DELETE` on shared state with live `WorkflowRun`s attached.
- **Suggested home:** project docs (`falkor-chat/docs/DESIGN.md` §12 or the `materialize_snapshot`/`advance_run` docstrings) — worth a one-line note that a snapshot deletion's blast radius is bounded to "live position + `OF_DEF` back-reference," never the `StepRun`/`TraceEvent` audit trail, since that's exactly the kind of thing an operator needs to know *before* authorizing a destructive snapshot drop on a graph with real run history.

## 2026-08-16 — a scoped `DETACH DELETE` of a workflow snapshot subgraph reported far more relationships deleted than the def's own topology + its `WorkflowRun` attachments account for
- **Evidence:** `ws:acme`'s `triage@v1` snapshot had exactly 1 `WorkflowDefSnapshot` + 3 `Step` nodes, 1 `START` + 3 `HAS_STEP` + 2 `TRANSITION` edges (6 structural edges, confirmed by direct `RO_QUERY` immediately beforehand), plus 7 attached `WorkflowRun`s via `OF_DEF` (2 of them `status:'waiting'`, the rest `done`/`failed`, which per `repository.py:1473-1500` clear `AT_STEP` on completion). Expected relationship deletions: 6 + 7 (`OF_DEF`) + ≤2 (`AT_STEP` on the still-waiting runs) ≈ 15. The actual `GRAPH.QUERY ... DETACH DELETE` result reported **34** relationships deleted (4 nodes). Follow-up scoped queries confirmed the deletion was otherwise clean and correctly scoped (0 remaining `triage:v1:*` `Step`s, `access-request@v1`'s 6-step snapshot and 14 `OF_DEF`-linked runs untouched) — so this is a discrepancy in the *count*, not evidence of an incorrect blast radius.
- **Context:** same `triage@v1` snapshot-resync task. Did not have a chance to re-query the pre-delete state to reconcile the extra ~19 relationships (data was already gone by the time the count was noticed) — plausibly stale/uncleaned `AT_STEP` edges on nominally-terminal runs, or another edge type into `Step`/`WorkflowDefSnapshot` not covered by this read (`LAST_STEP_RUN`/`HAS_STEP_RUN` attach to `StepRun`, not `Step`, per the entry above, so they shouldn't be it).
- **Suggested home:** unsure — flagging as an open observation. A future operator doing a similar scoped `DETACH DELETE` on this schema should count relationships on the target subgraph *before* deleting (`OPTIONAL MATCH (n) WHERE n IN [...] -[e]-() RETURN count(DISTINCT e)`) rather than trusting the structural-edge arithmetic, and/or check whether `advance_run`'s `AT_STEP`/`LAST_STEP_RUN` FOREACH-guarded writes (`repository.py:1382-1388`) can leave stale edges on old runs under some race — worth a `graph-dba` follow-up if it recurs.
