## 2026-08-16 — a live `pytest -m live` run doing ~50 sequential local-LLM round trips against LM Studio takes ~3 minutes wall-clock, exceeding Bash's default 120s foreground timeout
- **Evidence:** `falkor-chat`'s K-026 eval harness (`server/tests/eval/test_judge_live.py`) issued ~50 sequential `.complete()` calls (20 generation + 20 judge-of-generation + 10 calibration-judge) against a local `qwen/qwen3-4b-2507` via LM Studio; the foreground Bash call auto-moved to background after 120s, final run time `175.92s (0:02:55)` per `time`'s own output. Resolved cleanly with `Monitor` polling `kill -0 <pid>` on the backgrounded process, no manual sleep-looping needed.
- **Context:** K-026 GraphRAG eval harness QA acceptance pass (TP-005, `docs/test-plans/graphrag-eval.md`).
- **Suggested home:** knowledge base (`qa-engineer/qa-testing-techniques.md`) — a live-marked suite with many sequential local-LLM calls should be launched expecting >120s and either use `run_in_background` proactively or be ready to hand off to `Monitor`/an until-loop rather than assuming a single foreground Bash call will return in time.

## 2026-08-16 — a prompt instruction that both prior static gates verified as "correct, near-verbatim, word-for-word matching the plan" can still fail to manifest in a live dispatch, in three distinct ways at once
- **Evidence:** `cpg-agent-adoption` (M4) acceptance pass, 3 live subagent dispatches on small real tasks. All three agents' prompt wiring had already been independently verified twice (plan gate + diff gate, both `analyst`, both zero findings on the wording itself). Live behavior still diverged: `coder` used the CPG and reasoned about freshness correctly but never emitted the literal `CPG: <shape> — <clause>` line the convention requires (used "**CPG freshness note:**" prose instead — a `grep "CPG:"` spot-check gets a false negative despite correct underlying behavior); `architect` used the CPG but explicitly declined to run the paired "mandatory, not a separate optional pass" freshness check, substituting its own weaker cross-check reasoning; `tdd-engineer`, given a task in a component with no loaded CPG, produced a response with zero mention of "CPG" in any form — indistinguishable from the check never having run at all. See `docs/test-reports/cpg-agent-adoption-report.md` DEF-1/DEF-2/DEF-3.
- **Context:** `cpg-agent-adoption` (M4) U6 acceptance pass — the requirement's own AC-2/AC-3/AC-4 (evidence-trail line + freshness signal + stale-surfacing) targeted exactly this behavior.
- **Suggested home:** knowledge base (`qa-engineer/qa-testing-techniques.md`) — when the acceptance criteria for a feature are *prompt-compliance* claims about an agent's own output (a required line, a mandated sub-step), treat a clean static/diff gate on the prompt wording as necessary but never sufficient; budget for live-dispatch sampling as a distinct, required test layer, and expect independent, differently-shaped failure modes per dispatch rather than one shared root cause — a single passing dispatch does not predict the next agent's compliance, even when both carry near-identical prompt wording.

## 2026-08-16 — a live re-dispatch confirming three prior defects closed surfaced a fourth, previously-unseen defect in the same convention's decision surface
- **Evidence:** `cpg-agent-adoption` (M4) U9 re-pass, re-running D1/D2/D3-equivalent dispatches against `coder`/`architect`/`tdd-engineer` after two analyst-diff-gated fix rounds (`bafc3a7`, `59af4df`). DEF-1 and DEF-2 closed cleanly with reversed-failure-mode evidence. DEF-3's silence failure (zero CPG mention) also closed — a `CPG:` line was present — but the line used the wrong one of the convention's three defined shapes (`CPG: not applicable —...` where the plan's own worked example calls for `CPG: considered, not relevant —...` for a "component has code but no loaded CPG" case). This shape-selection error was invisible to Pass 1 because Pass 1's D3 never emitted any `CPG:` line at all — there was no line to check the shape of.
- **Context:** `cpg-agent-adoption` (M4) U9 acceptance re-pass (`docs/test-reports/cpg-agent-adoption-report.md` Pass 2, DEF-4).
- **Suggested home:** knowledge base (`qa-engineer/qa-testing-techniques.md`) — when a re-pass is scoped narrowly to "confirm these N named defects are closed," still read every re-dispatch's full output for compliance with the *whole* convention/contract, not just the specific clause each defect targeted; fixing a defect can newly expose a previously-masked decision point (here: which of 3 shapes to pick) that the original failure mode had been hiding entirely. A "confirm closure" re-pass is still a fresh opportunity to find a new defect, not a narrower check than the original.

## 2026-08-17 — a `coder` dispatch, faced with a populated `:CpgBuildInfo` marker whose `SOURCE_COMMIT`/`SOURCE_DIRTY` were absent (scratch-copy build with no `.git`), substituted the real repo-relative source path for the marker's literal (unusable) `SOURCE_PATH` and ran the stronger git-log staleness check anyway, rather than falling back to raw-age-only reasoning as `freshness.md`'s own "Limits" section implies is the ceiling for this build pattern
- **Evidence:** C-409 follow-up dispatch (`docs/test-plans/cpg-agent-adoption2.md` TP-002, `docs/test-reports/cpg-agent-adoption2-report.md`). `cpg_falkorchat`'s marker: `SOURCE_PATH = /tmp/cpg-src/falkor-chat-server` (a `.git`-less scratch copy, never itself tracked), `SOURCE_COMMIT`/`SOURCE_DIRTY` = null. The dispatched `coder` agent ran `git log --since=<builtAt> -- falkor-chat/server` (the *real* repo-relative directory the scratch copy was staged from, correctly inferred from context, not from any field in the marker itself) instead of either skipping the check or literally querying `-- /tmp/cpg-src/falkor-chat-server` (which would silently return zero commits too, but as a meaningless artifact of the path never being tracked — not a true "unchanged" signal). Independently confirmed the substituted path was in fact the correct source directory for this graph's known build pattern (`docs/plans/cpg-agent-adoption-graph.md` §6).
- **Context:** targeted C-409 follow-up — first live observation of an agent reasoning over a real, populated freshness marker (all three prior live dispatches only ever saw zero rows).
- **Suggested home:** knowledge base (`skills/cpg-analysis/references/freshness.md`) — the recipe's "Limits" section currently reads as "no stronger check is possible" for a `.git`-less scratch-copy build, full stop. This dispatch showed a capable agent can still derive a real (non-fabricated, verifiably correct) stronger signal when it can independently infer the scratch path's real repo-relative counterpart from task context — worth an explicit note that such a substitution, when it can be confirmed correct, is valid signal and not an over-reach past the documented limitation; also worth flagging the adjacent trap for a *less* careful agent: running the literal `sourcePath` through `git log` on this build pattern doesn't error, it just silently returns a spurious "zero commits" that reads as false confidence rather than "no signal available."
