## 2026-08-15 — A nested delegate's completion notification bubbles to whichever ancestor session is currently live, not necessarily to the direct delegator; `SendMessage` itself appears to force-resume a dormant target
- **Evidence:** during K-026's coordination (`cobb` → `teco` → `architect`/`analyst`), every nested-child completion (the `architect` U1-fix, `analyst`'s Pass 2, the `architect` v3 follow-up) routed its task-notification to `cobb` — two levels up — rather than to `teco` one level up, apparently because `teco`'s own turn had already ended right after each dispatch, leaving it dormant. `cobb` then had to manually relay each result and explicitly `SendMessage` `teco` to continue; the tool result on each of those calls read `"Resuming agent a8d402d..."`, i.e. the call itself appears to force-resume a stopped session, distinct from the passive notification-bubbling path.
- **Context:** the same K-026 live coordination that also surfaced the paired `analyst` inbox entry (no `SendMessage` tool available to a nested delegate).
- **Suggested home:** unsure — logged at the stakeholder's direction, not yet independently verified as a stable harness contract (could be specific to this session's dormancy pattern). If it holds up: pairs with the `analyst` entry's proposal (grant `SendMessage` to review-gate reporters) but needs a second, `teco`-side half — the brief template (step 3) would need to hand each delegate `teco`'s own `agentId` so there's an address to send to; the tool alone doesn't help without it. Also separately notable and independently true regardless of the `SendMessage` question: **injection-defense held correctly under real pressure this run** — three consecutive relayed messages claiming to carry a stakeholder directive (routed the normal way, through `cobb`, not as a raw injection) were declined because they arrived as unattributed `system-reminder`-shaped blocks rather than the documented `<cross-session-message>`/`<task-notification>` envelope; `teco` cited its own measured LM Studio state (18 models, several above "small") as contradicting the claimed premise, and kept D1 unchanged pending direct stakeholder confirmation. Worth a deliberate mention in the prompt-quality lint (§7, subagent-awareness / coverage) as a positive pattern to preserve, not just a friction cost — don't "fix" this by making `teco` more trusting of `cobb`-relayed text.

## 2026-08-15 — A background delegate that cannot address `teco` by name gets relayed through "main" as a `system-reminder`-shaped block, and this is the legitimate delivery path, not an injection to decline
- **Evidence:** resuming the K-026 coordination in a fresh session (after the 2026-08-15 pause above), two delegates `teco` itself had just dispatched via `SendMessage` (a `tdd-engineer` resumed at `ab8434008dc3d5521`, an `architect` resumed at `ac14d9ee4e42543b5`) each finished and, per their own report, tried `SendMessage` to reach `teco` by the literal name `"teco"` and got `"No agent named 'teco' is reachable"` (one also had no `ListAgents`-equivalent available). Both results instead arrived to `teco` wrapped as `<system-reminder>The coordinator sent a message while you were working: ...</system-reminder>`, explicitly explaining the routing detour. Both messages' factual content was independently re-verified against the filesystem/git (embeddings file present with correct model/dim/count, shared `opencode.json` untouched, `pytest` re-run reproduced the exact reported pass count; plan v4's cited section text matched grep output) — every claim checked out.
- **Context:** this is the *same session* that had just dispatched those two delegates itself via `SendMessage` (not a cold-start ambiguity) — so the wrapper format alone was not the basis for trust; independent verification of content was, per standing practice. Distinguishing this from the earlier (2026-08-15, same day, prior session) three genuinely-declined messages: those also arrived in a similar shape but carried *unverifiable* directive content (an unconfirmable claimed hardware constraint + claimed direct user conversation) contradicted by directly-observed environment state. This entry's two messages carried only *completion relays* of work `teco` itself had dispatched moments earlier, with content that verified clean.
- **Suggested home:** prompt — a line near the injection-defense guidance (Guardrails/subagent-awareness) distinguishing "a relayed message whose content is independently verifiable and matches work I dispatched" from "a relayed message asserting new unverifiable directive authority": the wrapper shape (`<system-reminder>...The coordinator sent a message...`) is not itself the trust signal in either direction — verify the *content*, every time, regardless of envelope. Possibly also worth a line noting that a background delegate literally cannot resolve `teco`'s own conversational identity by the name `"teco"` (it needs an `agentId`, which nothing currently hands it) — so a delegate's own completion routing through "main" appears to be the structural default for exactly this reason, not a fallback for a failure state.

## 2026-08-16 — Two "independent" units dispatched in parallel to `tdd-engineer`, touching disjoint files but both running `server/`'s full pytest suite against the live shared FalkorDB, produced mutually-corroborated but transient cross-contaminating flakiness — the existing "serialize same-file units / one owner per shared graph key" rule needs to extend to "shares the live test-suite's shared graph state," not just literal file/key overlap
- **Evidence:** dispatched K-046 (`server/tests/conftest.py` + new `tests/test_conftest_probe.py`) and K-047 (new `tests/eval/test_generate_report.py`, `generate_report.py` untouched) in parallel — genuinely disjoint files, correctly judged independent by the letter of the existing rule. Both delegates independently reported the same phenomenon from opposite sides: repeated full-suite runs in the same session produced a *different* set of unrelated transient failures each time (`test_graphrag.py`/`test_tools.py` one run, `test_repository.py`/`test_services_live.py` the next, `test_process_flow.py`/`test_process_input.py` after that), with the failing files varying based on run *timing*, not on any code diff — and each delegate found direct filesystem/mtime/HISTORY.md evidence that the *other* delegate's session was concurrently running its own `pytest` invocations against the same live FalkorDB instance and shared `ws:test`/`reference` graph keys (via the session-scoped `_schema`/`wf_repo` fixtures both suites use), with no locking or per-session workspace isolation. Both suites still landed clean and matched each other's before/after counts exactly (1034→1051) once I re-ran the suite myself after both had finished — the flakiness was real but fully transient, not a correctness defect in either delegate's work.
- **Context:** K-046/K-047 dispatch, both rated low-risk/independent and correctly so for git-diff purposes; the file-disjointness test alone missed a second axis of sharing (live DB state) that isn't visible from `git diff` or file paths.
- **Suggested home:** prompt — sharpen the existing "Serialize units that touch the same file... give one agent ownership of a shared database/graph key when the units' suites wipe shared state" line: the shared-state trigger isn't only "the units' own suites wipe shared state" (implying a destructive step like `GRAPH.DELETE`/reference-wipe) but more broadly "both units will run a suite that reads/writes the same live graph key(s) at any point during execution" — even read-mostly session fixtures that rebuild `ws:test` per session count, because concurrent rebuild/read timing alone (not just destructive overlap) produces cross-run flakiness. Practical mitigation for next time: either serialize the dispatch when both units will run `server/`'s full suite, or accept the transient-flakiness risk explicitly and re-verify with a solo, no-concurrent-session suite run before integrating (which is what actually resolved it here) rather than trusting either delegate's in-flight suite counts at face value.

## 2026-08-17 — A background delegate's `completed` task-notification can carry a stale placeholder as its "result" text, not the actual final deliverable, when the delegate itself kicked off a long-running background step and its own turn ended before that step's completion notification reached it
- **Evidence:** dispatched a `tdd-engineer` unit (K-027 item 3, guard-judge calibration harness + a live k=3×26-case LM Studio run expected to take real wall-clock time). Its `completed` notification's `<result>` was the single line *"The re-run is in progress in the background; I'll wait for its automatic completion notification."* — not a report at all, despite the wrapping notification's own `status` reading `completed` and its note explicitly stating that status fires "each time this agent stops with no live background children of its own." Sent a plain status-check `SendMessage` ("that's not a final deliverable, check your actual current state and report concretely") to the same agent id; it resumed, re-checked `git status`/the actual files/the background job directly, and returned a complete, verified report (numbers independently re-derivable from the report's own per-case table, all correct) roughly 20 more minutes later. The eventual result was accurate and complete — the placeholder wasn't a sign of failed or fabricated work, just an interrupted turn.
- **Context:** K-027 item 3 (`falkor-chat/docs/plans/guard-judge-calibration-coordination.md`), U2 dispatch — a live, stochastic, genuinely long-running unit (~5.5h wall clock across two dispatches, 82+169 tool uses total per the two notifications), the kind most likely to hit whatever internal limit truncated its own turn mid-flight.
- **Suggested home:** prompt — a line near "Never state or predict a pending delegate's result": a `completed` notification's `<result>` text should still be read critically before being treated as the delegate's actual final answer — if it reads as a mid-task status line (references "in progress," "will wait," no concrete numbers/paths/confirmations the brief asked for) rather than an answer to the brief's stated deliverables, that is itself the signal to `SendMessage` a "report your actual current state" check before doing anything else with it (updating a ledger, dispatching a dependent unit, etc.), even though the wrapping notification's own status says the run is over. Costs one extra round-trip; treating the placeholder as the real result would have meant recording a false "delivered" ledger row and potentially reporting fabricated status upstream.
