## 2026-07-24 — FastAPI's `response_model_exclude_unset=True` propagates into **nested** response models, so a defaulted field on a nested model silently disappears whenever the returned dict omits it
- **Evidence:** against the installed pydantic in `falkor-chat/server/.venv` — `class Inner(BaseModel): a: str; b: str = 'default'` / `class Outer(BaseModel): x: str; inner: list[Inner]`, then `Outer.model_validate({'x':'1','inner':[{'a':'q'}]}).model_dump(exclude_unset=True)` → `{'x': '1', 'inner': [{'a': 'q'}]}` — `b` is gone, not defaulted. FastAPI's `serialize_response` uses the same `exclude_unset` path. Consequence for review: `exclude_unset` is a correct way to make "absent" and "explicitly null" distinguishable on the top-level model (it is what `falkorchat/schemas.py:WorkflowDefStructureOut` uses to omit `startKeys` without `exclude_none` swallowing a legitimately-null `startKey`), but it silently turns every *nested* defaulted field into an optional one. The guard is an exact-key-set contract assertion on the nested object, not just the envelope.
- **Context:** K-031 implementation gate — judging whether the coder's third option (`response_model_exclude_unset=True`, chosen over both reviewer suggestions) interacted badly with any other field on the response models.
- **Suggested home:** knowledge base (a FastAPI/pydantic gotcha worth carrying across projects) or prompt (analyst — check nested models whenever a review meets `exclude_unset`)

## 2026-07-24 — FastMCP (`mcp` 1.28.1) emits an `outputSchema` even for a `-> str` tool, duplicating the whole payload as `structuredContent`; only `@mcp.tool(structured_output=False)` suppresses it

## 2026-07-24 — `GRAPH.PROFILE` is not read-only: it executes the query for real, so a `PROFILE`-prefixed write bypasses any `GRAPH.RO_QUERY`-based read-only guard
- **Evidence:** docs.falkordb.com/commands/graph.profile — *"Unlike `GRAPH.EXPLAIN`, `GRAPH.PROFILE` actually executes the query including any write operations (CREATE, DELETE, SET)"* (it suppresses `RETURN` output, not the side effects). Pairs with two facts already in `claude/graph-dba/falkordb-quirks.md:159-165`: `GRAPH.QUERY` on a non-existent graph materializes an empty key while `GRAPH.RO_QUERY` does not, and RO_QUERY rejects writes server-side. Also verified live on v4.18.11: an `EXPLAIN …` **prefix** inside `GRAPH.QUERY` is silently ignored and the query executes (`GRAPH.QUERY cpg_falkorchat "EXPLAIN MATCH (m:METHOD) RETURN count(m)"` → `747`); plans come only from the separate `GRAPH.EXPLAIN`/`GRAPH.PROFILE` commands. In `falkordb-py` 1.6.x, `Graph.explain`/`Graph.profile` take **no `timeout`** parameter (only `query, params`), unlike `query`/`ro_query`.
- **Context:** reviewing an MCP read-tool design that claimed read-only enforcement via `ro_query` while routing an `EXPLAIN`/`PROFILE` directive prefix to `Graph.explain()`/`Graph.profile()`.
- **Suggested home:** knowledge base (`claude/graph-dba/falkordb-quirks.md`, next to the existing RO_QUERY/empty-key entry)

## 2026-07-25 — FalkorDB ignores an `EXPLAIN`/`PROFILE` prefix even under `GRAPH.RO_QUERY`, and also when the prefix follows a Cypher comment
- **Evidence:** live, v4.18.11, read-only against `cpg_falkorchat`: `GRAPH.RO_QUERY … "PROFILE MATCH (m:METHOD) RETURN count(m)"`, `"EXPLAIN MATCH …"`, `"profile MATCH …"`, `"// hi\nPROFILE MATCH …"` and `"/* hi */ PROFILE MATCH …"` all return **747** — results, no error, no plan. ## 2026-07-25 — `CLAUDE_PROJECT_DIR` is set in the *spawned MCP server's* environment, not in Claude Code's config-expansion environment — so `bash -c` with an unbraced `$CLAUDE_PROJECT_DIR` is the portable launcher form

## 2026-07-26 — A containerized stdio MCP server is itself a running container for the whole session, so any `docker ps --filter label=…` "no orphans" check is unsatisfiable when run from inside a session
- **Evidence:** reviewing a plan whose verification step was `docker ps -a --filter label=cpg-mcp=1` with **done-condition: empty**, sequenced *after* an in-session `/mcp` + real tool call. The MCP stdio process owns the session's pipe for the session's lifetime, so the current session's own labelled container is `Up` at that moment: the filter can never be empty on a healthy system, and the step's follow-on instruction ("capture `docker inspect`, then `docker stop`/`docker rm` the survivor") would kill the live server it had just proved — and stdio servers are **not** auto-reconnected (`code.claude.com/docs/en/mcp` §Automatic reconnection), so recovery costs a session restart. The author's own probe (`docker ps -a --filter label=… ` → empty) was measured with no session open, which is why the gap did not surface.
- **Context:** re-reviewing a containerization design for the repo's `cpg` MCP server; this was the sharpest finding of the pass and came from asking "where in the sequence is this command actually run?" rather than from reading the command itself.
- **Suggested home:** prompt (reviewer habit: for every verification step, check *where in the sequence* it runs and what the system state is at that point — a correct command can have an unsatisfiable done-condition) or knowledge base (containerizing stdio/MCP processes: liveness-aware orphan checks — expect N `Up` per open session and zero `Exited`, and only assert "empty" with all sessions closed)

## 2026-07-31 — A `cp -r` scratch copy + `patch -p<N> -R` verifies "was this test red before the fix?" on an *uncommitted* diff with literally zero touch to the tracked working tree — stronger isolation than `git stash`, not a route around its block
- **Evidence:** a `git stash push --keep-index -m "…" -- falkor-chat/server/falkorchat/executor.py` attempt on this review was denied by auto mode's Bash classifier ("Blocked by classifier … modify the working tree"). That classifier is a harness-level, product Bash safety check — **not** one of this repo's `claude/scripts/guard-*.sh` hooks (those match specific destructive command patterns/paths and don't reach `git stash` at all), so there is no repo-owned mechanism here to special-case. Rather than re-attempt the blocked command in another form, the review used a substitute that needs no working-tree write of any kind: `cp -r <component>/server "$SCRATCH/server-check"`, `git diff -- <file> > "$SCRATCH/x.diff"`, then inside the scratch copy only, `patch -p<N> -R < "$SCRATCH/x.diff"` (N = the diff's path depth relative to the copy root — here `-p3`). Symlinking `.venv` and any repo-root-relative script dir the fixtures shell out to let the reverted copy's pytest run for real, including live-FalkorDB integration tests. `git status` on the real tree before/after confirmed zero residue — same discipline as the existing 2026-07-24 entries (stub-package HEAD-vs-working-tree import, review-safe pytest subset), which this one joins rather than supersedes.
- **Scope note (read before reusing):** this is **not** a general "when a classifier blocks you, find another way to the same effect" pattern, and the entry should never be read that way. The classifier's block was doing its job — a working-tree mutation is exactly the class of action that deserves scrutiny. This substitution is fine *because* it doesn't touch the tracked tree at all, which is a strictly stronger property than the blocked command (even `--keep-index`), not a lower-visibility path to its effect. A future reader reaching for this entry should confirm their own substitute is actually zero-touch, not just "the classifier didn't catch it."
- **Context:** implementation-review gate on the K-039 `mention-reply-delivery` mitigation (`falkor-chat/docs/reviews/mention-reply-delivery-impl.md`) — needed to independently confirm the new regression tests were genuinely RED pre-fix, not tautological, without disturbing the uncommitted working tree under review.
- **Suggested home:** prompt (analyst — the zero-mutation scratch-copy-and-reverse-patch technique belongs beside the existing 2026-07-24 stub-package entry, under "verifying claims about an uncommitted diff without touching the working tree"). The classifier behavior itself is not actionable in this repo (no `claude/scripts/guard-*.sh` reaches it) — at most it's product feedback, filed separately from this technique note.
