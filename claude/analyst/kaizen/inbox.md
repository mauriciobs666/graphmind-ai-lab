# Kaizen — Learnings Inbox: analyst

> Append-only capture of durable, non-obvious environment facts the `analyst` agent
> discovers during runs — raw observations, not conclusions. The maintainer (cobb)
> periodically distills this inbox (agent-maintenance skill §5): verifies each entry,
> routes it (prompt / knowledge base / project docs / discard), logs the promotion in
> `history.md`, and clears it. The agent only appends here; it never promotes.
>
> Entry format (append at the end):
>
> ```markdown
> ## YYYY-MM-DD — <the fact, one line>
> - **Evidence:** what was run/read/observed (command, file:line, output)
> - **Context:** the task where it surfaced, one line
> - **Suggested home:** prompt | knowledge base | project docs | unsure
> ```

## 2026-07-19 — `falkor-chat/server` pytest silently self-skips ~half the suite when FalkorDB is down, so "N passed" alone is not evidence
- **Evidence:** `cd falkor-chat/server && .venv/bin/python -m pytest -q` with no FalkorDB container running → `171 passed, 177 skipped, 1 deselected` (skip reason: "FalkorDB not reachable — start it with ./scripts/start_falkordb.sh"); with the DB up the same command is reported as `348 passed, 1 deselected`. `171+177+1 = 349` collected either way, so the *collected* count is stable while the *passed* count halves. `docker ps` is the one-command precheck.
- **Context:** analyst implementation gate on `aa8b813` (K-022 Landing 2) — a claimed-green suite had to be reported as partially unverified, and the drive-level Defect-B regression pin (`tests/test_executor.py`, `wf_repo` fixture) was among the skipped.
- **Suggested home:** project docs (`falkor-chat/AGENTS.md` M1-server section, next to the existing "needs FalkorDB up" note — make the skip-vs-fail behavior and the expected pass/skip split explicit)

## 2026-07-19 — Byte-identity of a "locked" function is cheap to verify mechanically with an AST line-range hash, and separates docstring-only edits from real ones
- **Evidence:** `ast.parse` → walk for the `FunctionDef` by name → hash `src.splitlines()[node.lineno-1:node.end_lineno]` across `git show <rev>:<path>` extracts. On this run it proved `executor._drive_loop` identical (`71055f756280`, 2844 bytes) across `514346b`/`c3cc239`/`aa8b813` despite its line offset moving 310→324, which a `git diff` line-range check would have mis-read. A second pass comparing `ast.dump` with docstring `Expr` nodes stripped showed `_drive` was docstring-only.
- **Context:** the gate's mandatory "the §2.1 A/B/C drive loop must be byte-for-byte unchanged" confirmation.
- **Suggested home:** prompt (analyst — a standard technique for "this artifact is locked, prove it didn't change" confirmations)

## 2026-07-24 — `pytest --collect-only -q` is the non-mutating way to get a `falkor-chat/server` test count; an actual run wipes the shared global `reference` graph
- **Evidence:** `cd falkor-chat/server && .venv/bin/python -m pytest --collect-only -q` → `551/552 tests collected (1 deselected) in 0.57s`, no FalkorDB connection made, nothing written. A real run cannot be used for the same purpose during a review: `tests/conftest.py:85-93`'s `wf_repo` fixture does `db.reference_graph(conn).query("MATCH (n) DETACH DELETE n")` at **setup**, and `scripts/test_queries.sh` deletes `reference` at **teardown** — either one destroys the live seeded `triage@v1`/`access-request@v1` defs while each `ws:<id>` snapshot survives (the documented split-brain).
- **Context:** K-031 plan gate — needed to check the plan's "pytest 533 → 533 + N" baseline claim without mutating shared state, and to separate a concurrent agent's uncommitted test additions from the stated baseline.
- **Suggested home:** prompt (analyst — "verify a claimed suite count without running the suite" belongs with the existing skip-vs-fail entry) or project docs (`falkor-chat/AGENTS.md` M1-server section)

## 2026-07-24 — In `falkor-chat`, a workflow **def** publish has no graph seam (hardcoded global `reference`); the isolatable equivalent is the **snapshot** side, which reuses the identical query constant
- **Evidence:** `repository.Repository._reference()` (`server/falkorchat/repository.py:132-134`) → `db.reference_graph()` (`server/falkorchat/db.py:87-94`) is `db.select_graph("reference")` — a literal, with no parameter, env var or `config.py` override. So `publish_def` can only ever write the global graph, and "publish a probe def into a throwaway workspace" is impossible. But `materialize_snapshot` (`repository.py:1483`) formats **the same** `_PUBLISH_CYPHER` constant (`:937`) with `label="WorkflowDefSnapshot"` against `self._graph(ws)`, and `get_snapshot`/`_read_subgraph` (`:976`) read it back with the same `_READ_META_CYPHER` (`:961`) — so any engine-semantics probe about publish/read behaviour can be run byte-identically in a throwaway `ws:<probe>` graph and torn down with `GRAPH.DELETE`.
- **Context:** K-031 plan gate — the plan scheduled a pre-implementation live verification "in an isolated throwaway workspace (never `reference`/`ws:acme`)" that was unexecutable as written; this is the reformulation that makes it isolated.
- **Suggested home:** project docs (`falkor-chat/AGENTS.md` — next to the `seed_workflows.sh` create-only trap row, as the "how to probe def/publish behaviour without touching shared state" note)

## 2026-07-24 — `falkor-chat/scripts/bootstrap_schema.sh` **always** runs `bootstrap_reference`, whatever arguments it gets — but that touch is DDL-only, so bootstrapping a throwaway workspace is safe for the shared `reference` graph's *data*
- **Evidence:** `scripts/bootstrap_schema.sh:238` calls `bootstrap_reference` unconditionally, before the `for wid in "$@"` loop (`:240-242`), so `./scripts/bootstrap_schema.sh k031probe` also hits the global `reference` graph. `bootstrap_reference` (`:37-70`) is exclusively `CREATE INDEX` (×5) + `GRAPH.CONSTRAINT CREATE` (×3) — no `MERGE`, no `CREATE (n:…)`, no `DELETE` — and the header (`:8-10`) records that duplicate-DDL errors are non-fatal under `set -euo pipefail` because `redis-cli` exits 0 on Redis-level errors. So the *only* cross-graph effect of bootstrapping a probe workspace is idempotent DDL. (Same reason `tests/conftest.py:60-66` can shell out to it per session without disturbing published defs.)
- **Context:** K-031 plan re-gate — verifying that a plan's "this probe never touches `reference`" isolation contract actually holds, given its first step bootstraps a throwaway `ws:k031probe`.

## 2026-07-24 — When a fix pass lands on an *uncommitted* tree, the round-1 review's own quoted `file:line` numbers are the only proof available that untouched code stayed untouched
- **Evidence:** K-027 slice A re-gate. Both the reviewed change and the fix pass were uncommitted, so `git diff` shows their union and no pre-fix baseline exists (no stash, no `.orig`). The implementer claimed "all 8 positive pins survive by name, unchanged". Verified instead by checking that every line number round 1 had quoted still lands on the same construct — `test_llm.py` 224-229 (fixture), 263, 296, 312, 323, 332, 340, 354 — while the round-1 pin quoted at `:362` had moved to `:448`, i.e. the new blocks are **pure insertions at 362 and 426**; anything edited *above* 362 would have shifted 224. Same check on `test_app.py` (249/260/266 unmoved ⇒ the helper functions at 231-245 predate the pass). Combined with reading the bodies, that is sufficient; alone, neither is.
- **Context:** re-gating a 13-disposition fix pass against a prior `analyst` review, with a concurrent agent's unrelated change in the same working tree.
- **Suggested home:** prompt (analyst — two halves: (a) when reviewing an uncommitted diff, quote `file:line` for *every* finding and for the pins you certify, because that is what makes a later re-gate provable; (b) at re-gate time, line-number invariance + body inspection is the substitute for a diff)
- **Suggested home:** project docs (`falkor-chat/AGENTS.md` key-scripts table, `bootstrap_schema.sh` row — "always bootstraps `reference` too; DDL only, no data")

## 2026-07-24 — A `HEAD` version of a `falkor-chat/server` module can be loaded *alongside* the working-tree one to verify a "red before the fix" claim, but only via a stub package — PYTHONPATH shadowing does not work under the editable install
- **Evidence:** `pip install -e '.[dev]'` registers an `__editable___…_finder` **MetaPathFinder**, which is consulted before any `sys.path` entry, so copying the tree to a scratchpad dir and prepending it to `PYTHONPATH` still imports the working-tree `falkorchat`. What does work, with no working-tree write at all: `git show HEAD:falkor-chat/server/falkorchat/llm.py > $SCRATCH/llm_head.py`, then in the venv build a stub package to satisfy the relative import — `pkg = types.ModuleType("hp"); pkg.__path__ = []; sys.modules["hp"] = pkg`, `sys.modules["hp.config"] = <ModuleType with LLM_BASE_URL/LLM_MODEL>` — and `importlib.util.spec_from_file_location("hp.llm", …)`. Both versions are then importable in one process (`old._parse_chat_message` vs `new._parse_chat_message`) and a behaviour table diffs directly. Works because `llm.py`'s only intra-package import is `from . import config`; a module with a wider relative-import fan-out needs more stubs.
- **Context:** K-027 slice A impl gate — the implementer claimed "19 new tests, 11 red before the fix, 8 negative pins green before and after"; this reproduced the exact 11/8 split and additionally surfaced an undisclosed `HEAD`→new behaviour change (`{"tool_calls": [], "name": …}` envelopes now yield a call), without `git stash`, a worktree, or any edit.
- **Suggested home:** prompt (analyst — the standard technique for "was this test actually red before?" and "what else changed vs. baseline?" on an uncommitted Python diff)

## 2026-07-24 — An interrupted `analyst` run can leave a complete-looking review at the deliverable path whose "executed" claims were written *before* the command ran — re-verify any shared-state claim against the live system before inheriting it
- **Evidence:** a resumed K-027 review was briefed that `falkor-chat/docs/reviews/k027-parse-robustness.md` did not exist; it did (22 KB, fully structured, verdict + 12 findings), left by the interrupted attempt. Its evidence block asserted *"the `pytest` run wiped the global `reference` graph as documented. I re-ran `./scripts/seed_workflows.sh acme` afterwards. It printed `(created)` for **both** `reference` defs … `reference` is reseeded."* The live instance said otherwise: `GRAPH.QUERY reference "MATCH (n) RETURN labels(n)[0], count(*)"` → **0 rows**, while `GRAPH.QUERY ws:acme "MATCH (s:WorkflowDefSnapshot) …"` → both snapshots present. The doc had been written narrating the re-seed in past tense before (or instead of) the command actually running. Its *offline* claims all reproduced exactly when re-probed (SHA lock `71055f756280`, the 3 shadowing shapes, the `consumed`-cursor and duplicate-call findings), so the failure mode is specific to **side-effecting** steps narrated at write time.
- **Context:** K-027 slice A impl gate, resumed after an interruption; the stale claim would have told the coordinator the estate was healthy when `@mention`-to-start was in fact silently no-op'ing.
- **Suggested home:** prompt (analyst — when a deliverable already exists at the review path, treat its executed/side-effecting claims as unverified until re-checked; and write the "I ran the cleanup" sentence only *after* running it)

## 2026-07-24 — `falkor-chat/server/tests/test_services.py` is the *review-safe* pytest subset: pure `FakeRepo`, no FalkorDB, no `reference` wipe — so a reviewer can execute the service half of a change while shared state stays untouched
- **Evidence:** `cd falkor-chat/server && .venv/bin/python -m pytest -q tests/test_services.py -k "structure or diff_" tests/test_api.py::test_structure_response_model_start_keys_omission_all_three_directions` → `21 passed, 61 deselected, 1 warning in 0.44s` with no FalkorDB connection. `tests/test_services.py` builds `Services(FakeRepo())` (module-local fake, `tests/test_services.py:56-200`) and requests **no** conftest fixture; only fixtures that reach `conn`/`wf_repo` (`tests/conftest.py:69-93`) touch the graphs, and only `wf_repo` wipes the global `reference`. A `test_api.py` node id that doesn't request `wf_client` is safe for the same reason (that test builds its own throwaway `FastAPI` app). Complements the 2026-07-24 `--collect-only` entry: collect-only gives counts, this gives *executed* evidence at zero shared-state cost. Companion probe, also zero-risk: `./scripts/verify_workflows.sh <wsId>` (K-031, read-only, all `GRAPH.RO_QUERY`) reports whether the shared `reference`/`ws:<id>` defs are still in sync — a one-command before/after check for a review that must not disturb a live instance.
- **Context:** K-031 implementation gate, run against a live FalkorDB shared with a concurrent agent and an explicit "do not run the full pytest suite" constraint — needed executed evidence for the coder's claims without wiping `reference`.
- **Suggested home:** prompt (analyst — the "run the tests, but only the ones that can't mutate shared state" triage) or project docs (`falkor-chat/AGENTS.md` M1-server section)

## 2026-07-24 — FastAPI's `response_model_exclude_unset=True` propagates into **nested** response models, so a defaulted field on a nested model silently disappears whenever the returned dict omits it
- **Evidence:** against the installed pydantic in `falkor-chat/server/.venv` — `class Inner(BaseModel): a: str; b: str = 'default'` / `class Outer(BaseModel): x: str; inner: list[Inner]`, then `Outer.model_validate({'x':'1','inner':[{'a':'q'}]}).model_dump(exclude_unset=True)` → `{'x': '1', 'inner': [{'a': 'q'}]}` — `b` is gone, not defaulted. FastAPI's `serialize_response` uses the same `exclude_unset` path. Consequence for review: `exclude_unset` is a correct way to make "absent" and "explicitly null" distinguishable on the top-level model (it is what `falkorchat/schemas.py:WorkflowDefStructureOut` uses to omit `startKeys` without `exclude_none` swallowing a legitimately-null `startKey`), but it silently turns every *nested* defaulted field into an optional one. The guard is an exact-key-set contract assertion on the nested object, not just the envelope.
- **Context:** K-031 implementation gate — judging whether the coder's third option (`response_model_exclude_unset=True`, chosen over both reviewer suggestions) interacted badly with any other field on the response models.
- **Suggested home:** knowledge base (a FastAPI/pydantic gotcha worth carrying across projects) or prompt (analyst — check nested models whenever a review meets `exclude_unset`)
