### K-005 — `verify_workflows.sh` false-negatives an intact `ws:<id>` snapshot after `test_queries.sh`
- **Status:** 🔵 proposed (verified true, not yet actioned — outside `cobb`'s write remit)
- **Priority:** high — `verify_workflows.sh`/`test_queries.sh` are the standard operational hygiene loop after every query-suite run; a false "everything's missing" reading during a session resumption could plausibly prompt an unnecessary re-seed or, worse, a manual "fix," when the workspace snapshot was never actually touched.
- **Rationale:** distilling `kaizen_team` entry `c1e8a0a2-9b6b-4f0a-8f1a-3d6b6b2f6a01` (coder, 2026-08-24, K-050 M5 Stage 2). Raw claim: after `test_queries.sh` (which `GRAPH.DELETE`s both `ws:test` **and** `reference`), `verify_workflows.sh acme` twice reported the `ws:acme` **snapshot** itself MISSING — not just the `reference` def — even though `GRAPH.QUERY ws:acme "MATCH (s:WorkflowDefSnapshot) RETURN s.key"` showed it still present; the claimed fix was the full `bootstrap_schema.sh <wsId>` + `seed_demo.sh <wsId>` + `seed_workflows.sh <wsId>` sequence, not `seed_workflows.sh` alone (current AGENTS.md guidance).
- **Verified independently, traced to a real code path (not just re-confirmed the citation):** `falkor-chat/server/falkorchat/services.py:1748` `diff_def_snapshot`'s own docstring claims "one side missing is a first-class 200… the documented trap after a `pytest`/`test_queries.sh` run wipes `reference`" — true when `reference` *exists but is empty of the def* (its two `_repo.read_*_structure` calls return `None` cleanly). **False when `reference` doesn't exist as a graph key at all** (post-`GRAPH.DELETE`, `test_queries.sh`'s exact teardown): `repository.py:1717` `_read_structure` calls `graph.ro_query(...)` with **no exception handling** — a nonexistent-key read raises `ERR Invalid graph operation on empty key` (per `graph-dba/falkordb-quirks.md`'s existing "read via `GRAPH.QUERY`/`RO_QUERY` on an absent key" entry), uncaught inside `diff_def_snapshot` too, and propagates all the way to `verify_workflows.sh`'s own `read()` wrapper, which catches **any** `ResponseError` containing `"empty key"` and returns the **whole-diff** `ABSENT` sentinel — `{"defPresent": False, "snapshotPresent": False, ...}` — even though only the `reference` side actually errored and the `ws:<id>` snapshot read never ran (or its result was discarded).
- **Two concrete fixes, not decided here:** (1) doc — `falkor-chat/AGENTS.md`'s `test_queries.sh` row currently says "Re-run `seed_workflows.sh <wsId>` afterward" as the remediation; that's incomplete once `reference`'s indexes/constraints were destroyed by the `GRAPH.DELETE` too — needs the full bootstrap sequence, and `verify_workflows.sh`'s row should note the false-negative-on-full-delete case so an operator doesn't mistake it for real data loss. (2) code — `_read_structure` (or its two callers) should catch the "empty key" case and return `None` per-side, matching what `diff_def_snapshot`'s own docstring already promises, instead of the exception silently defeating both presence checks.
- **Why kept open instead of applied:** both fixes land in `falkor-chat/`, outside `cobb`'s hook-enforced write remit (agent definitions, kaizen, `claude/`+`skills/` catalogs, and a short explicit MCP/agent-standards doc list — not project docs/code for other components). Recommend routing to `teco` (coordinates falkor-chat work, has commit authority for a coordinated specialist's verified deliverable) to assign the doc note to whichever agent owns `falkor-chat/AGENTS.md`'s script table and the code fix to `coder`/`tdd-engineer`, plus a `docs/BACKLOG.md` defect entry if the team wants it tracked formally (parallel to the existing K-049 precedent, opened the same way — `coder` surfaces it mid-implementation, `teco`/the doc owner files it).
- **Notes:** distillation source entry cleared from `kaizen_team` after this disposition was logged (2026-08-25) — this plan item, not the raw graph node, is now the durable record.
