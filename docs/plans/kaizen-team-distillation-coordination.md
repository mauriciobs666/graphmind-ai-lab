# Kaizen-team distillation — one producing agent per turn

> **Status:** archived · **Owner:** `teco` · **Tracks:** — (no backlog id; stakeholder-triggered `cobb` sweep of the shared `kaizen_team` graph)

## Context

Stakeholder asked to distill the shared `kaizen_team` FalkorDB graph's raw `:KaizenEntry` capture
— **one producing agent per turn**, not one all-at-once sweep. Precedent for *why* that matters:
the 2026-08 full-team sweep (`docs/plans/kaizen-inbox-distillation2-coordination.md`, review at
`docs/reviews/kaizen-inbox-distillation2.md`) processed 39 files in one uncommitted pass and
`analyst` returned **needs changes** with a blocker and five majors — a single big pass is where
that defect class showed up before. This coordination is scoped narrower (the `kaizen_team`
graph's raw entries, not a general documentation sweep) but keeps the same lesson: split per
producing agent, gate each, don't batch the risk.

**Snapshot at open (2026-09-16)**, `MATCH (a:Agent)-[:PRODUCED]->(k:KaizenEntry) RETURN
a.agentId, count(k)`:

| Agent | Raw entries |
|---|---|
| `analyst` | 16 |
| `frontend-engineer` | 8 |
| `architect` | 8 |
| `tdd-engineer` | 7 |
| `qa-engineer` | 5 |
| `coder` | 3 |
| `data-scientist` | 1 |

Order: largest batch first, so any systemic defect class surfaces on the biggest sample early.
Distillation procedure is `cobb`'s own, per `skills/agent-maintenance/SKILL.md` §5 (verify →
route → log → clear); `cobb` decides the actual promotion per entry. Each unit's deliverable
(prompt/skill/kaizen-file edits, working tree, uncommitted until gated) is diff-scoped-gated by
`analyst` before the next unit starts — same discipline as the 2026-08 precedent, applied per
agent instead of once at the end. **Revised after U1**: units are still strictly sequential
(they share `claude/cobb/kaizen/history.md`), but each dispatches a **fresh** `cobb` instance
rather than resuming the same one across units — U1's own instance hit ~258k tokens after its
fix round, and a later unit's work doesn't need U1's reasoning about a different producing
agent's entries (the large-context-delegate guidance applies). Resuming the *same* instance is
still right within a unit's own fix-and-regate cycle.
