# python-web-quirks KB: promote the 4b embedder to production `ws:agent-team`

> **Status:** active · **Owner:** `architect` · **Tracks:** — (W7 of `docs/plans/python-web-quirks-kb-path-ml.md` §6)

Plan for the stakeholder's approval. Nothing on `:8200` changes until the approvals in §7 are given. Every figure below was observed read-only in the run that wrote this plan unless marked "estimate" or "not observed".

## 1. Goal, scope, recommendation

**Goal.** Move production `ws:agent-team` (served by `:8200`) from `text-embedding-qwen3-embedding-0.6b` (1024-dim, skill floor 0.43) to `text-embedding-qwen3-embedding-4b` (2560-dim, floor 0.42), the configuration that passed sealed Set B3 on staging (115/126, near 4/30, off 0/30; `docs/test-reports/python-web-quirks-kb-report.md` W5).

**Out of scope.** Any workspace other than `ws:agent-team`; the server default embedder; chunking; the 17 S7 captures; deleting `ws:pwq-test` / stopping `:8210`; re-scoring any sealed set (B, B2, B3 are spent).

**Recommendation: Option A (in-place, per-workspace migration of `ws:agent-team` only), gated by a read-only pre-gate (§4 step 0) that can stop the whole thing before any outage.** Not promoting (Option C1) is the fallback if the pre-gate fails or the stakeholder declines the floor change.

## 2. Findings that shape the design

- **One server process serves exactly one workspace.** `/proc/1268/environ` of the `:8200` uvicorn: `FALKORCHAT_WS_ID=agent-team`, `FALKORCHAT_EMBEDDING_DIM=1024`, `AGENT_TEAM_PORT=8200`, `FALKORCHAT_OPENCODE_CONFIG=~/.config/opencode/opencode.local.json`, no `FALKORCHAT_MODEL_CONFIG`. `config.py:16` reads `WS_ID` once; `docs/plans/embedding-migration.md` §2.6 states the tenancy. Only two falkorchat uvicorns run now (pid 1268 on `:8200`, pid 3487158 on `:8210`). **Therefore stopping `:8200` takes down only the agent-team KB front door, not `ws:demo`, `salesperson`, `acme`, `eval` or `nlq-eval`**: the embedder note's §3(a) ("every workspace on that process, including `ws:demo` and the `salesperson` agent") is wrong for this deployment; the demo/storefront is a separate process (`scripts/start_demo.sh`, `FALKORCHAT_WS_ID=demo`, and `SERVER.md` says the storefront process mounts no `/mcp`).
- **Dimension is per model and per workspace, not server-wide.** The index dimension is DDL on each `ws:{id}` graph; the dimension an embedder is checked against is the overlay's `models.<ref>.dim`, else `FALKORCHAT_EMBEDDING_DIM` (`SERVER.md` §1.8 "embedding-dimension guard", `embedding.py:182-197`). Observed: `ws:agent-team` Chunk index still 1024 (staging doc), `ws:pwq-test` 2560 beside it in the same FalkorDB, with 4b ref declared `dim: 2560` in `falkor-chat/config/models.pwq-staging.json` (the diff against `config/models.json` is exactly that one entry). So 2560 for agent-team and 1024 for demo coexist; a **server-wide default change is the wrong lever**.
- **Pins observed this run:** `ws:agent-team` and `ws:demo` `WorkspaceConfig.embeddingModelOverride` = `lmstudio/text-embedding-qwen3-embedding-0.6b`. `acme`/`eval`/`nlq-eval` follow the default and `k069probe` is pinned, per the embedder note §3 (not re-observed). A migration of `ws:agent-team` sets only that workspace's override.
- **`ws:agent-team` today:** 505 `Document` (488 `ready`/agent, 3 `ready`/document, 14 `failed`/agent; **0 `processing`, not the 1 in the brief; 14 failed, not 17**: re-read at execution time), 884 `Chunk`, 871 embedded, 0 `Message`, 0 orphan chunks. The 13 unembedded chunks sit in 12 of the 14 `failed` documents (`pendingJobs` 0 on all 14). `Chunk.embeddingModel` is absent on production chunks. `pwq_kb.py gate` against `:8200` with `claude/cobb/scripts/pwq-kb-manifest.json`: **`gate: clean`** now (baseline).
- **Migration mechanics** (`falkor-chat/scripts/migrate_embeddings.sh`, `docs/DESIGN.md` §7.1): the serving process must be stopped; re-embeds every Message then Chunk whose `embeddingModel` is not the target (this includes the 13 null-embedding chunks: on staging it embedded the 16 previously unembedded chunks); drops and recreates both vector indexes at the target dimension; sets the override; the process must be restarted afterwards (dimension cache). Resumable and idempotent. On staging: 902 chunks in 75.0 s.
- **Startup script trap.** `scripts/start_agent_team.sh` (the supervised, locked, logged route; lock/log under `~/.local/state/graphmind-ai-lab/agent-team-8200.*`) deliberately never sets `FALKORCHAT_MODEL_CONFIG`, defaults `EMBEDDING_DIM=1024`, and re-runs `bootstrap_schema.sh` with it (`bootstrap_schema.sh:391-397` issues `CREATE VECTOR INDEX ... dimension:${dim}`; the script says duplicates return "already indexed" and do not abort). Run unchanged after migration it would try a 1024-dim create over a 2560 index: not observed what FalkorDB does with a differing dimension, so **start it only with `EMBEDDING_DIM=2560`** (see step 6).
- **Host.** `free -m` in WSL: total 5930 MB, used 2638, free 686, available 3291. FalkorDB `used_memory_human` 478.34 MB, persistence RDB only (`aof_enabled:0`, `rdb_changes_since_last_save:0`). Vector RAM for the migration is small (884 vectors x 2560 x 4 B is about 9 MB, arithmetic not measured); the 4b model itself loads in LM Studio (Windows side), not in WSL RAM; its footprint is not observed.
- **Staging is not production.** `ws:pwq-test` holds 518 documents (36 units, 17 S7 captures that production deleted, 465 shared with production); production holds 4 documents staging lacks (W3 §4), and any capture written since. B3's pass is for staging's competitor set, scored with the 17 excluded.

CPG: not applicable — operational migration plan; no code-level change is designed (the one repo edit, a config entry, is not code).

## 3. Options

| | Description | Verdict |
|---|---|---|
| **A** | Stop `:8200`; `migrate_embeddings.sh agent-team <4b>`; restart `:8200` with the 4b dim declared; other workspaces untouched via their pins. | **Recommended** |
| A2 | Change the server default embedder to the 4b (`config/models.json` `defaults.embedding`) instead of migrating. | Rejected: `acme`, `eval`, `nlq-eval` (no override) would then embed/query 2560-dim into 1024-dim indexes (`EmbeddingDimensionError` or silent garbage); the pinned `agent-team` would not move at all. |
| B | A second falkor-chat instance on another port serving the 4b workspace; repoint agents' MCP config. | Rejected (below). |
| B' | Variant: migrate a `GRAPH.COPY` of `ws:agent-team` on a side port while `:8200` keeps serving, then swap with `RENAME`. | Rejected: agents keep ingesting learnings into the live graph during the copy (newest document createdAt observed `1794342428342`, the KB is written continuously), so a delta merge or write freeze is needed, which costs more than A's outage. |
| C1 | Do not promote: keep 0.6b/0.43 in production, B3 pass stays a staging finding. | Valid fallback; costs the AC-3 miss recorded for production (B 73/84, B2 110/126 at the 0.6b). |
| C2 | Repoint agents to `:8210` (`ws:pwq-test`) as the 4b KB. | Rejected: stale copy (lacks 4 production documents and everything written after W3; carries the 17 deleted S7 captures), and a dev/test workspace becomes the team's raw-learning store. |

**Why B loses.** In this deployment "a second instance for the 4b workspace" is what every workspace already is (a separate process per workspace), so B = A plus a new port. Cost of B: the new port must be repointed in `.mcp.json` (`falkor-chat-agent-team` -> `http://localhost:8200/mcp`; `~/.claude.json` also contains one `8200` string, content not inspected), `claude/cobb/scripts/pwq_kb.py` `TARGETS` (`agent-team` -> `http://localhost:8200`, a hard check), `start_agent_team.sh` and docs that name `:8200` (`falkor-chat/docs/SERVER.md` §1 lines 686 and 904, `falkor-chat/AGENTS.md`); two copies of the KB drift unless cut over at one instant, which is the outage A already takes. The one thing B buys (instant rollback by flipping a URL) A gets from the pre-migration copy plus a supported re-migration (§5). **Deciding trade-off:** A changes one workspace's state with a ~5 minute single-door outage; B changes consumer configuration across many agents and keeps two stores.

## 4. Runbook (Option A)

Owners: `devops` (processes, LM Studio, backup), `graph-dba` (migration, indexes, copy), `qa-engineer` (gate, regressions), `coder` (the one config edit), `cobb` (skill), `teco` coordinates; stakeholder approvals in §7 precede step 1. Time estimates are estimates; staging measured 75.0 s for 902 chunks.

**Step 0: pre-gate on staging, read-only, no outage (`qa-engineer`, `data-scientist` reads).** Re-run the Stage 8 45-pair golden set (design in `claude/docs/plans/agent-knowledge-base-strategy-ml.md` "Stage 8 Phase 1"; baseline report `claude/docs/test-reports/agent-knowledge-base-strategy-ac2-report.md`: pooled recall@5 0.875 at the 0.6b) against `:8210` (4b, 2560) **and**, for a same-corpus baseline, against `:8200` today (the corpus changed since 2026-09-19), using the skill's literal prefix and `limit=5`, with floors 0.43 and 0.42 reported side by side, plus the closest-negative scores and the R6 document's score. Expected ids are production ids: map by id where staging shares the document (465 shared), mark rows that do not map. **Go/no-go:** no regression in pooled recall@5 against the same-day `:8200` run, no new false accept among the 6 negatives at 0.42, and no true positive whose 4b score exceeds 0.42 that scored at or under 0.43 at the 0.6b (any such row is listed for a `data-scientist` call on the floor, which is a stakeholder decision, never tuned on a sealed set). Also run the §6 non-pwq smoke queries on `:8210`. Outcome goes into a `docs/test-reports/` addendum.

**Step 1: pre-checks (`devops`, `graph-dba`).**
1. No demo is running (storefront process stopped; `ensure_demo_models.sh`/`start_demo.sh` header: keep `:8200` idle during a demo, the 4b may evict the demo's resident models) and nobody has an `ingest_document` batch in flight.
2. LM Studio reachable, 4b present (`GET localhost:1234/v1/models` lists it), one probe embedding returns 2560 values; note the timing.
3. `curl :8200/health`; capture `pwq_kb.py gate` output and the counts of §2 as the "before" record (documents by status, chunks, embedded).
4. Backup, in order: (a) `redis-cli BGSAVE` on FalkorDB (rdb only; wait for `rdb_last_save_time` to change) so the volume holds a restorable dump; (b) `GRAPH.COPY ws:agent-team ws:agent-team-pre4b` (verify node counts equal and `db.indexes()` on the copy; do not serve it; `claude/graph-dba/falkordb-quirks.md` says GRAPH.COPY transiently doubles RAM, trivial at this size; whether the copy carries the vector indexes is not observed, verify; if not, rollback R2 below is documents-only); (c) a logical export: every `Document` id, title, status and verbatim text via `GET /documents/{id}` into a file outside the repo (vectors are regenerable, text is not). Rollback artefacts are untracked and live outside git; their location is recorded in the ledger.
5. Tools stopped or told: announce the outage to the stakeholder (agents cannot be messaged; they hit FR-9 degraded mode).

**Step 2: declare the 4b dim in the shipped config (`coder`, one edit).** Add `"lmstudio/text-embedding-qwen3-embedding-4b": {"dim": 2560}` to `models` in `falkor-chat/config/models.json` (default stays the 0.6b). Reasons: the migrate precondition needs the dim declared; `start_agent_team.sh` must not carry an overlay; the staging overlay `models.pwq-staging.json` equals this edit and is left alone. The running `:8200` ignores the edit until restarted. Check: `python -c` resolving the ref through `modelconfig.ModelGateway` from the server venv, and the falkor-chat offline suite's config tests if any reference `models.json` shape (not run by this plan).

**Step 3: outage begins (`devops`).** Stop only pid 1268 (confirm with `ss -ltnp` that it listens on `:8200` and its environ shows `FALKORCHAT_WS_ID=agent-team`; the `:8210` process is untouched).

**Step 4: migrate (`graph-dba`).** From `falkor-chat`:
`FALKORCHAT_OPENCODE_CONFIG=$HOME/.config/opencode/opencode.local.json ./scripts/migrate_embeddings.sh agent-team lmstudio/text-embedding-qwen3-embedding-4b --i-have-stopped-traffic`
Expect `Chunk: migrated 884/884`, `Message: migrated 0/0`, then override and indexes at 2560 (staging log format). Verify by read-only Cypher: both vector indexes `dimension: 2560`; 0 chunks without `embedding`; all chunks `embeddingModel` = the 4b ref; override = the 4b ref; document/chunk counts equal step 1.3; `ws:demo` override still the 0.6b and other graphs unchanged.

**Step 5: restart (`devops`).** `EMBEDDING_DIM=2560 AGENT_TEAM_PORT=8200 ./scripts/start_agent_team.sh` (same env as the old process: `FALKORCHAT_OPENCODE_CONFIG`, FalkorDB 127.0.0.1:6379; log under `~/.local/state/graphmind-ai-lab/`). Check the log for startup complete with no dimension error. If the script's bootstrap step misbehaves on the existing 2560 index, fall back to the `uvicorn falkorchat.app:app --port 8200 --log-config config/logging.json` command from `server/` with the old environment and `FALKORCHAT_EMBEDDING_DIM=2560`, exactly as W1 did for `:8210` (`docs/plans/python-web-quirks-kb-staging-graph.md`). Outage ends when `/health` is 200 and step 6 starts. **Estimated outage: under 10 minutes (estimate; migrate 75 s on staging).**

**Step 6: verification (`qa-engineer`, read-only).**
1. `pwq_kb.py gate --ws agent-team --base-url http://localhost:8200 --manifest claude/cobb/scripts/pwq-kb-manifest.json --copy claude/knowledge/python-web-quirks.md` -> `gate: clean`.
2. `pwq_kb.py eval --set A --floor 0.42 --sweep ...` same target flags, plus the perturbed forms W3 used (`docs/test-reports/python-web-quirks-kb-report.md` W3 §2): compare with the 4b table there (raw 42/41/38/41, floor-applied 42/37/26/36, near FA 0/7, off FA 0/7, tolerance within 1 per form). Production has no `--exclude` need (the 17 S7 captures are deleted there). A sealed set is **not** re-run (sentinels spent).
3. The 45-pair set against `:8200` at 4b: must match step 0's staging result within noise; record the R6 document.
4. Non-pwq smoke (§6).
5. Ingest one disposable test document? **Not recommended** (production write, and no delete safety posture); instead verify new-document embedding by waiting for the next organic capture and checking `embedded == chunks`, `embeddingModel` = the 4b ref (`qa-engineer` re-checks within a day).

**Step 7: skill floor (`cobb`, only after step 6 is green).** In `skills/agent-kb-retrieval/SKILL.md`: floor 0.43 -> 0.42 in the frontmatter description, calling-convention step 4 and the "Score floor" section; replace "Qwen3-Embedding-0.6B (standing embedding model)" with the 4b; restate the derivation (rule: 1.03 x largest full-form Set A best-unit positive = 0.42 on the 4b, `docs/plans/python-web-quirks-kb-embedder-ml.md` §4) and that the R6-type instability caveat is re-measured at the 4b by step 6.3 rather than inherited. Exposure window between restart and this edit is minutes (agents at 0.43 on 4b scores are slightly looser; agent sessions that cached the skill keep 0.43 until they restart: accepted). The skill's other numbers (top-K 5, prefix literal) do not change; `pwq_kb.py` reads the prefix from the skill and takes `--floor` explicitly, so it needs no edit.

**Step 8: record (`teco`).** `docs/HISTORY.md` entry (this repo's root history is the CPG component's; this feature's record lives where W1-W5 went: the test report and coordination ledger, `docs/plans/python-web-quirks-kb-coordination.md`), report addendum with before/after counts and the backup locations, plus an update of the live-spec statements that name the 0.6b for `ws:agent-team` (cite `falkor-chat/docs/SERVER.md` §1.8 and `DESIGN.md` §1.3 `EMBEDDING_DIM=1024` rows; `analyst` checks the writer's diff per root `AGENTS.md`). ## 5. Rollback

- **R1 (default; keeps everything written after cutover).** Stop `:8200`; `migrate_embeddings.sh agent-team lmstudio/text-embedding-qwen3-embedding-0.6b --i-have-stopped-traffic` (the 0.6b `dim: 1024` is already declared in `models.json`; embedder note measured 18 s for 902 chunks); restart with `EMBEDDING_DIM=1024`; `cobb` reverts the skill to 0.43 / 0.6b; gate + Set A at 0.43 as in step 6. Re-embedded 0.6b vectors are not guaranteed bit-identical to the originals (the skill documents embedding-session instability on R6 at 0.4201 vs 0.4405).
- **R2 (only if R1 fails).** Stop `:8200`, `RENAME ws:agent-team ws:agent-team-failed`, `RENAME ws:agent-team-pre4b ws:agent-team` (plain Redis rename, `claude/graph-dba/falkordb-quirks.md`), restart at 1024. Loses every document written after step 1.4(b); re-ingest from the logical export or the failed graph. If the RDB dump of step 1.4(a) is needed, `devops` restores it with FalkorDB stopped (affects every graph, a last resort).
- **Decision trigger:** any of: step 6.1 not clean, Set A outside tolerance, the 45-pair pooled recall below step 0's staging figure, a non-pwq smoke query regression the stakeholder rejects, startup dimension errors that do not resolve in 15 minutes.

**Irreversible.** (1) The 13 previously unembedded chunks (12 `failed` documents, K-102) become embedded, hence searchable, and stay so after R1 (migration embeds every row; status stays `failed`). (2) Original 0.6b vectors are overwritten; R1 regenerates them approximately, only R2/restore gets the exact set, and R2 loses newer writes. (3) `Chunk.embeddingModel` is populated where it was absent. (4) The spent seals (B, B2, B3) cannot be re-run, so production's post-migration quality is checked by Set A and the 45-pair set only. (5) Agents' already-loaded skill text keeps 0.43 until their next session. Reversible: the skill edit, the `models.json` entry, the override, the indexes (by R1/R2), the process.

## 6. Verification detail, other agents' retrieval, ingestion afterwards

- **Non-pwq smoke (step 0 on staging, step 6.4 on production).** `qa-engineer` runs a fixed list of 10 situation queries drawn from the 45-pair set's non-pwq rows plus 4 raw-learning situations (for example one each on FalkorDB, asyncio, agent hooks, WSL/LM Studio, chosen without reading sealed data), with the prefixed literal, `limit=5`, floors 0.42 and 0.43: record top-1 title, score, count under floor; compare with the same queries on the 0.6b before migration (run the 0.6b leg in step 1, read-only). The pass condition is no query whose known answer drops out of the top five or above 0.42; anything else is shown to the stakeholder with the scores, not tuned.
- **Cobb and other agents.** Raw learnings and distilled claims share `ws:agent-team` and the same `search_documents` call (`skills/agent-kb-retrieval/SKILL.md`, "What this skill does not cover"). After migration all of them, including the raw captures, are embedded and queried by the 4b; scores change scale (4b: best positive 0.408 vs 0.417, closest near-negative 0.422 vs 0.380 on Set A), so any consumer with its own hard-coded floor needs the same edit: grep of this repo finds the 0.43 constant in the skill, plans/reports and `claude/cobb/scripts/pwq_kb_selftest.py` (selftest string, not a runtime floor); no agent prompt carries the number (they cite the skill). Quality of the 4b on non-pwq raw text is **not measured anywhere except by the 45-pair set**, hence step 0.
- **Failed documents.** Unchanged status (`failed` stays `failed`; this plan does not touch K-102's status question or the extraction job). The 12 documents with unembedded chunks become visible to semantic search after migration; the 2 failed documents whose chunks were all embedded stay as they were. No document is `processing` at observation; if one is at execution time, wait for it to terminate (migration re-embeds, but an ingest racing a stopped server is lost, `devops` confirms none is in flight).
- **New documents afterwards.** The ingestion pipeline resolves the embedder through the workspace override (hard cap) -> 4b at 2560, checked against the index dimension at first write after restart; the query side the same. Entity extraction (`extraction` default, `qwen/qwen3-4b-2507`) is independent. Each capture adds LM Studio load: 4b JIT embedding plus the extraction model share the single-slot GPU (K-102's candidate cause is model eviction mid-ingest); not measured with the 4b, so `qa-engineer` counts `failed` documents created in the week after cutover against the prior weeks' rate.
- **Other consumers named.** Every Claude agent through `.mcp.json` `falkor-chat-agent-team` (the twelve consumers in the skill description plus `cobb`, which writes raw learnings): reads/writes fail during the outage, and **already-open streamable-HTTP sessions may need a reconnect after the restart (not verified)**. `pwq_kb.py` (production target). `mcp-monitor`: no `:8200` reference in its checked-in docs/example config (its local `config.toml` not read); ask the operator whether a watch targets `:8200`. `ws:demo`/`salesperson`/`acme`/`eval`/`nlq-eval`: separate processes or no process, not affected, no step touches them. `tank` shares the LM Studio model copy only (`opencode/docs/HISTORY.md`). After cutover a later demo bring-up must not find the 4b resident as a "foreign" model: `ensure_demo_models.sh` behaviour with a resident embedder other than its own is not observed (its header says it warns on an embedder at another context, refuses on a foreign chat model); `devops` checks before the next demo.

## 8. Risks and open questions

- Floor margin is thin on both sides (rule floor 0.42, closest staging near-negative 0.422); embedding-session instability applies to the 4b too.
- B3 was scored on staging (17 deleted captures excluded; 4 production-only documents and newer captures absent); production's competitor set differs slightly, which is why step 6 re-runs Set A through the tool on production.
- GRAPH.COPY index carry-over, `start_agent_team.sh` behaviour on an existing 2560 index, streamable-HTTP reconnect, 4b LM Studio footprint and `ensure_demo_models.sh` with a resident 4b are **not observed**; each has a named fallback above.
- The brief's counts (17 failed, 1 processing) differ from the observed 14 failed, 0 processing; the runbook re-reads them in step 1.3.
- Pre-gate rows that do not map between staging and production ids reduce its power; recorded, not hidden.
- After promotion `ws:pwq-test`/`:8210` remain as a test double (stakeholder decides their retirement; nothing here removes them).
