## 3. Design and rationale

### 3.1 Scripts: a resolver in the assembler

**Layer: the assembler** (`cpg/ccg/assemble/rows.py`, a new pass after `symbol_ids`/`sym_path` exist, beside the `calls-target-not-in-snapshot` drop at l.546). Extractors run per unit and cannot see other units' files; only the assembler (system-wide snapshot) can match across units. The assembler adds the `CALLS` edge (`CallSite -> Symbol`), taking the call site's own status and reason, which exist today (`shell-dynamic`, `prompt-mention`), so the reason registry does not change.

**Carrier, ruled: existing record shapes; no bundle-schema change, no pin of the schema.**
- *Argument paths (families D, E, H):* the existing argument `valueSet` (`a0..`), verified to keep the literal tail and mark the dynamic head.
- *Computed command word (family G, 10 items):* a new `valueSet` record on the same call site with `arg: "recv"` and the same `values` shape as an argument, written only when `calleeName` is `<dynamic>` and the site is not an `eval`, and with no `data` flow records for it. This is inside the existing shape: the path grammar and `bundle-v1.schema.json` already admit `recv` as a `valueSet` `arg` (`cpg/ccg/bundle.py:285`, schema pattern at l.412), the id is `ids.value_set_id(callSiteId, "recv")`, `bundleSchemaVersion` and the rule-pack format do not move, and `cpg/ccg/packrt/` never reads a `recv` `valueSet` of a shell site (a negative test pins it). What it does change: bundle-spec3 §5.1 defines `recv` as the call's receiver, so the active bundle spec gains one sentence ("for a shell call site whose command word is computed, `recv` is the command word's value"), an `architect` documentation edit at the unit's close; the shell extractor's golden bundles and the fixture build's bundle bytes move, which §3.6 owns. If CO-2 finds a validator or consumer that rejects or misreads it, the alternative is a new path head, which **is** a bundle-schema amendment and a stakeholder-level decision; it is not made here.
- *Markdown tokens:* the call site's `calleeName`, as written (family A); a Markdown `curl` span's URL is a new `valueSet` (§3.3).

Tiers, in order, first match wins:
1. **Exact path:** a shell site's literal argument (`./x.sh`, `scripts/x.sh`), resolved relative to the calling script's directory then the unit root, naming a script file of the snapshot (a literal path that misses tier 1 does not fall into tier 2, CO-2c): the edge takes the call site's status (m2 below).
2. **Unique static-tail suffix match (stakeholder-ruled last tier):** the dynamic head (`$VAR`, `$(dirname "$0")`, `$HERE`) is dropped, `..` and `.` segments normalised, and the remaining tail, **at least two path segments**, is matched as a suffix against the snapshot's script files; **exactly one** match gives a `possible` edge; zero or several give no edge and a counted refresh-report line. Never `confirmed`. A one-segment tail never matches here (that is the rejected basename match); it matches only under the own-directory tier below.
3. **Own-directory tier (stakeholder-approved 2026-11-24, accepted as built in CO-2b):** behind any computed head, a one-segment tail with no `..` matches only a shell `<script>` in the **caller's own directory**; `possible`, existing reason reused. The bundle cannot say that the head is the caller's directory (a precise head check would be a bundle-schema amendment, declined), so the tier is judged as built and recorded in CO-6b as "same-directory file named by a computed path".

**Ancestor-directory tier: not built.** The literal-path restriction of tier 1 (CO-2c) loses 6 true edges (`bootstrap_schema.sh`, called as `./scripts/bootstrap_schema.sh` from `falkor-chat/scripts/test_queries.sh` and its five evidence copies under `falkor-chat/docs/reviews/`) for 0 dev hits; the loss is accepted (`docs/reviews/connected-code-graph-p1-closeout-co2.md` Pass 2, answer 1 and P2-3). Revisit only if CO-9 shows a built-family miss caused by it.

**Edge status (m2 ruling, CO-2 review Pass 2 item 5):** the edge takes the call site's own status; never `confirmed` on real data (the shell extractor marks every unresolved site `possible`).
4. A Markdown script mention uses tiers 1 and 2 on its token and is always `possible`/`prompt-mention` (a prose mention proves nothing). A shell site whose command word is computed (family G) and whose path is in the `recv` record uses tier 2 (or the own-directory tier).

**Rejected:** a new `Link` kind (bundle and answer-spec change for a lexical fact); basename matching (false-positive rate is what the wrong-`possible` bound measures); extractor-side resolution (cannot see across units).

### 3.3 DEF-1: one URL source, two carriers

A `curl`/`wget` URL in a shell script becomes an http consumer through a pack beside `shell-mcp-call` (`cpg/packs/shell-http-client/`, new, `callKind: command`): the 3 shell items already carry the URL in the argument `valueSet`, `possible` with the existing URL reasons when the URL has a dynamic part. **The Markdown carrier change is still needed** (CO-1 §6): the inline `curl` span's call site exists (`curl`, `possible`/`prompt-mention`) but carries **no `valueSet`**, because the Markdown extractor writes only a mention's name (`cpg/extractors/markdown/extract.py` module docstring). The change: for an inline span only (never a fence, the shipped "a fence is not a call" contract), write the first token of the span that starts `http://` or `https://` as an `a0` `valueSet` literal on that call site, through the token screen (`bundle.screen_fails`). The pack gets a second rule for the Markdown call kind (`callKind: mention`, callee `curl`/`wget`), emitting `possible`. The Markdown extractor's contract line ("a mention carries only its name") and `docs/plans/connected-code-graph-p1-extraction.md` P1-12 are amended in place at the close. No bundle-schema change.

### 3.4 Wiring: withheld

The 11 dev wiring items need a spec change (`docs/plans/connected-code-graph-answer-spec2.md` §3.3: a `config` item exists only as the `BOUND_BY` target of a `Link` reached by `TO <-`; `launchFact` entries are not items; the real build had 0 `bound[]` on 179 `Link` hops). Launches-a-script (4) and names-a-tool (3) are inexpressible; the 4 server-URL entries need a code consumer that the entry binds. **CO-1 proved it: 0 of 11 expressible** (`ConfigEntry` rows exist under every dev keyPath and no `Link` is bound to any; the launches-a-script class is 4 items, not 3; server URL 4, tool name 3). CO-4 (wiring) is removed; a reduced re-add would need a new failing-then-passing dev test and the stakeholder's say. Consequences: wiring's 8 held-out items stay blind; AC-2 and AC-4 wiring halves stay open; the gate certifies nothing about wiring.

### 3.5 Gate entry criterion

Pre-registered verbatim from the gate-marker note's last section ("Entry criterion", six items), with these plan-level readings: on the dev gold, at the freeze commit F, by a dispatch that has read no held-out material, **every dev item of a gated stratum is a hit, or is removed only as a stakeholder-confirmed `key-error`**; "triaged" under any other category means not met. A shape this plan rules "not built" (§3.2) is reported withheld and is excused from the criterion with its counts beside it (teco ruling 2026-11-24, on the stakeholder-approved scoped AC-5 wording; the harness implements it, `docs/reviews/connected-code-graph-p1-closeout-harness-pin.md`): the withheld shapes are those the `data-scientist`'s Q8 ruling lists (J, K, M, C, I-in-`bash -c`, fenced B: 10 of 49 dev scripts items), judged by a build-invariant predicate that is a pure function of the gold locator, the snapshot file text and the language tag, written by someone other than the extractor builder, in a module the engine does not import, never spent knowingly; the withheld share of held-out scripts items is capped at 25%.

**The withheld-shape statement, verbatim for the CO-6b record:** "The close-out engine does not build these scripts shapes: a Markdown mention by bare basename; a Markdown front-matter hook command; a script named inside a `bash -c` string or read as a file; a `-m` package launch; a script run from Python by subprocess; a Python MCP call embedded in a shell string. On the dev gold they are 10 of 49 scripts items (B 2, C 2, I 2, J 2, K 1, M 1); dev item 47 (the `awk` file read) is a confirmed dev `key-error`, not a shape. A held-out item of such a shape is neither asked nor scored: the build-invariant predicate withholds it, and the verdict, the floors and the bounds are over the scored set; the 25% cap is checked over all counting scripts items before exclusion (denominator 79, refused at 20); the withheld counts by shape letter are reported beside the verdict. Their held-out analogue counts are unknown and not estimated, because counting them requires reading held-out items. Wiring is withheld as a stratum (11 dev items, 0 expressible; 8 held-out items blind)."

**Candidate key-errors, for the stakeholder to confirm or reject (not decided here).** Seven dev items whose gold line holds no mention of the anchor within the line (the mention is 2 to 11 lines away in the same file; CO-1 §5): items 2, 15, 16, 27, 39, 41, 42 of the CO-1 table. In each the impacted element does contain a call site naming the anchor (at lines 101, 114, 81, 89, 87, 54 and 274 respectively), and the hit rule is the element identity, so my reading is line drift and **expected hits, not key-errors**; if CO-2's measurement shows any of them missing for that reason, they are the candidates. Item 47 (`test-stamp-wiring.sh` impacts `pipeline.sh`) is a file read, not a launch: a candidate whether the gold's claim is a cross-boundary impact at all. The dev set drove the mechanism design: that caveat is recorded in the preregistration (a dev pass is a fit statistic, not AC-5 evidence). The pre-gate probe tied to this criterion blocks when a gated stratum has **fewer dev hits than dev items** (not only zero).

The fixture builds already contain shell scripts and prompt mentions, so script-to-script `CALLS` and the new pack can move edge counts, `packSetHash` and goldens: CO-2 and CO-3 are done only when the fixture and conformance suites (R1, R7 of the closure report: `test_fixture_gate_p1.py`, `test_fixture_gate_p1_ac.py`, `test_fixtures.py`) are unchanged, or each moved row is owned and re-derived; a silent re-pin is a finding.
