## 3. Design and rationale

1. **Scripts: resolve, don't invent.** Treat "script A runs script B by path" as a call whose target is resolved lexically: a literal path (`./x.sh`, `scripts/x.sh`, `bash x.sh`, `source x`, `. x`, `exec x`, `python -m pkg.mod` to its module file) that names a file of the system becomes a `CALLS` edge to that file's `<script>` (or module) symbol, `confirmed` only when the literal is complete and the file exists, `possible` with the existing dynamic-reason vocabulary otherwise. Prompt documents that name a script path become call sites of the document symbol with the existing `prompt-mention` reason, resolved by the same resolver. This reuses the Link-free `CALLS` machinery and adds no answer-spec row if the walk already follows it. **Rejected:** a new `Link` kind for script hops (a new contract kind, bundle and answer-spec change for a lexical fact) and a kind-wide name match on the script basename (the false-positive rate is what the gate's wrong-`possible` bound measures).
2. **DEF-1: one URL source, two carriers.** A `curl`/`wget` URL literal in a shell script, and the same command in a fenced or inline command of a Markdown prompt, becomes an http consumer through a pack beside `shell-mcp-call` (`cpg/packs/shell-http-client/`, new), with `possible` and the existing URL reasons when the URL has an unknown part. The Markdown carrier needs the Markdown extractor (`cpg/extractors/markdown`) to emit a command call site for a command line in a code span or fence; this is the largest risk of DEF-1 (prompt text is not shell) and is bounded to lines whose first word is `curl`, `wget` or an existing consumer command.
3. **Wiring: decided by the probe, with a fallback.** Only the shapes that `config` items can already express stay in scope without an answer-spec change: a config entry that is the `BOUND_BY` target of a `Link` (a client URL entry, a launch entry whose chain the binder already stores). Shapes that need a new hop (a unit's launching entry as an impact row, a tool named in an allow-list as a consumer) require an answer-spec amendment (`-answer-spec3.md`, V5/V19, schema and algorithm bump, golden re-pin). That is a different size of work, so it is a stakeholder fork (Q3), not a default.
4. **Gate path before everything else.** The held-out list is spent once. Entry criterion for spending it (decided here, recorded in the pre-registration): on the **dev** gold, every dev item of the four strata is listed or carries a recorded triage, in a no-workaround rehearsal run on the frozen commit. A dev pass is not AC-5 evidence (closure report §5 item 12) but a dev miss predicts a held-out miss.
5. **No fixture-row changes.** The P1 census is 81 and was just reconciled at 12 sites; new behaviour is tested on synthetic trees under `cpg/tests/`, not by new rows in `cpg/fixtures/` manifests. Any new fixture row is a separate, owned census change.

## 7. Test strategy

- **Unit and mutation (CO-2..CO-4):** one red test per mechanism on a synthetic tree under `cpg/tests/` (literal path, relative path from another directory, `source`, `bash`, a variable path stays `possible`, a missing file produces no edge, a basename collision produces no `confirmed`, a `curl` with a template URL, a Markdown line that only mentions `curl` in prose); mutants on the confirm/possible split and on the resolver's path normalisation; the existing suites stay green (R1 to R8 of the closure report).
- **Dev measurement per unit** is the proof of §4's done-conditions (scripts 0/49, wiring 0/7 asked, http 17/18, mcp 20/20); results under `cpg/eval/results/`, dev gold only, no tuning on held-out. A fix that works by naming a dev item is a defect, not a result (`docs/test-plans/connected-code-graph-p1.md` L3 stance).
- **Contract:** answer-schema validation V1 to V16 on every new answer shape; a version bump re-pins `ALGORITHM_VERSIONS` and the goldens in the same commit.
- **Gate (CO-9):** the harness's own offline tier (R8) plus the pre-gate probe from CO-5; the no-workaround rehearsal must be run on the freeze commit by a dispatch that has not read the held-out lists.

## 9. Risks

- **The held-out gate is likely to fail on the first spend.** Zero misses are allowed over 159 items, built on 49 dev scripts items and 11 wiring items that were used for development. A fail costs the list and a new blind list (new key-writers, capture-recapture, re-record of the manifest). Mitigation: the §3.4 entry criterion and the no-workaround rehearsal; the cost is stated here so Q4 is answered knowingly.
- **Wiring may force a schema and algorithm change** (§3.3); the largest schedule risk, hence Q3.
- **Dev overfitting:** the mechanisms are lexical and general by design; the guard is the synthetic-tree tests, not the dev count.
- **Prompt-as-shell (DEF-1 Markdown carrier)** may raise wrong-`possible` counts; the AC-5 bound (at most 4 wrong `possible` per real impact) is checked in the rehearsal's noise figures.
- **`wiring` at the floor of 8:** a triage removal drops it below floor; then it is "below floor, not gated" unless a reserve cluster exists.
- **Host contention:** 30-minute builds on a small host serialize the gate path, CO-12 and the AC-8 images.
