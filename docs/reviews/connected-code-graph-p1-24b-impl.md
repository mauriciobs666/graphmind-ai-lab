## Findings

### m1 (minor) Notice is an unmarked run-on paragraph in the text rendering; the zero-item case reads slightly oddly
Evidence (rendered, verified): text output is `0 items listed (0 confirmed, 0 possible).` immediately followed, no blank line and no label, by `Flow-dependent effects in javascript, python may be missing from this list. In javascript, python the walk did not follow ... edges; ...`. Wording is the spec's and I found no way to read it as "nothing missing" or "none listed": it says "may be missing", "not evidence that no such effect exists", and contains no `none`/`nothing`. Two readability points remain: (a) the second sentence "In javascript, python the walk" is ungrammatical for a multi-language list (a natural reading is "In javascript and python"); (b) in text mode the notice shares a block with the counts line, so a skimming reader may take "0 items listed" as the finding. Markdown sets it off as a blockquote; text does not.
Suggestion: render a blank line before the notice in text mode (placement stays "directly after counts_line" in line order), and join the second `{langs}` with a human list ("a, b and c") — but note the §5.1 test statements must then be re-pinned; low stakes, owner may decline since the spec wording does not require it.

### m2 (minor) `summary_input` and langs: P1-26's "dropped on any added entity" rule is not exercised
Evidence: `render/__init__.py:49` emits `notice flow-not-enumerated: python`. Verified: line carries the enum code and validated language names only; no wording, no figure (tests assert `"missing"`/`"Flow-dependent"` absent; mutant M18 killed). It respects P1-26 behaviour (5) as far as this unit goes. But P1-26 (not built) checks the model's summary for added entities; a language name in the input (`python`, `javascript`) is an input token the summary may legitimately repeat. Not a defect here; P1-26's entity check must treat `langs` as allowed input (or the plan should say so).
Suggestion: add one sentence to P1-26 behaviour (5) naming `langs` as an allowed echo; owner `architect`.

### m3 (minor) The golden is a self-pin; independent evidence is the substring tests, which are literal
Evidence: `answer-notice.{txt,md}` are generated by the renderer, and `test_the_notice_golden_renders_to_the_committed_text_and_markdown` only compares current output to it, so alone it pins, not proves. Independent evidence that does exist: `test_the_notice_names_every_language_...` asserts literal phrases (not read from `FLOW_NOTICE_TEXT`); `test_the_notice_text_carries_no_banned_word...` uses a separately written ban regex test list incl. digit-bearing `c11`; the ban-matching test plants positive/negative words; the placement test derives expected positions from `counts_line`/`reach_note`. Weakness: the ban regex `FLOW_NOTICE_BANNED` and the test's expectation both come from that constant (`test_the_ban_matching...` uses a literal list, which is independent, good). The spec's ban list (`safe, complete, exhaustive, full, guarantee, guaranteed, no impact, all impacts`) is entirely contained in the regex; mutants A08/A09 killed. I consider this adequate; flagging so the golden is not mistaken for the wording check.
Suggestion: none beyond a comment in the golden test saying it is a regression pin and the wording is pinned by the literal-phrase test.

`render/__init__.py` module docstring line (now >120 chars) breaks the file's wrapped style; `FLOW_NOTICE_BANNED` is production code used only by tests (acceptable: it documents the contract next to the template).
