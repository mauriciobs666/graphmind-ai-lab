## Findings

### F1 (major, verified by probe; needs a ruling) — the fold takes items that are downstream of a candidate, not candidates
`group.candidate_site` (`group.py:170-181`) classifies an item by its **first possible hop** only, so every item past a doubtful candidate joins that site's `other-possible-callees` group. Probe (Appendix B): impact `A`; site `cB` in `B` resolves to `T` and name-matches `A`; `C` calls `B`. `C` (distance 2, reached `cB` → `Ret` summary → `cC` CALLS confirmed) lands in group `cB` with `B`. Depends-on `F`: `F` calls `A` (resolved) and name-matches `B`; `B`'s own resolved callee `T` (distance 2) lands in group `cF` with `B`. Same under flag-false and V-union. `-answer-spec.md` §5.4 defines the kind as "the unresolved other candidates of one resolved call site"; `C` and `T` are not candidates of `cB`/`cF`, so a renderer headlining "other possible callees of site X" lists a non-callee, and the group count overstates the site's candidates. No test pins either reading (the delegate's `test_only_an_item_whose_first_possible_hop…` plants a *later* candidate hop, not a downstream item), so I ran the narrow rule: all 94 tests still pass in my scratch copy.
Fix (architect's call; I recommend narrow): fold an item only when the candidate hop is its **own arrival**: depends-on, the hop is the chain's last hop; impact, the hop is followed only by the `HAS_CALL <-` owner hop. Downstream items stay in `items` as `possible`/`resolution-unverified` (their reason is unchanged: V7 first-possible-hop). The broad reading (hide everything behind an unverified edge) needs spec §5.4's definition widened instead. Either way pin it: a planted `C`/`T` downstream item asserted listed (or grouped), with the mutant that widens/narrows `candidate_site` killed.

3. **Fold classification — accepted for the rule as written, see F1 for its reach.** Site-unit language (not the candidate's): mutant using no site language killed; unresolved-site `name-match` never folds (`_candidate_reason` from `count(x)`); a `CallSite` at both ends of the hop is ambiguous and listed. **Singleton group: accepted.** Schema `Group.members` `minItems: 1`, `count` `minimum: 1` and the plan's "a group per site" allow it, and the fold is display-only.

5. **Reverse question — accepted.** `QUESTIONS["depends-on"] = bfs.DEPENDS_ON` through the same `group_items`; mutant routing it to the impact column killed; the never-built-unit case groups by its own root.
6. **Hostile input — accepted.** NUL, lone surrogate, RTL, empty and decomposed keys: total order, no merge, deterministic under shuffled items/facts/units (25 seeds); errors are static strings naming no data (`_bad`, `_count`).
