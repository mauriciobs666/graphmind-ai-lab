# Common LLM gateway plan — security review (hosted-key and trust-boundary design)

> **Status:** active · **Owner:** `security-expert` · **Tracks:** GAL-F0046 · **Reviews:** `docs/plans/llm-gateway.md`

**Lens:** code/design security (static; no exploitation attempted). **Artifact:** `docs/plans/llm-gateway.md` §3.4, §3.5, §3.8, D-1/D-5/D-6/D-7, against `docs/requirements/llm-gateway.md` (FR-2, 3, 8, 10, 12; AC-2, 5, 6, 21), `docs/plans/connected-code-graph-egress-spec3.md` (§2.0, the "does not cover" list) and `-spec4.md`, and `cpg/ccg/broker/{server,policy,runs}.py`.
**Threat model:** an LLM-driven agent under the human's uid with shell and file access (not root; sudo needs a password here).
**CPG:** not applicable — a plan review of a greenfield component; the ccg broker files were read directly.

## Verdict: needs changes

The plan's core move (a separate key holder, library never holds a key) is right, but as designed the **hosted guarantees (FR-8 hard control, FR-10 bound, FR-3 for non-ccg) hold only against an agent that uses the gateway library cooperatively**. Against the stated threat (an agent that goes around the library) two of them fail, and one recipe (container) fails on this host. Two blockers, five majors.

Environment facts I checked (read-only): the agent account is in the `docker` group (`/var/run/docker.sock` is `root:docker 0660`); no `/proc/sys/kernel/yama` (WSL2 5.15.167.4 has no Yama, so any same-uid process may ptrace and read `/proc/<pid>/mem` of any other — I confirmed `/proc/$PPID/maps` is readable); `sudo -n` requires a password; `/etc/llmgateway` does not exist yet.

## Findings

### B1 (blocker, confirmed by trace) — the run bound, and every hosted limit, lives in a layer the agent can skip
- Evidence: plan §3.8 "The bound is accounting at the library/service, not at the holder"; §3.4 holder checks only `endpoint`, `path`, `model ∈ pinned_models`, body size. `cpg/ccg/broker/server.py:_serve_one` accepts any same-uid peer; `Broker.open_run` mints a token for any `systemId`/`codebases` and `request` forwards an R7 hosted `model-call` with an agent-chosen body. The `run_id` that selects the bound is caller-supplied (§3.8), and omitting it means unbounded.
- Attack (theoretical to execute, certain by code path): the agent skips `Gateway`, opens the broker socket (or the service socket), sends hosted `model-call` requests with its own body (`max_tokens` at the provider maximum), in a loop. No `run_bounds` entry applies (no `run_id`, or a fresh one per call), nothing reaches the holder's check that would stop it, and the holder has no spend ceiling or `max_tokens` clamp. Same for FR-10's "agent supplies a different `run_id` each call". AC-6's test (calls through `Gateway`/service under `eval-1`) cannot see this.
- Also: the ledger is `state_dir/records.sqlite3`, same-uid writable; `DELETE`/`UPDATE` on `attempts` resets any bound, and `INSERT` of fake rows can starve another run (confirmed possible by file mode, not executed).
- Also (race, confirmed by reading §3.8): the check sums *before* the call and records *after*; N concurrent calls each pass the check, so overshoot is N times the per-call maximum, not "the last call".
- Fix: (1) enforce a spend ceiling **in the holder**, which is the only component outside agent reach: clamp `max_tokens` to an owner-configured maximum, and keep a holder-owned ledger (`run_id` carried in the HMAC-covered request, plus a mandatory global rolling ceiling that applies even with no or an unmatched `run_id`) fed from the provider's `usage`. The library bound becomes an early, friendly check. (2) Reserve `max_tokens` against the ledger before sending, release the difference after. (3) Keep the ledger in a store the agent cannot write (holder account), or state that the library ledger is advisory. (4) Add an AC-6 test that drives the broker socket and the service socket directly with no `run_id`.
- Requirements tension: a global ceiling is a cross-run budget, listed as out of scope, and FR-10 says interactive is "deliberately unbounded". A holder-side safety ceiling is a different thing from a budget feature; `tico`/the stakeholder should confirm that reading.

### B2 (blocker for the container recipe, confirmed environment fact) — a container holder gives no isolation from this agent
- Evidence: plan §3.4 offers "a `Dockerfile` modelled on `cypher-mcp/`" as one deployment; this account is in the `docker` group. Docker-group membership is root-equivalent: `docker exec`/`docker cp`/`docker inspect` on the holder, or `docker run -v /:/h`, reads the key file, the holder's memory-mapped state and its environment. AC-5's tier-2 probe ("as the agents run, same account, same tools") would find it.
- Fix: make a **separate OS account** (the holder's socket and state in directories owned by it, mode 0700/0600, ancestors root-owned) the only supported recipe on a host where the agent account reaches the Docker socket. A container is acceptable only with rootless Docker/Podman owned by the holder account, or on a host where agents lack docker access; the recipe must state this and the tier-2 test must run on the actual deployment shape. Same applies to the holder's key directory: root- or holder-owned, never under the human's home.

### M1 (major) — broker/service to holder authentication does not deliver "refused unless broker or service"
- Evidence and reasoning:
  1. **Reachability cannot discriminate.** The broker (human uid) must connect to the holder socket, so the socket is reachable to every process of that uid, including the agent. Only the HMAC credential distinguishes callers.
  2. **The credential is not hidden.** "Memory only, via stdin" fails operationally: broker and service restart often (SIGTERM handler, lock, 24 h run TTL), so the credential has to be re-supplied from somewhere persistent that the same uid can read, or the human types it each time. Provisioning (`add-caller` "prints the credential once") puts it in terminal scrollback, shell history if piped, and the transcript if an agent's Bash tool runs it. Where it is held in memory, there is no Yama here, so the plan's mitigation ("start from the human's terminal, outside agent process trees") does nothing: the agent need not be an ancestor.
  3. **The scheme as written cannot be verified:** the holder stores "a hash only", but an HMAC needs the secret key on the verifying side; with only `H(cred)` the holder cannot check a MAC made with `cred`. Either the holder holds the key (then it is a secret at rest in the holder) or the MAC key is `H(cred)` and the caller holds that (then the "hash" is the credential).
  4. **Even a perfectly held credential is bypassed by the broker being an oracle** (B1): the agent never needs the credential if it can ask the broker.
  5. Replay: a nonce set grows unbounded unless pruned by the timestamp window, and is lost on holder restart (timestamp window then the only control); there is no response authentication, so if the holder's socket path is in an agent-writable directory the agent can unlink it and bind a fake holder (forged model replies feeding ccg's interpreter; captured request bodies).
- Fix (recommended, also answers D-1): when hosted use is enabled, run the **broker and the service under their own account(s)**, with the holder socket in a holder-owned directory and the holder checking `SO_PEERCRED` uid against an allow-list of those accounts. The kernel authenticates the caller, no credential exists to store, leak or replay, and the holder's allow-list is the "only the broker and the service" rule of FR-8. The agent then reaches the broker as a *client* (as ccg legitimately does), and the broker's policy, manifest and audit are outside its write reach. This requires the broker's `peer_uid != os.getuid()` check (`server.py:289`) to become an allow-list of client uids and the audit/state dirs to be broker-account owned (a ccg design change, spec5). If that is rejected, fall back to HMAC but with the holder storing the MAC key, a persisted credential file readable only by the broker's account, bounded nonce cache, and an honest statement that it protects against accident and prompt-injected tool use, not a hostile same-uid process.

### M2 (major) — FR-3/AC-21 for ccg relies on a manifest the agent can write, and the plan widens the window
- Evidence: `cpg/ccg/system.yaml` is a git-tracked file in the working tree, owned by the human uid, so "writable only by its owner" (FR-3, AC-21) is true of the agent too; AC-21's check (`a file-mode check on the installed manifest copy`) is vacuous against the same uid. Today `server.py:load_systems` loads it once at start; the plan (§7, risk 5, S11) adds a **per-`open_run` re-read**, so an edit by an agent (or an accidental commit) flipping a codebase from `local-only` to `hosted`, or adding a hosted `egress` entry, takes effect on the next run with no broker restart and no human action. `ManifestMarkers` in the library re-reads the same file with no cache, so both the library and the broker follow the edit.
- Fix: the broker's authoritative manifest should be an **installed copy owned by root or the broker account** (same rule as `gateway.toml`), or a content digest pinned at start and re-read only if the digest matches an owner-approved value; changing local-only to hosted is then a human act. If the re-read stays, make it tighten-only (a change from `local-only` to hosted needs a restart or an approval step). Make AC-21's test an ownership check that the agent account cannot satisfy, not a mode bit. Related to D-4: its "loosens at the next broker run" is precisely the agent-writable loosening path.

### M3 (major) — restricted scopes for non-ccg callers are a cooperative control (D-7)
- Evidence: plan §3.5 "Service callers that are not ccg declare scopes", `scope_markers` resolve names; an unlisted name is `unmarked` = unrestricted (FR-3 text). The agent is the caller: it declares no scopes, or a made-up one (`workspace:Acme`, trailing space, other case), and gets hosted use. The sticky rule and `MarkerUnreadable` refusal protect only a caller that names its scopes truthfully. The ccg path is stronger (the broker derives scope from its own run/manifest), but the broker is authoritative only for the `model-call` it sees.
- Fix: (1) bind each **call site to its scopes in owner configuration**, so a call site that touches restricted data is restricted regardless of what the request says; the request may only add scopes (tighten), never remove or replace. (2) For any hosted step, require the scope to be **registered** in owner config (`unrestricted` explicit); an unknown scope name refuses hosted. This is stricter than FR-3's "no marking at all is unrestricted" and should be confirmed with the stakeholder as applying to unregistered names, not to a registered scope lacking a flag. (3) Canonicalize scope ids (exact match, ASCII, no whitespace/case folding) and test confusable forms. (4) State plainly in the design that the library-only restricted-scope check is a safeguard against mistakes, not against a hostile caller.

### M4 (major) — "owner-protected" check (D-5) has path, TOCTOU and identity gaps
- Evidence: plan §3.5 "the loader checks `stat`", "owned by root or the gateway account", `LLMGATEWAY_CONFIG` override, fallback "hosted disabled".
  1. `stat` on a path follows symlinks and races the later read; the broker's own spec uses strict ancestor checks (spec4 §4, `audit.require_dir(check_ancestors=True)`) and the plan does not. A root-owned `gateway.toml` inside any directory the agent can write (or rename-replace in) is not protected. Require `open(O_NOFOLLOW)`, `fstat` on the descriptor, parse from that descriptor, owner uid 0 (or one uid fixed in the holder's own build/recipe, never read from the file being checked), mode `& 0o022 == 0`, and every ancestor root-owned and not group/other-writable.
  2. "The gateway account" is undefined; if an implementer accepts "owned by the current uid" (natural in a dev setup), the agent satisfies the check by owning the file. Name the account check explicitly and test that a file owned by the test's own uid is refused.
  3. Hosted disabled is the right fail direction, but the plan does not say that **`deployment.local_endpoints`, `scope_markers` and `scope_overrides` from an unprotected file** are also ignored. An agent-writable file adding `local_endpoints = ["https://exfil.example"]` would make a remote URL "local" and `DirectTransport` would send data there with no key (breaks FR-6/AC-4). With an unprotected file the local allow-list must collapse to loopback IP literals only.
  4. The service, broker and holder must ignore `LLMGATEWAY_CONFIG` (the plan says so for the holder only) and check protection **per call or on inode change**, not once at start.
  5. `is_local(url)` must compare a canonical origin (reuse `ccg.manifest.canonical_endpoint` rules): userinfo (`http://127.0.0.1:1234@evil`), `localhost.evil.com`, `127.0.0.1.nip.io`, IPv6 forms, a DNS name that resolves elsewhere. Accept IP literals only and connect to that literal, no redirects.

### M5 (major) — the holder's own validation is thinner than the broker's, and moves SSRF/leak decisions into it
- Evidence: §3.4 holder checks endpoint ∈ providers, allowed paths, pinned model, body size; the broker's R7 path today validates the resolved address (`addr_mod.validate`, spec3 §3.4 forbidden ranges) and passes `validated.addr` to the exchanger. The holder re-resolves on its own.
- Fix: the holder must (a) refuse any hosted provider `base_url` that is not `https` and refuse to attach a key to a plaintext request (an `openai_compat` hosted entry written `http://…` would send the key in clear); (b) apply the same forbidden-range/DNS pinning as spec3 §3.4 before attaching a key, or connect to a validated IP with SNI/hostname verification; (c) refuse redirects, verify hostname against the provider host, and cap response size (planned); (d) clamp `max_tokens` (B1); (e) treat `pinned_models` as exact membership only — never accept a pattern for "not an alias", since the plan's own §2 notes undated ids are aliases pre-4.6.

### Minor
- **m1.** The scrubber matches only the exact key string; also scrub URL/base64 forms and drop provider error text entirely rather than scrubbing (the plan already discards bodies in `classify`; keep that the only path). Disable core dumps and Python tracebacks to logs in the holder.
- **m2.** `add-caller` printing the credential once is a leak path (see M1.2); if HMAC stays, write it to a 0600 file in the owner's account, not stdout.
- **m3.** `records.sqlite3` and WAL/SHM files: create with 0600 in a 0700 directory (they hold `component, scope, run_id` and, for opted-in scopes, text); a record DB readable by other accounts is a minor disclosure.
- **m4.** Text recording guard: "no scope on the call is restricted" uses the same caller-declared scopes as M3; derive it from owner config.
- **m5.** Timeouts/aborted streams after the provider has billed produce no `usage` and are not counted toward the bound (B1's holder ledger should count request-size estimate as a floor in that case).
- **m6.** HMAC `caller|nonce|timestamp|body-digest` does not bind the target holder, path or endpoint; include method, path and endpoint in the MAC input (if HMAC is kept).

## What is solid
- Library has no key-reading code and `DirectTransport` refuses non-local URLs before opening a socket; the holder never takes keys from env/argv/tracked files and reads the key per call (rotation, revocation by deleting the file, missing key fails closed).
- `Request` has no model/provider field; hosted overrides honoured only from owner config; `policy_refused` never falls back; `local_chain` vs refuse for restricted scopes with no silent filtering.
- Broker stays the enforcement and audit point; a down/refusing holder gives `upstream-error`, never a direct fallback; the plan states the same-uid residual and the ccg boundary honestly, and the AC-5 tier-1/tier-2 split rightly says tier 1 cannot prove "agent cannot read".
- Record allow-list with no header/error-body columns; a positive-control search in AC-5.

## Stakeholder decisions: recommendations
- **D-1 (same-uid HMAC): do not accept as written; require separate accounts for broker and service when hosted is enabled, with peer-credential authentication (M1).** The same-uid residual is not "ptrace the broker": the broker is itself an oracle (B1), and without Yama any same-uid process can read it anyway. If the stakeholder wants to keep the broker in the human's uid, accept it only as a *cooperative-agent* control, add holder-side ceilings (B1), and word FR-8/AC-5 and the design doc accordingly. Hosted can ship in stages: local-only first, hosted behind the account split.
- **D-5 (owner config = root/gateway-owned, sudo setup): accept, with the M4 amendments** (descriptor-based check, root-owned ancestors, named uid never read from the checked file, ignoring unprotected `local_endpoints`/markers, env override ignored by service/broker/holder, per-call or inode-change recheck). The "developer without sudo gets local-only" fallback is the correct fail direction.
- **D-6 (unmatched `run_id` is unbounded): reverse it for hosted.** A hosted step with no `run_id`, or one matching no `run_bounds`, should be refused (or bounded by a mandatory `default_hosted_bound`), enforced at the holder (B1). Local steps stay unbounded. This needs the stakeholder to reconcile FR-10 "interactive deliberately unbounded" with an agent-reachable hosted path: interactive hosted use would take an explicit owner-set bound or ceiling, not no limit.
- **D-7 (service callers declare scopes; owner `scope_markers` the only loosening): not sufficient as the sole control.** Add call-site-to-scope binding in owner config, request-can-only-tighten, registered scopes required for hosted, canonical ids (M3). Sufficient only if the stakeholder accepts the non-ccg restricted-scope guarantee as advisory until the follow-on.

## Open questions
1. Are the broker and the service allowed to run under their own account(s) when hosted is on (a ccg design change, spec5)? Everything in M1, M2, B1(3) is cheaper if yes.
2. Does the stakeholder accept a holder-side global ceiling given "cross-run budget" is out of scope (B1)?
3. Does FR-3's "no marking at all is unrestricted" cover unregistered scope names for hosted calls (M3)?
4. Which uid is "the gateway account" in a single-developer WSL setup, and does the host expose Docker to agents beyond this account (B2)?

## Pass 2 (2026-11-23, plan revised in place; stakeholder kept HMAC, accepted the same-uid memory-read residual)

**Verdict: needs changes** (one new major that falsifies a stated guarantee; all else closed or honestly residual). Re-read: `docs/plans/llm-gateway.md` §1 (guarantees paragraph), §3.4, §3.5, §3.8/FR-10 text, §5.2, risks.

### Dispositions of Pass 1
- **B1** — partly closed. Holder-owned ledger, MAC-covered `run_id`, transactional reserve/settle (`max_tokens + len(body)`), `unmatched = "refuse"`, library bound declared cooperative: all present (§3.4). Not closed: see N1 (per-id bounds are mintable).
- **B2** — closed. §3.4 makes a dedicated account the only recipe, container only rootless and holder-owned, names the docker-group fact, and tier 2 probes `docker` access.
- **M1** — declined by the stakeholder; accepted as residual. Verifiability fixed (holder stores the secret), credential never printed (`--out` 0600 file), MAC now covers method/endpoint/path/run_id, response MAC plus socket-dir owner check against a fake holder. Residual stated in §1; the statement overreaches, see N1 and N3.
- **M2** — closed in design: installed root-owned manifest copy, no per-run re-read, tracked-file edit has no effect (tested). Gap: N4 (flag is optional).
- **M3** — closed: call-site-bound scopes, add-only requests, unregistered name refused for hosted, canonical ids, confusable-form tests (§3.5, §5.2 case 4).
- **M4** — closed: `O_NOFOLLOW`, fstat on the descriptor, `trusted_uids` injected `{0}`, root-owned ancestors, per-call recheck, unprotected file's `local_endpoints`/scopes/bounds ignored and allow-list collapses to loopback literals, canonical-origin `is_local`, env override library-only.
- **M5** — closed for the Anthropic shape, open for others (N2). Refuse-not-clamp is the right call: it satisfies FR-18 and the ceiling. https-only, address validation then connect-to-address with SNI, no redirects, exact `pinned_models` all present.
- **m1–m6** — fixed as written (scrub forms, no stdout credential, 0600 DB/dir, text guard from owner config, aborted call keeps reservation, MAC binds path/endpoint). Not re-argued.

### New findings
- **N1 (major, confirmed by reading §3.4) — the holder ceiling does not bound a credential thief's spend.** `[[run_bounds]]` matches a run-id *glob* (`eval-*`, `interactive-*`) and each distinct matching id gets its own bound; only `unmatched = "cap"` shares one bucket. `run_id` is chosen by the caller (via the broker it is the agent-settable `gatewayRunId`/`CCG_GATEWAY_RUN_ID`). An agent holding the broker/service credential, or simply using the broker as an oracle, sends `eval-1`, `eval-2`, … each with a full bound: unbounded spend. §1's "the holder's ceiling still bounds spend" is therefore false. Fix: add an owner-set holder-wide rolling ceiling (all run ids, per calendar day, plus an optional per-provider one) in the same reservation transaction; document it as a safety ceiling, not a cross-run budget feature (requirements tension flagged in Pass 1 still needs the stakeholder's yes). Add an AC-6 case: 100 fresh `eval-N` ids against a glob stop at the global ceiling.
- **N2 (major) — `max_tokens` presence/ceiling is provider-shaped.** §3.4 tests `max_tokens` generically, but §3.2 maps it to `options.num_predict` for Ollama (hosted Ollama is in scope), OpenAI-compat may use `max_completion_tokens`, and Ollama has no required cap. The holder must read the *provider's* wire field through a per-kind table (it cannot import the gateway providers, so duplicate it in `holderconf`) and refuse when absent/over-ceiling; a body with both the neutral and the wire field, or a nested/duplicate key, must be rejected, and the reservation must use the same value. Test per provider kind, including a hosted Ollama body with no `num_predict`.
- **N3 (minor, wording) — state the credential-theft blast radius completely.** With the credential, the same-uid agent can: send any pinned-model request with caller=`broker` or `service`, skipping R5/R6 and every scope check, so any data it can read reaches the provider (marginal harm is low since it could exfiltrate by other routes without the key, but the "local-only is sticky" guarantee does not hold against it); spend up to N1; leave no broker audit record (holder has its own ledger only). It cannot read the key, use an unpinned model or an `http://`/internal endpoint, or exceed the per-call `max_tokens`. §1 and D-1 should say this in one sentence; add a holder-side log of caller/run_id/endpoint/bytes so a bypassed broker audit is detectable.
- **N4 (minor) — `--require-owner-protected` is a flag, not a default.** A broker started without it, with `--system cpg/ccg/system.yaml` (tracked, agent-writable), silently restores M2. Make it mandatory whenever `--key-holder-socket` is given (broker refuses to start otherwise) and when no holder is configured keep it available; test the omitted-flag start.
- **N5 (minor, interaction) — directory modes contradict the connect path.** §3.4 owns the socket directory 0700 by `llmholder`, but the broker and service run as the human's uid and must traverse it and connect. The directory needs 0711 (or a shared group) and the socket 0666/0660 for that uid, with authentication left to the MAC; the recipe and the §5.2 case 7 owner check should say so, or the install will silently push implementers to loosen modes ad hoc.
- **N6 (minor, interaction) — the shared `cap` bucket plus "aborted call keeps its reservation" is an availability lever.** A same-uid agent can drain the bucket with aborted calls and refuse every unattended run. Acceptable if documented; otherwise expire an unsettled reservation after a timeout.
- **N7 (nit, residual)** — the broker's audit directory remains human-uid writable (spec3 §2.6 same-uid out of scope), so AC-21's "refusal is in the audit log" is evidence, not tamper-proof. One clause in §1 suffices.

Releasing a reservation only for a call that failed before any byte went upstream is the right line: a sent, usage-less call may have been billed, so keeping it is the safe floor. Drain of the shared `cap` bucket is a DoS lever only for a holder of the credential, who can equally spend the same tokens legitimately, so there is nothing further to defend. One wording suggestion: the same lever applies to the window ceiling, not only the `cap` bucket; say so in the "documented lever" clause.
- **N7** — closed. §1 states the broker audit dir is human-uid writable and AC-21 evidence is not tamper-proof.
- **(b) `window_seconds` configured** — accepted (sliding window, timestamps rolled off by the injected clock). Nit P3-2 below.

### New findings
- **P3-1 (major, theoretical but a standard code path) — `install.sh caller` has root create and chown a file in an agent-controlled directory.** `<caller home>/.config/llmgateway/callers/<name>.cred` is created by root with `O_EXCL|O_NOFOLLOW` then chowned. `O_NOFOLLOW` guards only the final component; the agent owns `~/.config/llmgateway` and `callers/` and can pre-plant either as a symlink (to a root-owned directory), so root creates a new agent-owned file there; and if the chown is path-based, a swap between create and chown makes root chown an arbitrary file to the agent uid. Fix: perform the write as the caller — `setresuid`/`su -c`/`runuser` to `<caller-uid>` before creating the credential file (root only reads the registry secret and passes it on stdin), or walk the path with `openat`/`O_NOFOLLOW|O_DIRECTORY` per component, verify each directory is owned by the caller uid, and `fchown` the descriptor, never the path. Add a root-conditional test with a planted symlink at each component, and make `check-deployment` verify the credential file is a regular file owned by the caller. Keep `--out` restricted to a path under the caller's home.
- **P3-2 (nit)** — validate `window_seconds`, `window_max_tokens`, bounds as positive integers (and a sane upper limit on `window_seconds`) at holder start; a zero or enormous window would silently disable the ceiling.
- **P3-3 (minor)** — the 0666 socket makes the holder reachable by every local account. Confirm: frame size cap and read timeout before authentication, nonce cache insertion only after the MAC verifies (otherwise unauthenticated flooding fills it or evicts a live nonce), and a per-connection cap. State in §3.4. Also, a retry must sign a fresh nonce (a reused signed request is `replayed_nonce`, class `config`, permanent).
