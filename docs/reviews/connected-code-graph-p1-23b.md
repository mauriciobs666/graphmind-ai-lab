## Findings

### F1 (major, verified by probe; needs a ruling) — V-both lists callees one level deep, not "to bound 2"
`-p1-ml.md` §3.5: V-both is "callers and callees to bound 2". `flow.candidate_table` adds `has_out:CallSite:fn:both` (inc 0) + `calls_out:both`/`name_out:both` (inc 1, arrival `end`), and `end` has no outgoing row. Probe (`probe.py`, Appendix B): flag-false `F` holds `pF`, `F`→`Q1`→`Q2`, bound 2: V-both lists `Q1` (d 1) and **not `Q2`** (d 2, inside the bound). Callers are walked to the bound; callees are not, so V-both and V-union understate `s` relative to the pre-registered definition and the burden comparison between walks is asymmetric. P1-39's rule ("lowest burden among the maximum `s`") would pick the shipped walk on that bias.
Fix: needs the method owner (`data-scientist`) to rule which reading §3.5 means; if two levels, the callee state needs a continuation (a table change; a new hop `state` would be a schema change like `site`, so prefer a state already in the closed set and say how callers of the callee are kept out). Test: planted `F→Q1→Q2→Q3` at bound 2 asserting exactly the ruled set, plus the distance of each.

### F2 (minor, verified by probe; doc ruling) — V-union is a union of rows; `-p1-ml.md` §3.5 says "computed from the two listed sets"
The two authorities disagree: `-p1-answers.md` P1-23 builds V-union as a row-table variant; §3.5 says set union. The row union is the only form that can ship (the shipped object is a table), and it is a strict superset: probe `b` lists `Q` under V-union that neither V-flow `{D,X}` nor V-both `{X}` lists (V-flow reaches `D`, then V-both's row leaves `D`'s function state). So V-union's `s`/burden is not the set-union figure the pre-registration describes. Accept the delegate's choice; amend: §3.5 states V-union is the table union (and P1-39 may report the set-union as a lower bound), before `ccg-p1-flow-fallback-v1` is frozen.

### F3 (minor, verified) — the shipped flag-false world has no pin on real data
`slice_rows()` sets `flowAvailable=True` on every slice unit. That is **faithful to the oracle** (the spike loader writes the flag `None`, which now reads false, and `impact.py` follows precise rows everywhere; without it the equivalence would diverge) and is not hiding a regression: all P1-22 pins are flag-true worlds, which the spec says P1-23 must not change. But P1 expects every flag false (index §5), so `SHIPPED_OBSERVED` (22/157/5 …) pins a counterfactual. I ran the real flag-false world: `p0` 19 items / 38 states / `unexplored` 6 (18 `possible`/`flow-unavailable:javascript`, 1 confirmed); `buildUrl` 10 / 21 / 9: `apiFetch` d1 confirmed, nine callers d2 `possible`/`flow-unavailable:javascript`. That matches spec2 §5's "Consequences in P1" — the first real-data confirmation of it. Fix: add one `slice` test with the flags set false asserting that named delta (`apiFetch` confirmed; the nine callers by qname, status, reason, distance), so the spec's consequence list is pinned on real data. Test altitude: it fails if `owner:CallSite:fn` or the label source regresses on the real graph.

### F4 (minor, verified) — stale statements in the work's own docs
`cpg/README.md` `bfs.py` row still says "a table of 40 `Row` records" and "Not built: the flow-flag gate and labelled rows" next to the new `flow.py` row that says they are built; `ccg/engine/state.py:3-5` says "the shipped P1-22 table never enters `function`". The delegate flagged the README one. Replace, do not append (root `AGENTS.md`, context-file convention): "49 rows", drop the clause, rewrite the state.py sentence.

### F5 (minor, measured) — paired rows issue the same read twice per level
`owner:X`/`owner:X:fn`, `calls_out`/`calls_out:fn`, `name_out`/`name_out:fn` share a `read` and are asked separately (the gate filters afterwards). Counted on 100 random worlds × 2 columns: 8,121 reads, 1,323 identical `(name, ids)` repeats (16 %). On a live store each is a round trip and a result-set against `RESULTSET_SIZE`. Fix: memoise `(read, ids)` per `_expand` call (results are filtered per row afterwards); the `test_a_row_the_flag_closes_is_not_asked_of_the_reader_at_all` pin stays valid.

### F6 (minor, verified) — two item rules exist only for V-both but sit in the shipped definition
`_ITEM_RULES` gained `("Symbol","CALLS"|"CALLS_NAME","->","end")` for impact; no shipped row arrives at `Symbol`/`end` by `CALLS ->` (`arg_*` rows arrive in `path`). They are in the shipped fingerprint and untestable on the shipped table. If the as-built walk ships, `1.1` carries dead rules and removing them later is a bump. Fix: let a candidate table carry its own item rules (the table is the walk), or accept and say so beside F1's ruling.

### F7 (nit, verified) — a missing anchor now raises instead of returning an empty walk
`bfs.walk(reader, ("Cond","nope"))` (and `("Param","nope")`) raises `GraphDataError` from the gate's unit read; at HEAD it returned no items. Anchors come from the resolver over the same snapshot, so this is only a stale-snapshot race, and failing closed is the right default; say it in the `walk` docstring so P1-39 maps it to a build error, not a "no impact" answer.
