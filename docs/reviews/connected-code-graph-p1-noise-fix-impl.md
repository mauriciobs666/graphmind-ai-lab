## Findings

### F1. major. `MENTION_REASONS` is not in the walk definition, so a changed reason set keeps `algorithm.version` 1.3

Evidence (run): in the archived HEAD, `bfs.fingerprint(bfs.definition())` is `0d5d961e…`, equal to the `ALGORITHM_VERSIONS["1.3"]` pin and `PINNED_1_3`. After `config.MENTION_REASONS = frozenset({"prompt-mention","name-match","shell-dynamic"})` the fingerprint and `bfs.algorithm_version()` are unchanged (`1.3`). After `config.MENTION_REASONS = frozenset()` (the rule is then inert on every graph) `algorithm_version()` is still `1.3` and `definition()` still carries `mentionBound: 1`. `config.py:10-12` says so on purpose ("a change here is a version bump by review, not by the fingerprint"). Mutant m09 (reasons widened) is killed only by a behaviour test, never by a version test.

Why it matters: `recipe.algorithm.version` is what an auditor reads to know which walk produced an answer (spec2 §1.2). Version 1.3 would name two different walks, and the worst case, an empty set, names a walk with no mention rule at all. Inside the freeze the `coreTreeHash` of the R3 record covers it, but a recorded answer outlives the freeze and carries only the version. The plan's own argument for `mentionBound` ("the definition gains `mentionBound`") applies to the reason set with the same force: the bound is meaningless without the class it applies to.

Fix (cheap now, a re-pin plus a 1.4 later): add `"mentionReasons": sorted(config.MENTION_REASONS)` next to `mentionBound` in `bfs.definition()`, emitted only when `mentionBound` is. Compute the new fingerprint, replace the `1.3` literal and `PINNED_1_3`. 1.3 has not been emitted in any recorded answer (the only literal occurrences of the pin are `bfs.py` and the test), so this is a re-pin of an unpublished version, the P1-22/P1-23 precedent in the `ALGORITHM_VERSIONS` comment. Add a test, in the same commit as the field, that monkeypatches `MENTION_REASONS` to a widened set and to the empty set and expects `WalkError` from `bfs.algorithm_version()`. The expected value is "raises", not read from the constant. The red check is the mutant "drop `mentionReasons` from `definition()`", which this test kills; because the test and the field land together, run it once against the pre-change tree (it must fail) before accepting. Update the `config.py` comment, which then states the opposite.

### F2. minor. No answer-level test of a mention cut (build, validate, render)

Evidence: the commit's answer-test edits are literal `1.2` to `1.3` swaps (`test_engine_answer.py`, `test_engine_answer_v18.py`); no test builds an answer from a graph where a mention hop is cut. Plan §7 asks for rule tests only, and AC-18 and the chain-replay rule are claimed "unchanged".

I ran it: `AB.build_answer` on the guard-test `callee_run_world` (hexified, `AnswerReader`) for a mention-then-mention and a confirmed-then-mention graph. `answer.validate` passes, `recipe.algorithm` is `{id: bfs-v1, version: 1.3}`, `depthBound` is `{bound: 2, unexplored: 2}` and `{bound: 2, unexplored: 1}`, the surviving item is distance 1 with its chain unchanged, and `render_text` reads "Reach stopped at distance 2 with N unexplored edges." (the accepted wording gap at a cut of 1). `render_markdown` also runs. So the claim holds; it is just not pinned. Suggest one answer-level test with these two worlds asserting `unexplored`, the version and the render line, so the wording gap is a recorded contract and not an accident.

### F3. minor. `unexplored` also counts a cut mention edge whose target is already reached closer

Evidence: guard test `test_a_mention_hop_that_would_arrive_at_distance_2...` pins it: the mention site `m` called from the function state is walked as a callee run (`m -> A`), cut at distance 2, and counted (`cut == {c2->B, m->A}`, `unexplored == 2`), although `A` is the anchor. Without the rule that candidate is a dominated arrival and is never counted. This is the same mechanism as the existing bound cut (a cut is recorded before domination), so it is consistent, and the plan accepts the count; but a scripts answer's "N unexplored edges" will now include edges to nodes already listed. Document it in the spec2 §4 sentence the plan owes at close, and do not read `unexplored` as "nodes missing".

### F4. minor. A listed item's distance and chain can change when its best chain is cut (the plan's flagged limit): sound, but state it

Constructed (guard test `test_the_cut_item_is_still_listed...` plus my own differential): item `B` reachable by a mention hop at 2 and by a non-mention chain at 2. The best chain is chosen among kept arrivals; cutting the mention hop before candidates are formed means the other chain is not dominated and survives, with its real edges, status and distance. Differential probe over 3000 random graphs (two units, one flag-false; CALLS and CALLS_NAME with confirmed, `prompt-mention` and `runtime-built` edges; both columns; bounds 1, 2, 3) against the walk with `mention_bound=None`, 9000 walks: new items are always a subset of old; no kept chain holds a mention hop arriving past 1; any state that still had a clean old arrival is still visited; a graph with no mention edge is bit-identical (visited, cut, items, chains). Items whose chain changed (196 in the first run): every one `possible` before and after; at the shipped bound 2 every one stays at distance 2 (160 of 160 in a 6000-graph run). Status cannot move from `confirmed`: a mention chain is always `possible`, so a confirmed best chain never contains one.

At request bounds above the shipped 2 the distance can change: 108 items 2 to 3 and 1 item 3 to 2 at bound 3 (6000 graphs). The listed distance is the best surviving chain's, no longer the shortest graph distance. P1 ships bound 2 and the guards test pins `min(bound, 1)`, so this does not touch the gate; note it in the spec sentence.

### F5. nit. The explicit-`SHIPPED_ROWS` trap is documented but not guarded

`walk(table=bfs.SHIPPED_ROWS)` runs without the mention bound and labels itself 1.2 (honest, tested). Production callers (`group.listing`, `answer_build.build_answer`) pass `table=None`; the P1-39c candidate `V-both` is `candidate_table("V-both") is SHIPPED_ROWS` and so measures the pre-fix walk, which is the historical meaning. No change needed; mentioned so nobody passes `bfs.SHIPPED_ROWS` to "get the shipped walk".

## What was checked and holds

**1. The rule matches the plan exactly.** Read `bfs.py` `walk`: `limit = bound` unless `mention_bound is not None` and `mv.edge.reason in MENTION_REASONS`, then `min(bound, mention_bound)`; the cut condition is `base[1] + mv.row.inc > limit` and records `cuts` through the existing branch, so the edge counts in `unexplored`. The old condition `mv.row.inc and ...` is equivalent for non-mention hops: an arrival's distance never exceeds the bound, so `base + 0 > bound` is false, and the random differential confirms bit-identity on graphs without mention edges. Behaviour checked by the guard tests and my probes: a mention hop arriving at 1 is followed (chain unchanged); arriving at 2 or later is cut and counted; a confirmed first hop does not exempt a later mention hop; an increment-0 mention hop (`ON`, `TO` rows) is followed at base 0 and 1 and cut at base 2; both columns (the depends-on test and the random differential run both); request bounds 1, 2, 60 give `min`; labelled fallback hops keep a possible edge's own reason (`flow.labelled_edge`), so a labelled mention hop is cut and a confirmed edge, relabelled `flow-unavailable:<lang>`, never carries the mention reason (a mention edge is never confirmed: `linker/link.py:252`, `extractors/markdown/extract.py:345`). Termination: a cut only removes candidates; the visited set and `LEVEL_GUARD` are untouched. Only `Walk(...)` in `bfs.py` and one test helper construct `Walk` (`mention_bound` is a defaulted last field).

**2. Chains, schema, render.** Surviving chains are unchanged (F4); the answer builds and validates (F2); the render says "distance 2" for a cut at 1 (user-accepted).

**3. Version and fingerprint.** `ALGORITHM_VERSIONS["1.3"] == "0d5d961ea53c3217468ed1e9ed148a28" == fingerprint(definition())`, recomputed in the archive. `1.1` and `1.2` literals are byte-identical to `7fb9ca06^` (`git show` of the previous file); `definition(ROWS)` fingerprints to the 1.1 pin and `definition(SHIPPED_ROWS)` to the 1.2 pin (run). `answerSchemaVersion` is untouched.
