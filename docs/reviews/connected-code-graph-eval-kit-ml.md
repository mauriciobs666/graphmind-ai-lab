## Rulings

1. **`falkor-chat/server` ports: `[8000, 8200]` stands (default-env reading).** EP §2.4 defines `ports` as "the TCP ports it listens on", recorded from source, and its only consumer is the `.env` row (a variable is `server` class if its URL or integer value hits some listed unit's port). A port is therefore a statement about where the unit really listens in a deployable configuration, not a grep for the token `--port`. `start_agent_team.sh` line 137 sets `AGENT_TEAM_PORT="${AGENT_TEAM_PORT:-8200}"` and line 157 `UVICORN_ARGS="${UVICORN_ARGS:---port ${AGENT_TEAM_PORT}}"`; with no override it execs `uvicorn falkorchat.app:app --port 8200`, so the default expansion is a literal `--port 8200` in the unit's start script, which is the case §2.4 names. The strict reading would classify a `:8200` URL in a `.env` as `contract`, the wrong class for a variable that points at a listed unit's own server. Cost of the reading: none today. The kit holds one `.env*` file (`falkor-chat/server/.env.example`) and its only port-like value is `FALKORDB_PORT=6379` (6379 is in no listed unit). The other five units' empty `ports` hold: no `EXPOSE`/`--port`/`port=` listener in their source (`cypher-mcp/Dockerfile` states "listens on nothing"; `salesperson/vite.config.ts` sets no `server.port`).
   - **Boundary I am fixing so the reading is not open-ended:** a port counts when a compose service, a Dockerfile, or a start script for a service run (`start_*.sh`) resolves to it by default. It does not count for `load_test.sh` (default `SERVER_PORT=8100`, a throwaway harness the script itself calls "off the default"), nor for doc-comment examples (`8010` in `seed_nlq_eval_corpus.sh`, `8201` in `start_agent_team.sh`'s header). `8000` also comes from `compose.yaml` line 34 (`"${FALKORCHAT_SERVER_PORT:-8000}:8000"`, container side) and `Dockerfile` `EXPOSE 8000` plus `--port 8000`; `start_server.sh` and `start_demo.sh` print `localhost:8000` and pass no `--port` (uvicorn default).
2. **`screen.specVersion: "1.2"` stands (spec3).** `docs/plans/connected-code-graph-bundle-spec3.md` carries `Version: 1.2`; `-spec4` carries no `Version:` and its sections are rule 4/file population, symbol and point amendments, and §10/writer notes: `grep -i screen` over spec4 returns nothing, so it amends nothing about the token screen that `bundle.py`'s `screen_fails` implements. EP2 §1.5 says "spec3's version" and the field is diagnostic only, so spec3's `1.2` with `specDocument` named beside it is exactly what the note asks for. EP2 §1.5's wording predates spec3 being superseded; no change to the manifest is needed.

### Findings

**m-1 (minor): `ports` rationale lives only in a comment and a notes file.** `eval-manifest.yaml` calls 8200 "a judgement call". After ruling 1 it is a ruled reading with a boundary (default-resolved ports of compose/Dockerfile/service start scripts; not harnesses or doc examples). Suggest replacing that comment with the one-line boundary above, and amending EP §2.4's "a literal `--port`/`port=` in its start script" to "or the default a service start script resolves to" at the next EP revision. No re-pin: the ports already in the 13 briefs and the manifest are unchanged.

**m-2 (minor): `excludedScope.byClass` mixes two populations.** `count: 3` equals the `prompt-md` class only, while `byClass` reports `doc: 13` beside it. EP §13.1 step 3 counts only files that would be in census scope (code/config `lang` or prompt-bearing Markdown); `doc` files are not. Suggest relabelling `byClass` as "content-check hits by class; only code/config/prompt-md count toward `count`" so the report cannot sum 16 by mistake. The figures themselves reconcile (13 + 3 = 16 content-check files).

**n-1 (nit): `screen` could name the superseding document.** Optionally add `supersededBy: docs/plans/connected-code-graph-bundle-spec4.md (no screen change)` next to `specDocument` so a later reader does not wonder whether spec4 should have been recorded. Diagnostic only.

**n-2 (nit): the `.mcp.json` URL at `:8200` is classified by the `mcpServers.<name>` row, not by `ports`.** Ruling 1's benefit is for `.env` entries only; there is no regression risk either way, but do not cite `.mcp.json` as the reason for 8200 in the manifest comment (S40-NOTES does).
