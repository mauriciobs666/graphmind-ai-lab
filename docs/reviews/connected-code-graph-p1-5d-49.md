## Findings

### B1 (blocker) — origin-drop in `url_path_of` can mint wrong `confirmed` keys, and its tests do not cover the cases that do

Verified (ran; read). Today `normalize_key("GET \x00/api/items/1","consumer")` is `GET /{?}/api/items/1` (the plan's diagnosis of LNK-13 is correct). Reading `ccg/packrt/run.py:_one`: `confirmed` is downgraded to `partial-key` only `if "{?}" in key and unresolved`. After the drop the key has no `{?}`, so the site is `confirmed/key-match` although `unresolved` is non-empty. Problems:

1. **The unresolved piece is not always an origin.** `UNKNOWN` collapses every cause (`extract.py:106,116`: importRef, ref-miss, depth cap, param, env read all return `[UNKNOWN]`). In this repo's own idiom the leading piece is a *path prefix* (`API_PREFIX = "/api"` imported; `BASE = "/api"` in `fx-job`; `API_PREFIX='/shop/api'`). Any residual extractor miss, e.g. the exported-constant defect 5d itself fixes, or `export {X}`/`export default`/a binary expression that 5d's Identifier-target scan does not cover, now yields `GET /files/{?}` **confirmed**, lacking the `/api`. Before: honest `possible/partial-key`. `link.py` matches a confirmed key against every provider of that key in every unit (binding narrows only when one exists), so a consumer whose base is another service (`clients/peer.py`: `os.environ["FX_PEER_BASE"] + "/api/health"`) becomes `confirmed/key-match` to the local `/api/health`. The origin was the only evidence separating the two services. I patched the function in-process (scratchpad plugin) and ran `tests/test_packrt_*`, `test_linker_link.py`, `slice/test_packrt_conformance.py`, `slice/test_linker_conformance.py`: 217 pass, 1 xfail. **No existing test constrains the change**, so only the new tests guard it.
2. **N-17 / spec §1.4 is contradicted, not satisfied.** The rule is "`confirmed` only when every slot its key uses is resolved in that alternative". The key template is `{url}`: one slot, and its alternative contains `UNKNOWN`. The plan's reading ("the dropped origin is not a slot the key uses") redefines slot to sub-string. Reasonable, but it is a spec change, and only the §11 close-time item records it, after P1-41/42 and `ac5-gate-1` have run on the new behaviour.
3. **Under-specified: "an unresolved piece that precedes the first `/`".** Verified edge: `normalize_path_rfc("")` is `/`. A sole-unknown URL (`requests.get(os.environ["X"])`, alternative `"\x00"`, no `/`) under a literal reading drops to `""` and becomes `GET /` **confirmed**, a false match to every root route. `\x00api/x` (partial segment), `a\x00/b`, `\x00?q=1`, `\x00:8000/api/x` (port after an unknown host) are likewise undecided; today they all give a `{?}` segment. The listed tests (leading-unknown, mid-path, scheme-first) pass under every one of these wrong readings.
4. **`LNK-14` is mis-stated.** (c4) says that if the base "is a field read the pack cannot carry, it is reported `possible` with its cause". With the drop, `f"{base}/api/health"` is `confirmed/key-match`, never `possible`. The manifest plants `binding-confirmed`. State which.

**Suggested improvement** (design decision for `architect`; I did not implement it, so it is not proven): make the drop cause-aware or status-honest. Option A: drop the leading piece and keep `possible/partial-key` (the link exists, path-matched, status honest). It still satisfies P1-49 done-condition (2), which counts a `CONSUMES http` linking to the gold provider at any status, but not (1)'s `LNK-13` `confirmed`. Option B: `confirmed` only when the leading piece's cause is a config/environment read (the format already distinguishes `fieldAccess` reads, rule-pack spec §1.4 `config-derived`), `possible` for importRef/ref-miss/param. Either needs `Corpus.alternatives` to carry the cause, which it does not. The stakeholder question "is `confirmed` acceptable for an unknown base?" is `architect`'s to put (see Open questions).

**Coverage probe, required instead of a case list.** One asserted row per cell over: position of the unknown (sole / leading whole segment / leading partial segment / mid-path / trailing) × scheme (none / `http://` / `//`) × remainder after it (empty / `/` / `?q` / `/p`) × count (1 / 2 adjacent) × cause (param / env read / importRef / ref-miss); expected key *and* status per row. The cause axis rows must be authored and committed in a round *before* the implementation round (red first), not inside it, so they cannot be satisfied by construction. Add one two-provider test: same path in two units, consumer with unknown base, asserts the link status the design intends.

### M1 (major) — the 5d rule is stated over one receiver shape; Joern does not support it on the other shapes

Verified by running Joern on snippets (Python `pysrc2cpg`, TS/JS `jssrc2cpg`).
- Method calls: receiver is the CALL `p.uniq`, and the base is its first argument. Python: `p.uniq(2)` base `p: ANY` links module function `uniq` (plan's claim holds); `a.dup()` base typed `A`; `self.m2()` base `self: ANY`. TS: `p: any` ANY, `c.dup()` typed class, but **`this.m()` base type is `a.ts::program`, not ANY**, so a "type unknown" test keeps it `confirmed` (the plan's `this.m()` JS expectation is untested; Python's `self` differs).
- **Bare-identifier calls are DYNAMIC_DISPATCH too** (`helper(1)`, `cb(1)`), receiver an IDENTIFIER, not a base of a member access. The plan's "absent for a call with no receiver" only covers STATIC calls like `fetch`, which `dt` already excludes. Python `def run(cb2, cb): cb(1)` links the module function `cb` (receiver typed `ANY`); `cb2(2)` is typed `__builtin.int` (a shadowing local) yet links module function `cb2`. TS: parameter `cb` receiver typed as the module function `a.js::program:cb`, i.e. known-but-wrong. So a type-based test demotes some and misses others; the rule's guarantee ("name-only links are not `confirmed`") holds only for Python attribute calls on untyped bases.

**Suggested improvement.** Restate the rule over both shapes (member access: the base argument's type; bare identifier: the identifier's own type) and state its limit per language ("TS: not demoted when the base is typed, including wrongly typed"). Add to test (1): bare-identifier on an untyped parameter, a shadowing local, `this.m()` in TS, an interface-typed param, an `any` param. The "probe first" and "recorded deviation" escape hatch is fine; make the probe table those rows and say what a TS result that demotes nothing does to c1/AC-25 (the `name-match` plants would then remain unreachable on TS).

### N1 (blocker) — the bare-identifier rule demotes ordinary direct calls, including planted `confirmed` rows

Verified (ran Joern; the plan marked Python bare-call typing UNVERIFIED). Rule: "type-backed iff `rt` equals the target's `fullName`".
- Python same-module function: `local(1)` receiver `local: ANY`, target `a.py:<module>.local` → **demoted**. Nested `inner()`: ANY → demoted. Imported `from b import helper as h2; h2(2)`: typed, kept. Constructor `K()`: `rt` `b.py:<module>.K`, target `K.__init__` ≠ → **demoted**. A parameter `cb(1)` is also ANY, so type alone cannot separate `local` from `cb`.
- TS: imported `helper(2)` receiver typed as the signature string `(x: __ecma.Number) => ANY` ≠ `b.ts::program:helper` → **demoted**; `local(1)` typed `a.ts::program:local` kept.
- The fixtures call bare same-module/imported Python functions: `core/flow.py:18` `base_price(item_id, qty)`, `api/orders.py:31` `apply_discount(...)`. Their `confirmed` plants (DF-3 callee-run `base_price`, the AC-1/AC-25 Python chains) would turn `possible`, and the plan's own "a row that demotes a legitimate direct call is a stop-and-return finding" fires on the first probe.

**Suggested improvement (probed, not implemented).** Decide the bare-identifier shape by what the identifier refers to, not its type: `Identifier.refsTo` is `METHOD_PARAMETER_IN` for the name-linked cases (`cb`, `cb2` in both frontends, verified) and `LOCAL` for `local`, `h2`, `K`, `inner`, `len`, `helper`, imports (verified, both frontends). Demote a bare call only when the identifier refs a parameter; keep the member-call type-backed rule, which my probe supports (`k.meth()` `K`+`.meth`; `b.helper()` module+`.helper`; TS `k.meth()`/`q.meth()` typed; `self.meth()`/`this.m()`/`p.meth()` demoted; inherited method demoted, as stated). Limit to state: a local rebinding of a module name (`cb = f`) is `LOCAL` and stays `confirmed`. Probe-table rows to assert: module function, nested def, imported + aliased, constructor, builtin (`len`), parameter `cb`, shadowing local, TS imported function, TS parameter.
