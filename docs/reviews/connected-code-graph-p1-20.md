## Findings

### B1 (blocker) — `scope` builds a partial graph and swaps it over the live system graph; the ruled plan says the opposite

`refresh.py:261-273` (`_scoped`) replaces the manifest by the in-scope repositories, so discovery, link, assembly, load and swap all see only those units. Plan § P1-20 (2a): scope "selects which units are **rebuilt**; it never selects which units the graph holds ... a scoped refresh can never replace the system graph with a partial one"; out-of-scope units come from their last good bundle unchanged (`fresh`, own `builtCommit`) or `not-mapped`/`manifest:never-built`. The module docstring (lines 19-20) and `test_scope_limits_the_refresh_to_the_named_repositories` (`test_refresh.py:459-465`, asserts `{u.repo_id} == {"r2"}`) enshrine the old reading.
*Verified (run):* two-repo world, full refresh (6 units), then `refresh(SYSTEM, ["r2"])`: the swap renamed onto live with **3** units. Every r1 unit, and every link that crossed r1 and r2, disappears from the live graph. The implementer flagged the gap; the ruling arrived after.
**Fix:** discover units for every manifest repository; `build_units` only the in-scope ones; for an out-of-scope unit take `_stored_builds` newest passing `_gate` as `FRESH` with its stored `builtCommit` (no `failedAt`), else `NOT_MAPPED`/`NEVER_BUILT`. Heads for all repositories (staleness is then honest for out-of-scope units). Broker `codebases` stays the scope (already so). Replace the scope test. **Coverage probe, not a case list:** parametrize scope over {in-scope, out-of-scope} x {bundle stored / none / refused by the gate / a newer commit since} x unit language, and assert the live unit-id set equals the full manifest's set in every cell.

### M1 (major) — plan item not delivered: `write_private` is not unified to 16 hex

Plan Files: "`write_private` is unified to 16 in the same step". `atrest.py:181` still draws `token_hex(4)`; the sweep accepts both (`atrest.py:304`, verified). I confirmed the implementer's claim: every production bundle write goes `build.py:399 -> atrest.write_bundle -> write_private` (8 hex); `ccg.bundle.write_bundle` (16 hex, `bundle.py:123`) has **no production caller** (grep over `ccg/` and `extractors/`). So 8 hex is what a real crash leaves, and accepting it is right; the plan's "16" was the wrong writer.
Test gap behind it: `test_atrest.py:1036-1041` plants the names by hand (`H8`, `H16`), so a change to either writer's naming cannot fail it (mutating the regex to 16-only was killed, but changing the writers would not be). **Fix:** make `write_private` draw 8 bytes (16 hex), keep accepting 8; add a test that makes `os.replace` fail after `_write_new` with the unlink suppressed (or kills the write mid-way) in **each** writer, then sweeps and asserts the produced name is removed. Axes: writer (`write_private`, `bundle.write_bundle`) x outcome.

### M2 (major) — the plan's default-pack drift test is missing; the pack set is unpinned

Plan: "a drift test compares the set with `cpg/packs/` minus `paper-inhouse-bus`". None exists. *Verified (mutant):* `packs = packs[:3]` leaves all 47 tests green, so a refresh that runs three packs, or a new pack added under `cpg/packs/` and never listed in `DEFAULT_PACKS` (`refresh.py:56`), passes. ### M3 (major) — key-custody wiring is unpinned, and the survivor wrote to the real home

Three surviving mutants: `BuildContext(keys_root=None)` (`refresh.py:342`), `Binder(key=b'x'*32)` (`:373`), `Binder(repos={})`. No fixture produces `bindParts`, so no test would notice a Binder key that differs from the build key (every bindParts-carrying unit would silently become `stale-kept` `bundle:bind-key-check`), and the `keys_root` argument is not pinned at all: dropped, the build reads or **creates** the key under `~/.config/ccg` (I observed it). **Fix:** a test where `keys_root` is a tmp dir and `HOME` is pointed at another tmp dir, asserting afterwards that the key exists only under `keys_root` and `HOME` is empty; and one refresh over a unit whose bundle carries `bindParts` (a Compose/`.mcp.json` fixture with a URL entry) asserting no `bind-key-mismatch` line and that a different key does produce one. Axis: key source (build, binder) x key present/absent.

### M4 (major) — a prune failure after the swap raises and loses the report

`refresh.py:401-402`: `prune_unit` can raise `AtRestError` (it `ensure_private`s every candidate, `atrest.py:289-296`). *Verified (run):* a symlink `<unit>.zz.bundle.jsonl` planted in the bundle directory makes `refresh` raise `AtRestError` **after** the rename: the live graph is the new one, the caller sees an exception and no report, and a naive retry rebuilds everything. The docstring promises that a failure before `swap` leaves the live key untouched; it says nothing of one after. **Fix:** catch `AtRestError` per unit in the retention loop, count it (`RefreshReport.prune_failed`) and put the count in `lines()`; add the planted-symlink test above (after the swap, the report is returned and `swap.renamed` is true).

### M5 (major) — the peak-memory figure does not measure what R-4 needs

Which method ran: `/proc/self/clear_refs` (value 5) then `VmHWM` (`refresh.py:162-181`). *Verified (run) here (WSL2 5.15.167):* it works, a 200 MB allocation moved the figure 29.8 MB to 234.6 MB and a reset brought it back to 29.9 MB, so `peak_rss_kb` is a trustworthy per-stage figure **for the Python process alone**. Two limits: (1) the Joern run is `docker run` (`sandbox/offline-run.sh:522`): its JVM lives in the container's cgroup, not in this process or in `RUSAGE_CHILDREN` (the child there is the `docker` CLI). The R-4 question (peak on a 6 GB host, `p1.md` R-4) is the JVM's. (2) `children_peak_rss_kb` is `RUSAGE_CHILDREN.ru_maxrss`, a never-reset maximum over all waited children, not per stage; in my planted run it equalled the parent's own peak (47,632 KB in every stage), the fork-before-exec artifact of `ru_maxrss`. The test (`test_refresh.py:182-187`) only asserts `> 0`.
**Fix:** label the field as the orchestrator's; for the Done record take the container's peak from `docker stats`/the cgroup `memory.peak` of the sandbox run (a devops-owned measurement) and record it beside; drop or rename `children_peak_rss_kb`, or compute a per-stage delta; assert that two stages with a planted allocation in between report different peaks.

### M6 (major) — `RefreshReport.lines()` prints repository-controlled text raw

`refresh.py:148-149` prints `u.root_path` (and `fail_reason`) for every non-fresh unit; the module docstring (line 24) says "counts, codes and ids ... no source text". *Verified (run):* a committed file named `a\nrefresh rfs: 99 fresh\x1b[2J.sh` produces the line `not-mapped <id> shell a\nrefresh rfs: 99 fresh\x1b[2J.sh extract:failed`, i.e. a forged report line and a terminal escape in whatever prints it. **Fix:** print the unit id only (the path is in the graph), or `repr`/escape it; add a hostile-path test over {newline, ESC, NUL, 4,100-byte name}.

**(1) Order of the state write — recommend writing before the swap, no `pending` token (S1).** The state's reader is the *carry*, which reads the **bundle store**, not the graph; so the record belongs with the bundles (written by the build, before the swap), not with the swap. Reproduced (planted `BaseException` at the state write, then `refresh(["r2"])`, two-repo world):
- *Crash after the swap, victim rebuilt `stale-kept` (kept bundle c1), previous record `fresh`:* the next carry reads **`fresh`** — the marker is lost (optimistic; the delegate's concern is real).
- *Crash after the swap, victim previously `stale-kept`, now rebuilt fresh at c2:* old record names c1, newest bundle is c2: fail-closed `stale-kept`/`extract:failed` (pessimistic, wrong code).
- *Swap fails, previous record `stale-kept` at c1, a fresh c2 bundle on disk:* the carry reads `stale-kept`/`extract:failed` although the unit's rebuild succeeded (pessimistic).

**(2) State versus graph, can they diverge?** Yes in two safe ways and no unsafe one beyond S1.
