## Findings

### M1 (major, verified by probe): the scripts resolver as specified reaches little of the dev gold, and its placement is not chosen

Plan §3.1 confirms only a "complete literal" path and otherwise emits `possible` with a dynamic reason. I ran both extractors over the dev gold's impacted files (46 symbol-anchored items; scratchpad `probe.py`). Result for "does the impacted element already carry a call site naming the anchor":

- **Markdown (17 items): 15 already do.** `extract_markdown` emits a `possible`/`prompt-mention` call site for an inline-code-span script path (`cpg/extractors/markdown/extract.py:313`). The plan's §3.1 "prompt documents ... become call sites" is therefore already built; only the resolver is missing. Two items do not: `claude/tdd-engineer/tdd-engineer.md` and `claude/tico/tico.md` carry the script only as a front-matter `hooks: ... command: $HOME/.claude/agents/tico/hooks/guard-...sh`, and front matter yields only tool mentions. Reaching them needs a new front-matter hook-command extraction (not in the plan), and the path is an installed path (`$HOME/.claude/agents/<x>/hooks/..`), not a repo path.
- **Shell (26 items): 1 already does; 25 do not.** The shell call site carries only the command word (`source`, `.`, `bash`, `exec`); the path argument is not in `calleeName` (`shell/extract.py:620-625`). Where I read the invoking line, the path is computed, never a literal: `. "$(dirname "$0")/shlib/opencode_config.sh"`, `exec "$(dirname "$(readlink -f "$0")")/../../scripts/guard-broad-write.sh"`, `"$REPO_DIR/scripts/bootstrap_schema.sh"`, and the gold `why` lines name `$HERE/...`, `$ROOT/run.sh`, `$PY $HERE/server.py`, `$PY -m modelbench` for 11 more. Under §3.1 these produce `possible` with no resolved target, hence no `CALLS` edge. The plan never says how a `possible` edge acquires a target, and its rejected option (basename match) is the only mechanism that would. The design needs a stated rule, for example: a dynamic head (`$VAR`, `$(dirname "$0")`) is dropped, `..` normalised, and the static tail resolved by unique path-suffix match among the system's script files, `possible` when unique, nothing when ambiguous. CO-1 must size that against the 25.
- **Unreachable by the plan as written** (dev, counted): 3 items impacted at `test-stamp-wiring.sh`, which fails tree-sitter parsing (`parse-error`, only `<script>` kept, so `run_block` has no symbol or call sites; also the source sits inside a `bash -c '...'` string); 1 Python caller (`falkor-chat/scripts/seed_eval_corpus.py` running `bootstrap_schema.sh`, which needs the Python extractor or Joern side, not named anywhere); 3 Python `<module>`/`server.py` anchors reached through `$PY -m pkg` / `$PY $HERE/server.py` (`-m` package resolution is a listed P2 item, `-p1-linking.md` ~l.929); 2 front-matter hooks (above); 1 contract item whose consumer is Python embedded in a shell script (`demo_falkor_chat.sh`).
- **Placement.** The extractors run per unit and may not follow files; the assembler already drops a target that is not in the snapshot (`rows.py:546-549`, `calls-target-not-in-snapshot`) and `symbolId` depends only on `(lang, repoId, qname)` (`ids.py:97`), so an extractor can name a target without seeing it, but only the assembler (or a linker pass) can do suffix matching across units. The plan names `rows.py`, the extractors, and "the existing dynamic-reason vocabulary" without choosing. It also does not say whether the path argument travels in an existing record (`valueSet`/`constant` for shell) or a new field, which decides whether `bundleSchemaVersion` moves; the "no answer-spec row" claim covers only the answer side.

**Suggestion.** Make CO-1's table classify each dev item by the five forms above plus the unreachable list, and make the architect's ruling state (a) the resolver's layer, (b) the dynamic-head rule and its ambiguity behaviour, (c) the carrier record and whether the bundle schema changes, (d) which of the unreachable items are triaged rather than built. Own the `test-stamp-wiring.sh` parse defect (the RCA's item 5, "independent of the decision") in CO-2; it is currently unowned (see M5).

### M2 (major, reasoned from `gate.py` and the plan): the §3.4 entry criterion does not predict a held-out pass

§3.4 admits "every dev item ... listed **or carries a recorded triage**". Only a `key-error` triage removes an item from the count (`gate.py` outcomes: `out-of-scope (triaged key-error; never a hit, a miss or a wrong-possible item)`); the other five triage classes (`extraction`, `recognizer`, `linker-engine`, `depth-bound`, `dynamic`) are still misses at the held-out gate. By M1, a rehearsal that triages the 8 or more unreachable dev items as `extraction`/`dynamic` would meet the criterion while predicting held-out misses at the same rate. Zero misses over 159 items is the pass rule; the plan itself (§9) calls a first-spend failure likely.

**Suggestion.** State the criterion as: on dev, every item is a hit or a `key-error` removal, and any item the architect rules "not built" is reported as a withheld shape with its held-out analogue count unknown, so the spend is a decision the stakeholder takes with the number in front of them. Record the dev-fit caveat in the prereg (the dev set drove the mechanism design).

### M3 (major, verified): CO-11 and CO-10 are not parallel to the freeze commit F

§5 lists CO-10/CO-11/CO-12 as parallel tracks and the minimum close-out excludes CO-11, yet §5's last bullet admits CO-11 edits `cpg/ccg/front/`. `coreTreeHash` covers every tracked file under `cpg/` except `eval/`, `packs/`, `tests/` and `*.md` (`cpg/eval/tools/ac24_smoke.py:576-596`), so `ccg/front/` is core; so are `ccg/`, `extractors/`, and `infra/` (CO-8). The gate also asks through the interpreter (HA-3 reads `interp.status`), so a prompt/model change is gate-relevant. CO-11 depends on Q5 and on LM Studio availability and so has no bound; as drawn it either blocks F indefinitely or invalidates the record after CO-6. Also note CO-3's new pack lands in `packSetHash`, and CO-8's `cpg/infra/ccg-falkordb.sh` edit is core, which the plan handles only by "finished before F".

**Suggestion.** Put an explicit rule in §5: CO-11 produces no `cpg/ccg/` change before the gate run, or else it is on the F critical path; if its output is a model/config change outside core, say where it lives and that the prereg pins it. The simplest honest arrangement: CO-11's code changes wait until after CO-9 and the AC-5 verdict does not depend on them. Q7's recommendation (b) already assumes this; the sequence diagram should say it.

### M4 (major, verified in spec): Q3's recommended W3 very likely collapses to W2

Answer-spec2 §3.3: a `config` item exists only as the `BOUND_BY` target of a `Link` reached by `TO <-`, and `launchFact`-origin entries "are not items" (`docs/plans/connected-code-graph-answer-spec2.md` §3.3 and the Not-changed list). Against the 11 dev wiring items: the 3 launch-a-script entries and 3 tool-name entries (`allowedTools[0]`, `tools[0]`, `prompt`) are inexpressible without a spec change; the 4 server-URL entries need a `Link` whose consumer is a code call site that the config entry binds, and the real run had 0 `bound[]` on 179 Link hops (RCA evidence 3). The 3 "launches script" items also cannot be reached through the shared §3.1 resolver (the edge is config to script, not call site to script). CO-1 may find one or two expressible entries at best, with a nonzero chance of none.

**Suggestion.** Rewrite §3.3 and Q3 to say that expectation: W3 is W2 plus whatever CO-1 finds, and name the consequence now (wiring held-out 8 stays blind, AC-2/AC-4 wiring halves stay open and need `tico`'s wording change; pooled floor stays met by the other three strata, 151 counting items). Also reconcile the denominators: the plan says wiring "0/7 asked" and "11/11", scripts "49/49", while the RCA's run measured 0/46 and 0/11 (11 gold items, 7 of them asked); CO-1 should publish the one denominator its table uses.

### Minor
