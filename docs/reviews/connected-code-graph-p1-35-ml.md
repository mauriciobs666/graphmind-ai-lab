## Pass 1

**(1) Scorer.** Conforms: unambiguous understood iff `resolved` and the request set equals gold; ambiguous with `goldOptions == []` iff `status != resolved`; otherwise `ambiguous` with every gold option contained and `|options| ≤ max(5, |gold|)`; silent single reading and `unresolved` on non-empty gold fail. Thresholds use exact `ceil` (23/24, 11/12) and Wilson intervals; the claim line avoids certifying 0.92.

- **M1 (major): the unusable-reply observable.** The harness reads "ambiguous, `no-anchor`, `options == []`, provenance present, `cacheHit` false" as an unusable reply and scores "not understood" on every item. A validly empty reply is the same shape: the grammar requires one anchor group, a question naming no anchor yields a group the resolver cannot use, and the answer is `ambiguous`/`no-anchor`/`[]`. That is precisely the legitimate answer to a held-out ambiguous item with `goldOptions == []`.
  - The harness would score it "not understood". EP §10.5 needs every ambiguous item understood (6/6), so a single such item makes the gate fail whatever the interpreter does. The direction is conservative (it cannot flatter), but the gate then fails for a reason unrelated to interpreter quality, and the failure is uninformative. A stated limit is not acceptable here.
  - Fix, no schema change: the live rig builds its own `Interpreter`; wrap its `interpret` call and record, per ask, whether the returned `Interpretation.draft is None`. That is the exact event. Score "unusable, not understood" from that flag on every item (the rule I set in `-p1-ml.md` §4.2 for repeat 1), and drop the shape heuristic. A usable empty answer is then scored by EP §10.4 like any other.
  - Test: a stub interpreter returning a valid draft that names nothing on an item with `goldOptions == []` scores understood; a stub returning a non-JSON reply scores not understood.
- **Minor (m1):** EP §10.4 applies E1 (map an interpreted symbol anchor to its eligible element) before comparing. The scorer compares `repoId`+`qname` directly. It is conservative and probably unreachable (the resolver returns eligible elements), but state that or implement it.

**(2) Repeat protocol: the author is right; my note and EP §10.4 were inconsistent.** Both said "each item runs 5 times with `cacheBypass`" and also "`cacheHit` true on repeat 1 stops the run (C5)". With a bypass on repeat 1, a hit cannot occur (the schema forbids bypass together with a hit), so the C5 check would be vacuous. The scored draw is the first fresh interpretation of the question for that snapshot. Repeat 1 without a bypass on an asserted-empty cache produces the same model draw (same request, `temperature` 0), and exercises the production path and the C5 control. Repeats 2–5 need the bypass because repeat 1 has filled the cache.
- `-p1-ml.md` §4.3 is amended in place (repeat 1 uncached on an asserted-empty cache and scored; repeats 2–5 with `cacheBypass`).
- **Owed to the EP owner (EP §10.4, "Repeats are uncached by a bypass, not by an empty cache"):** replace with: "Repeat 1 is uncached because the cache is asserted empty before the run; repeats 2–5 are uncached by a bypass, because repeat 1 fills the cache. Every repeat must carry `cacheHit == false`." The planted inputs there read "with the bypass, five repeats must give `false` five times": change to "repeat 1 without the bypass on an empty cache gives `false`; repeats 2–5 with the bypass give `false` and carry `cacheBypass`; with the cache on, the same question twice gives `true` on the second."

**(4) Parser-resolved items.** They enter the denominators (`n` is the recount of all 24 and 6) and are scored by the same rule as any item; only the flip rate and the per-draw rate exclude them. That is consistent with EP, which scores the interpretation of a question by the plain-language client, not the model alone. State in the report that the pooled rate then mixes parser and interpreter draws, with the parser count. Held-out questions are prose, so the expected count is near zero.

**(5) `coreTreeHash`/`packSetHash` not recomputed: M2 (major), close before the held-out run.** EP §12.3 requires the harness to recompute both at the run and compare them with the record. The harness only copies them into the record. `resolverVersion` is a constant a human bumps, so a resolver or front code change after registration is undetected; `coreTreeHash` is the control for that. Fix: recompute both from the working tree before the marker; refuse on a difference (stricter than EP's "after adaptation" label, which would waste the once-only run), with an explicit override that stamps the result "after adaptation". Also refuse a dirty tree or record `git rev-parse HEAD` and cleanliness in the result.

**(6) Effective sampler.** `build_live_rig` has no observer, so `sampler.effective` has no source, and `run_items` raises a harness error when the record's `effective` is non-null and no observer exists (fails closed, correctly, but after the marker; see m2). Recommendation, now that the request pins every shaping parameter explicitly (`top_k` 0, `repeat_penalty` 1.0, penalties 0):
- The record carries `sampler.request` (pinned) and `sampler.effective: null` with `effectiveStatus: "not-observable"`, so the harness need not fail on it. Non-null effective with no observer is a pre-flight refusal before the marker.
- Replace the unobtainable read with two checks, both recorded: (a) a live differential probe that the endpoint honours the pinned `repeat_penalty` (two requests differing only in it, outputs compared), recorded as a probe; (b) a canary digest: a fixed set of made-up `fx-*` questions run at dev time and again at the start of the held-out run, replies byte-equal or a harness error. That detects drift in preset, template, or model without reading config. `min_p` and the other truncating samplers cannot change a `temperature` 0 argmax.
- `-p1-ml.md` §4.3 is amended accordingly.
