## Findings

### Major

**M1. The `SessionStart`/probe hook can relaunch `:8200` during the outage, at dim 1024 (omission; traced by reading, not reproduced).**
Evidence: `claude/teco/hooks/ensure-environment.sh:155-166` launches `start_agent_team.sh` detached, via `env -i`, whenever `:8200/health` refuses the connection. The env kept (`:114-117`, `KEEP_ENV`) has no `EMBEDDING_DIM`, so the script's default `EMBEDDING_DIM=1024` applies (`start_agent_team.sh:137`). The hook runs on any `claude --agent teco` start and as teco's own step-1 probe at every decomposition (`claude/teco/teco.md:85`), and teco is the plan's coordinator. Between runbook steps 3 and 5 the port is free, so a probe launches a server at 1024 against a graph that is mid-migration: it then serves/ingests during the re-embed (violating the "traffic stopped" precondition), runs `bootstrap_schema.sh` with `CREATE VECTOR INDEX ... dimension:1024` (`:391-397`), and occupies `:8200` so step 5's start fails. If that bootstrap lands between migrate's `DROP VECTOR INDEX` and `CREATE` (`embedding_migration.py:202-212`) the create can find a 1024 index and the graph ends at the wrong dimension. The same race exists after cutover, because the default stays 1024 (plan step 8 treats a 2560 default as optional).
Suggest: (a) hold the existing start lock for the whole window: the hook only launches when `flock -n` on `~/.local/state/graphmind-ai-lab/agent-team-8200.lock` succeeds (`lock_held`, `:123-125`), so `devops` running steps 3-5 under `flock <that file>` makes the hook report "already being started" and do nothing; run the step-5 restart under that same lock; (b) make the `start_agent_team.sh` default `EMBEDDING_DIM=2560` part of step 8, not a stakeholder preference, and have the hook's `env -i` consistent with it; (c) add "no teco session start or `ensure-environment.sh` run during steps 3-5" to step 1 pre-checks. Verification the owner can run: with the lock held and `:8200` down, `ensure-environment.sh </dev/null` must print "already being started" and launch nothing.

**M2. The "45-pair regression" is a markdown table, not a runnable set; steps 0 and 6.3 depend on a harness that does not exist.**
Evidence: the pairs live only in `claude/docs/plans/agent-knowledge-base-strategy-ml.md` "Stage 8 Phase 1" (long free-text queries plus expected ids); results in `claude/docs/test-reports/agent-knowledge-base-strategy-ac2-report.md` (pooled recall@5 0.875, Wilson 95% CI [0.719, 0.950], n=32 applicable of 45). `claude/cobb/scripts/` holds only the python-web-quirks tooling (`pwq_kb.py`, fixture `fixtures/pwq-golden-set-a.json`); no file there or elsewhere encodes the 45 pairs (`grep -l "45-pair"` hits docs only). The plan says "re-run" as if it were a fixture. Mapping is not a problem: all 48 expected `documentId`s extracted from that table exist in `ws:agent-team` (48 found, 48 `ready`) and in `ws:pwq-test` (48 found), so the plan's "rows that do not map reduce its power" caveat can be dropped.
Also, the go/no-go "no regression in pooled recall@5" is undefined at this n: one pair is about 3 points and the CI is about +-0.12, so the stated rule fires on noise in either direction.
Suggest: (a) `qa-engineer` first freezes the 45 pairs into a committed JSON fixture plus a small runner (document-level top-5, literal skill prefix, scores kept), reviewed before step 0 runs, so the same artifact is used at step 0 (`:8210`, `:8200`) and step 6.3; (b) fix the decision rule before the first run, as a paired table (pairs found at 0.6b/0.43 and lost at 4b/0.42, and the reverse) with a named stop threshold chosen by `data-scientist`, not "no regression".

**M3. The plan's own premise "not verified" for MCP reconnect is already documented; it is an expected, user-visible consequence, not a possibility.**
Evidence: `claude/teco/coordination-techniques.md:27-29`: the `falkor-chat-agent-team` MCP "does not reconnect on its own after its ~7s initial-connect retry window", and the user must run `/mcp` -> `falkor-chat-agent-team` -> Reconnect; the hook text says the same (`ensure-environment.sh:164`). A ~10 minute outage is far past that window. Plan §6 "Other consumers named" says "may need a reconnect ... (not verified)"; §7 approval 2 lists only the outage.
Impact: after restart every open Claude session loses `search_documents`/`ingest_document` until its user reconnects, and learning captures attempted during the outage fail (not retried), so those learnings are lost. Neither appears in the irreversible list (§5).
Suggest: state both in §7.2 and §5 (lost captures during the window are irreversible; reconnect is required per open session), and drop the "not verified" hedge, citing `claude/teco/coordination-techniques.md`.

**M4. What the stakeholder is told about "no regression" must be narrower than §1/§7 imply, and the plan should say so explicitly.**
Evidence from the B3 report (`docs/test-reports/python-web-quirks-kb-report.md`): the pass is 115/126 at floor 0.42 against a bar of 114, i.e. one query; raw (no floor) recall is 123/126, the floor removes 8 (lines ~361, 376); B3 was never scored on the 0.6b, so there is no paired 0.6b-vs-4b result on the same sealed queries (0.6b's 110/126 is B2, a different set); the 4b was the best of many Set A looks (`path-ml.md` §7, cited by the plan itself); production's competitor set differs from staging's by 4 documents plus later captures (plan §2). The floor 0.42 sits 0.002 below the closest staging near-negative (0.422, plan §8), so most of the floor's value rests on Set A, which is saturated and not held out.
Answer to the question asked (check 3): a new sealed set on production is **not required as a go gate**: the change is reversible (R1), the corpus difference is small (465 of 518 staging documents shared, plan §2), and a post-migration sealed set would cost a new frozen set for a claim already bounded by R1's cheap rollback. But Set A (non-blind, saturated) plus the 45 pairs (n=32 applicable, wide CI) **cannot support the sentence "no regression in production"**; they support "no gross regression, and no loss of any pair that was found before". The stakeholder should be told: promotion rests on one staging pass by one query, with an unmeasured production re-check of limited power; if they want a claim about production quality, a new sealed set (B4) on the post-migration production corpus is the only instrument, and it can be scheduled after the fact without blocking cutover because R1 stays available.
Suggest: replace the §1 phrasing with this; add to §7.1 "knowing there is no paired 0.6b/4b result on a sealed set"; add a standing open item "B4 on production, optional".

### Minor

**m1. R2's backup is taken too early, so R2 loses more than necessary.** Step 1.4(b) copies the graph while `:8200` is still serving; every ingest between the copy and step 3 is absent from `ws:agent-team-pre4b`. Take the `GRAPH.COPY` (and the logical export) immediately *after* stopping the process at step 3, so R2 loses only post-cutover writes. The export can use read-only Cypher once the API is down. Also record the transient failure mode: a previous `GRAPH.COPY` here returned `could not fork` on first try (`docs/plans/python-web-quirks-kb-graph.md` §1 finding 1); the retry rule is "retry once, check `GRAPH.LIST` first, never query the destination key between attempts" (querying it silently creates it). Host memory now: `free -m` showed 562 MB free, 3323 available (FalkorDB 478 MB per plan).

**m2. Plan §2/§4 mark as "not observed" three things that are documented.** (a) `GRAPH.COPY` carries vector indexes and embeddings: verified in `docs/plans/python-web-quirks-kb-graph.md` §1 ("Verdict: yes"), and `ws:pwq-test` itself was created that way; R2 is therefore not "documents-only". (b) The `~/.claude.json` `8200` string is a telemetry float (`frame_duration_ms_p50 0.4335820...`), not a consumer. (c) The reconnect behaviour (M3). Replace each with its citation.

**m3. `start_agent_team.sh` with `EMBEDDING_DIM=1024` is probably harmless at runtime once `models.json` declares the 4b `dim`; the real hazard is only the bootstrap.** `embedding.py:182-197` resolves the dimension from the overlay model's `dim` before `config.EMBEDDING_DIM`, and compares it with the index; a mismatch raises `EmbeddingDimensionError` before any HTTP call (read, not run). `EMBEDDING_DIM` matters only to `bootstrap_schema.sh`, whose `CREATE VECTOR INDEX` on an existing index is stated to return "already indexed" without aborting (`bootstrap_schema.sh:8-10`); what FalkorDB does when the dimension differs is not observed, and I could not test without a write. Keep the plan's `EMBEDDING_DIM=2560` instruction and its fallback; just do not describe it as the only protection (M1(b) is).

**m4. Step 6 runs while agents are already using the 4b at the old floor.** Exposure is steps 6 plus 7, not the "minutes" step 7 claims; Set A with perturbed forms, the 45 pairs and the smoke list are not timed anywhere in the plan. Either bound the verification time or run steps 6.1-6.3 on a side port against the migrated graph before the `:8200` restart (costs one more restart). If the plan keeps the current order, say the window is unbounded and that a failed step 6 means a second outage for R1.

**m5. K-102 evidence is destroyed by the migration; the backup retention rule conflicts.** Today 14 `failed` documents, 13 unembedded chunks in 12 of them, `pendingJobs` 0 on all, 0 `processing` (observed by Cypher; matches the plan's counts, and the 17/1 of the brief is stale). Search has no document-status filter (`repository.py:1302`, `WHERE seed.documentCurrent = true` only), so once embedded those 12 documents become searchable, as the plan states. Before step 4, write the 14 document ids and 13 chunk ids to the ledger for `falkor-chat/docs/BACKLOG.md` K-102 (the item's reproduction state), and keep `ws:agent-team-pre4b` until K-102 is closed or that list is recorded, not just "one week".

**m6. LM Studio query-time timing.** `models.json` `timeouts.embedding` is 30 s. Step 1.2 says "note the timing" with no threshold; a cold 4b JIT load after eviction could exceed 30 s on the first agent query and surface as degraded search. State an acceptance threshold in step 1.2 and in the 4b post-cutover check. Staging 75.0 s for 902 chunks is in `docs/plans/python-web-quirks-kb-staging-graph.md`; the embedder note's 114 s (same workload) is not reconciled, so "under 10 minutes" is fine but the two figures should not both appear as measurements.

## What's solid

- The Option A vs A2/B/B'/C2 reasoning is correct and grounded: A2 would break `acme`/`eval`/`nlq-eval` (no override), which I confirmed; the single-process-per-workspace fact kills the "second instance" alternative.
- Runbook order (declare dim -> stop -> migrate -> restart -> verify -> floor last) matches the script's preconditions and the dimension cache restart rule (`embedding.py:146-151`).
- Irreversible list is honest and mostly complete; the `models.json` edit is one entry and safe.
- Read-only pre-gate on staging before any outage is a good stop point, and the floor decision is correctly left to the stakeholder.
