## Answers

### DS-1 — cache-key question normalization: NFC and case-kept are right; whitespace collapse is too aggressive; two inputs are missing from the key

- **Keep** NFC (macOS-composed vs decomposed Portuguese input would otherwise miss) and **case kept** (`getHealth` vs `gethealth` are different identifiers; PT `e`/`é` differ in meaning, so no accent-fold, no casefold). Do not use NFKC.
- **Change (E1, minor):** collapse only runs of spaces/tabs within a line, convert CRLF to LF, strip the ends, and **keep newlines**. Questions here include pasted fragments (EP §4.2: "pasted fragments are expected"); newlines and indentation in a pasted trace or YAML carry meaning. The cost asymmetry decides it: under-normalizing costs one extra model call; over-normalizing risks serving one interpretation for two inputs the model would read differently.
- **Change (E1, major):** the model must be fed **exactly** `normalizedQuestion`, the bytes that are hashed. Otherwise the cached interpretation depends on which raw variant was asked first, and FR-19's "same question, same facts" depends on cache history. Add this sentence to §3.
- **Cache-key gap (E2, major):** the key `h(["interpretation", normalizedQuestion, snapshotId, modelFingerprint, promptHash])` omits `temperatureMilli` and every other sampler or grammar input. Change the temperature and the old interpretation is served while the provenance describes the new setting. The key must contain every provenance field that can change the model's output (see DS-2).
- **Flip-rate effect:** none by construction, *if* the harness bypasses the cache. EP §10.4 / ML §4.4 want 5 **uncached** repeats. With the cache on, the repeats return one sample and the flip rate reads 0 regardless of the model. **Harness rule (E5):** every repeat must carry `provenance.cacheHit == false`; a `true` voids the item. Likewise "first run only" (EP §5.3) means the cache must be empty for the gate snapshot.

### DS-2 — provenance: not sufficient

Attribution of a changed interpretation works by differing two provenance records: one field differs, that factor is the cause; two differ, it is confounded and needs a factorial rerun. With identical provenance and `cacheHit` false on both, the change is **sampling variance** (the thing the flip rate measures). The current fields cannot support that logic because the following are missing or undefined:

1. **Resolver version (major).** An interpretation is the model's spans plus the *deterministic anchor resolver* (ML §3.1 (a)). A resolver change (lexical index, tokenization, candidate cap) changes `request.anchors` with model, prompt and snapshot all identical, and `recipe.algorithm.version` versions the *walk*, not the resolver. Add `resolverVersion` (MAJOR.MINOR string, bumped on any change that can alter resolution), and put it in the cache key.
2. **`promptHash` is undefined as to scope (major).** "SHA-256 of the interpreter prompt text" does not say whether it covers the few-shot examples, the JSON-schema or grammar used for constrained output, or the rendered text with the question substituted (which would make it per-question and redundant with `cacheKey`). Define it as the hash of the canonical bytes of `{template, fewShots, ...}` with the question slot empty, and carry a separate `grammarHash` for the constrained-output schema, so a schema change is not misread as a prompt change.
3. **Sampler parameters.** `temperatureMilli` alone is not the sampler. Carry the closed set that was actually sent (`topP`/`topK`/`minP` as integer milli or int, `maxTokens`, and `seed` if the endpoint honors one; verify that against the endpoint before specifying, I did not). Simplest form: `samplingHash` over the canonical object of every non-default parameter, with `temperatureMilli` kept readable.
4. **`quantization` optional.** `GET /api/v0/models` returns `quantization` per model (verified in `lm-studio-model-notes.md`); make it required when `endpoint == local`.
5. **`modelFingerprint` is an identifier, not an identity.** The LM Studio catalog fields (`id`, `arch`, `quantization`, `max_context_length`) do not hash the weights, and the same notes record that KV-cache settings and the app version are not machine-collectable. State both limits in §3: for `local`, those are operator-attested in the gate's pre-registration, not in the answer; for `hosted`, record the model id the API *returned*, not the one requested (an alias can move).
6. **Cache lifetime.** State that a cache entry lives as long as its snapshot. An eviction followed by a re-ask re-samples and can change facts under identical provenance; without a stated lifetime that is an undocumented FR-19 hole.

### DS-3 — what an RCA mark is, and an integer-only ranking score

- **An RCA mark is the investigator's feedback on a hypothesis**: `ruled-out` or `confirmed` (proposal §3.7 "Feedback marks", FR-12). It is **part of the echoed request**; it re-ranks and expands the tree for that investigation only, nothing persists. It is an input, not a score and not a ranker annotation. Verified: proposal §3.7 and §3.6 step 5 ("the interpretation (... and RCA marks)").
- **Consequence for the spec:** marks change facts, so they must stay **inside** the facts boundary (not under `provenance`). They do as drawn. Shape for P5, additive: `{hypothesisId: 32-hex, mark: "ruled-out"|"confirmed"}`, sorted by `hypothesisId`, where `hypothesisId` is the engine-minted id of the cause locator. Keep v1 `rcaMarks: []` (E6: also say "marks are request inputs").
- **Integer score** (ML Q2 uses floats in [0,1] and `0.85^hops`; floats are forbidden here):
  - features `f_i` are integer **permille** in 0..1000; weights `w_i` are positive integers; contribution `c_i = w_i * f_i` (exact, no division); `score = Σ c_i`, an integer; order by `(score desc, id asc by code point)`.
  - the only rounding is inside feature definitions, fixed once: anchor agreement `floor(1000*k/n)`; chain strength `floor(s * D[h] / 1000)` with `s` ∈ {1000, 500, 250} and `D` a **committed integer table** (round-half-up of `1000*0.85^h`), never a runtime float `pow`, which is platform-dependent.
  - the weights of record are the **quantized integers**; tuning (ML Q2, dev split) may use floats, but the held-out evaluation must be run on the integer ranker that ships. Any weight, table or rounding change bumps `recipe.algorithm.version` (extend §4.1's rule).
  - answer carries per hypothesis `score` and `[{feature, w, f}]` (integers), which is also the "each feature's contribution is shown" requirement (AC-12).
- **Eval note (inferred, for P5):** coarse integer features make exact ties common, and the id tie-break is an arbitrary hash order. Report hit@k under the id tie-break **and** under the pessimistic (true cause last among its ties) and optimistic readings; a gap between them means the rank metric is partly measuring the tie-break.

### DS-4 — a question naming an unknown or unmapped file: score as `unknown-name`, no new category, with an explicit rule

- Both `not-found` and `not-mapped` are "the asker named something that yields no anchor"; EP's `unknown-name` already has gold `[]` and the right behavior "ask / resolve no anchor silently". A fifth category would be a P1 gate change for no discriminating power.
- **Scoring gap (major, E3):** EP §10.4 says an ambiguous item is understood when the answer is "an option set, or an explicit request for clarification". The spec's `unresolved` status with `lookups` is neither literally. State the mechanical predicate: **for gold `unknown-name` and `no-anchor`, understood iff `interpretation.status != "resolved"`** (ambiguous or unresolved; no query ran, which V2 already enforces). For `several-symbols` and `two-use-cases`, status must be `ambiguous`. The emitted `ambiguityKind` is a diagnostic, not scored (the system's label and the writer's label need not agree).
- **Gaming note:** "resolves nothing" is trivially satisfied, so an always-ask system scores 100% on `unknown-name`/`no-anchor`. The over-asking rate on unambiguous items (EP §10.4) is the counterweight and must be gated together with it (EP §10.5 already requires 23/24 unambiguous).
- **A real-but-unmapped file as the *only* anchor** (a test file, `frontend-ignore`) cannot be an unambiguous gold item (gold anchors must be eligible, E1), so it either enters QW as `unknown-name` or is not written. The answer must keep saying "not mapped, reason", never "no impact" (FR-7a): that stays a spec §3 matter and is correct.

### DS-5 — is `interpretation.request` part of "facts"? Yes, keep it; the AC-16 test procedure must change, and one boundary detail should be fixed now

- FR-19 defines "same question" as the question *as the system understood it*, so the request is the input that determines the facts. Facts of two different requests cannot be equal, so excluding the request from `facts_bytes` would not help a plain-language client; it would only hide a client that lost `scope` or rewrote an anchor.
- A plain-language client that interprets differently is an **AC-24 failure, not an AC-16 failure**. Define the AC-16 test (**E4**) as pin-and-replay (ML §3.2 item 4): take the request echoed by the plain-language client, submit it through MCP, CI script and raw recipe, and require `facts_bytes` equality across all four. Counting a misinterpretation in AC-16 double-counts it.
- **Boundary detail (E4, minor):** `anchors[].line` is "the asker's file:line, informative" yet sits inside the facts bytes. Under replay it is equal, so no failure today; but state that a structured request may omit it and that the harness compares after replay, or move `line` out of the compared set **now** (changing the `facts_bytes` boundary later is a major, §9).
- Add to S34 test 11 two mutants that can fail: changing `request.anchors` changes `facts_bytes`; changing `provenance.promptHash` alone does not.

## Does the schema leave the hit rule open to gaming or scoring ambiguity?

The hit rule is deliberately recall-only (EP §5.2 "what does not matter"), so inflating recall is bounded only by the noise gate (EP §11). Within that, the following are open:

| # | Sev | Finding (all verified from spec §5.1-§5.3, §8 and EP §5.2 unless marked) | Fix |
|---|---|---|---|
| H-1 | major | **H3 is checked by endpoints only** (`chain[0].id` = asked anchor, `chain[-1].id` = subject id; V3-V5 check shape). A well-formed two-hop chain with a made-up middle satisfies H3 and V1-V14, so "carries its own evidence chain" is unverified. A system that emits many `possible` items with stub chains scores recall up to 100% before the noise gate sees it | Gate harness (E5): replay every hit's chain against the **gate snapshot**: each hop's `(kind, id)` exists and an edge of `edgeType`/`dir` joins consecutive hops. Positive control: a planted fake-chain item must score a miss. Cost is one query per hop |
| H-2 | major | **Subject span is self-attested.** §5.3 says H1 is "answerable from the answer alone"; `lineStart/lineEnd/ownedRegions` and `qname` are whatever the engine wrote. An engine bug in a span silently flips hits and misses, and the harness cannot tell | Harness reads span and `qname` by `symbolId` from the gate snapshot and asserts equality with the answer; mismatch is a harness error, not a miss. Additionally (inferred, S34 to confirm): `ids.symbol_id(lang, repoId, qname, signature?)` is a pure hash (`cpg/ccg/ids.py`), so a validator rule can recompute `subject.symbolId` from `repoId`, `qname` and `lang(path)` where `lang` is derivable from `path` (`-spec3` §3.3; skip `.h`/shebang cases) |
| H-3 | minor | H3 says "an id of a request anchor"; EP §5.1 asks "the asked anchor" (one per question). A rewriting engine that adds anchors passes H3 on a different anchor | Harness asserts `interpretation.request` equals the submitted request before scoring |
| H-4 | minor | The answer carries `stamp.snapshotId` and offset, but nothing says the harness checks the id against the pinned gate snapshot; an answer from the dev snapshot would score | Harness asserts `stamp.snapshotId == pinned` and `verdictLogOffset == 0` |
| H-5 | minor | Config branch (spec open item 3): `keyPath` is carried masked (`[#]`); gold `e.keyPath` is not. A real hit on a masked key fails the equality and prefix tests | Decision (closes open item 3 without reading any held-out data): the harness applies `answer.mask_identifier` to **both** sides before comparing, and lists every comparison where masking changed a segment for manual review (two different failing segments under one parent collide, a small false-credit risk) |
| H-6 | major | AC-24 option sets: "options contain every `goldOptions` entry" has **no upper bound**; listing every candidate in the repo passes `several-symbols` | Pre-register the did-you-mean cap (ML §3.1 (a)) before the gate; `|options|` above the cap is not understood. Report extras per item. (Also: spec §3 forces `options == []` for `unknown-name`, which forbids the did-you-mean list ML §3.1 (a) allows; either relax to "may be non-empty" or state the intent. Minor.) |

H1-H4 as written have no scoring ambiguity I could construct from the schema fields: each condition reads a named field, a symbol appears once across `items` and members, and group headers carry no subject. The finding is about trust in those fields, not their definition.
