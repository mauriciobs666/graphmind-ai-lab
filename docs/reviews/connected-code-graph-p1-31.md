## Rulings on the delegate decisions

1. **`AC8PROBE:<token>` → `probe.jsonl`: amend (accept the mechanism, revise the spec, tighten three things).** Spec3 contradicts itself: §8.1 says the detector writes one `conn` per connection and any `conn` fails the run, while P-a's positive control needs the probe to connect to the detector's ports. Some out-of-band class is unavoidable, so no spec-free alternative exists; the delegate's reconciliation is reasonable. Forgery/hiding: the token is 96 random bits, written 0600 into a host dir only the detector mounts; a *non-token* connection cannot hide (`detector.pl:45`, empty-token guard `length($tok)`; live test 2g, mutant D02 cover the wrong-token path). Remaining weaknesses: (a) the token travels in `docker exec` **argv** (`run.sh:183`), readable from `/proc/<pid>/cmdline` by any same-uid process in the component container and from host `ps`; harmless for P1's inert `perl -e sleep` stand-ins, wrong for the real P1-25/26 containers; pass it on stdin. ## Findings

### F1 (blocker) — the "no address on the bridge" guard fails open

`run.sh:86`: `[ -n "$(/usr/bin/ip -j address show dev "$bridge" 2>/dev/null | python -c '...json.load(sys.stdin)...')" ] && die`. If `ip` errors (bridge not named `br-<id12>`, device missing, `ip` failure), stdin is empty, `json.load` raises, stdout is empty, `-n ""` is false, and the guard **passes**. **Verified**: `ip -j address show dev br-doesnotexist00 2>/dev/null | python -I -c '<same>'` prints a `JSONDecodeError` to stderr and an empty substitution. The same pattern is test 2a (`test_ac8.sh:82`). This guard is the stated backstop for the case Docker ignores or does not support `gateway_mode_ipv4=isolated` (an unknown `-o` bridge key is not guaranteed to be rejected), and the delegate deliberately skipped the "network left reachable" mutant because P-a would then probe the host's real listeners (`mutants_ac8.sh:8-11`). So in exactly the failure it exists for, P-a becomes the first and only thing that notices, by connecting to (and UDP-sending one byte to) host services. Fix: capture `ip -j address show dev` into a variable, require exit 0, valid JSON and **a non-empty interface list** (the bridge exists) before computing addresses; otherwise `die 70`. Make it a function `bridge_has_address <dev>` returning 0/1/2 so a Docker-free test can assert `lo` -> 1 (has addresses) and a nonexistent name -> 2 (die), which turns the guard into something that can go red without a live network. Verified (the fail-open); inferred (the engine-ignores-the-option case).

### F2 (major) — P-e is evaluated after the run; spec3 says before

Spec3 §8.1 P-e: "**Before the run**, the harness calls the broker's resolve function ... on every non-local host". `run.sh` calls `assertions.py` only at step 7 (`run.sh:303`; `grep` for `P-e`/`pre_e` in `run.sh` finds only flag plumbing). The guard's purpose is that no allow *can* connect, and the broker runs on the host with a real network (§8.1 topology). A resolver that answers NXDOMAIN names (ISP hijack, split-horizon) lets a workload-triggered `R3/R4/R7` allow connect during the window; P-e then reports it after the fact, and 8.16 is the only other witness. Fix: add `assertions.py pre-e <manifest>` (reusing `pre_e`'s resolver half) and run it before `net_up`; keep the post-run recheck. Test: a stub resolver that answers one name makes `run.sh` refuse before creating any network or container (assert with `docker network ls`/exit code in test 6's style).

### F3 (major) — a stand-in run reports `pass` / exit 0, indistinguishable from the acceptance run

`--stub-resolver` (P-e vacuous: nothing resolves, nothing is queried), `--stub-model`, `--store-standin` and `--witness-parse` all still yield `overall: pass` and exit 0 (`assertions.py:865`, `:908`; test 3a asserts 0 with all of them). The resolver name appears only in a `resolver` field and the render header. P1-40's acceptance is "exit 0"; a self-test flag pasted into the P1-40 command line produces the same green. Fix: any stand-in flag caps the overall at `incomplete` (exit 3), or write `selfTest: [...]` into `facts.json` and have `evaluate` refuse `pass`; keep test 3a asserting the capped result, and add the one assertion that a run with none of them can reach 0. The P1-40 gate must then state "exit 0 with `selfTest == []`".

### F4 (major) — P-b/A2 can pass because `getent` is absent; the spec's positive leg is missing

`netprobe.pl:86-89` passes when `rc != 0 && dt < 5`. A missing `/usr/bin/getent` makes the child `exit 127`, i.e. PASS ("status=127"). Spec3 §7.3 A2 is two-legged: `getent ahosts example.com` fails **and** `getent hosts localhost` succeeds; the escape probe has it (`tests/probe.pl:99-101`, A2a/A2b), `netprobe.pl` (the P-b implementation) does not. Fix: add the localhost leg as `A2-localhost` (required in `component_probe_problems`) and require getent's "not found" status 2 for the ahosts leg. The delegate lists A2's negative control as untestable; a real one probably exists in-run: Docker's embedded DNS resolves other containers' names on a user-defined network, so `getent hosts <detector container name>` should succeed while `example.com` fails (inferred, not run; verify on a throwaway). With either, "A2 untestable" is acceptable for P1; without the localhost leg it is not.

### F6 (minor) — a TERM/INT/HUP handler that does not exit

`run.sh:343` traps `cleanup`, which runs `trap - EXIT INT TERM HUP` and returns without `exit`. In bash the interrupted script then **continues**. Verified with a 4-line script of mine: after `kill -TERM $$` the trap ran and execution resumed (`rc=0`). After an interrupt the run goes on with its containers and networks already removed; later steps fail or no-op, but nothing guarantees the "removes only its own, verified gone" claim afterwards, and no later EXIT trap exists to catch stragglers. Fix: in the signal traps `exit 130`/`143`; keep the EXIT trap as the cleanup (`trap cleanup EXIT; trap 'exit 130' INT; trap 'exit 143' TERM HUP`). Add to test 6.

## Was `--internal` + isolated gateway + no-bridge-address a proof of no route out?

Not by itself, and the delegate does not claim it is: P-a is the acceptance. What the mechanism gives is a container whose only route is its connected subnet (no gateway, no default), so any host or public address is `ENETUNREACH`; `net_up`'s address check, P-a's two-phase connect/`sendto` probes over *every* host address x listening port (`facts.py snapshot`), A1b's route reads (live tests 2l/2n show the probe sees a v4/v6 default route) and the negative control (test 2d: the probe reports FAIL against a reachable target, TCP and UDP) together are the proof. Strict rules help: a timeout counts as failure and `ECONNREFUSED` is not an accepted outcome for non-loopback targets. What a **false pass** looks like: (1) F1's fail-open guard with an engine that ignores the option, followed by a probe that happened to hit nothing; (2) a snapshot or probe that silently covers fewer targets (F5, Z01); (3) host-side listeners the host's `ss` does not list (WSL mirrored mode's Windows listeners; spec3 R-E8 accepts this); (4) a probe image without `getent` (F4). The skipped "network left reachable" mutant is **acceptable for the P1 gate** because tests 2d/2l/2n plus S01 give an equivalent signal on a harmless target, *provided F1 is fixed* (without it nothing proves the backstop; with it, the function-level test replaces the unsafe mutant). The un-proven joint is the wiring from `facts.py snapshot` into `netprobe.pl`'s `v4=/v6=/tcp=/udp=`; F5(iii) pins its count, and P1-40's own first run is the end-to-end evidence. A7 (vsock) negative untestable: **acceptable**, the escape-axis A7 inherits the sandbox suite's own coverage (`test_sandbox.sh:650`).
