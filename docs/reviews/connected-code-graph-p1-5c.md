## Findings

### F1 (minor, verified) The fingerprint clamp's upper bound is not pinned at the file end
`core.py:241` (`min(b, len(lines))`). My mutant m1 (`min(b, len(lines) - 1)`) **survived all 778 tests**. Cause: `Source.lines` is `text.split("\n")`, so a file ending in `\n` carries a trailing empty element and the off-by-one is invisible; the existing tests (`test_fingerprint_adds_every_line...`, the `10**12` test) all use trailing-newline files. A file with no final newline, where an owned region ends on the last line, would silently lose that line from the fingerprint, and nothing fails.
Fix: add to `test_normalize_core.py` a no-trailing-newline file whose region ends exactly on its last line, with the expected hash computed from the literal text (as the neighbouring test does).

### F2 (minor, verified by reading plus the delegate's mutation table) The two "far beyond the file" tests fail by resource exhaustion, not assertion
`test_a_region_far_beyond_the_file_neither_hangs_nor_changes_the_fingerprint` (core) and `test_last_changed_over_a_region_far_beyond_the_blamed_lines_is_bounded...` (history_git). Without the clamp the first builds a `set(range(2, 10**12))` (memory blow-up) and the second loops 10**12 times; the delegate's mutants for both died only to the `ulimit`/timeout. Ruling on item (5): the tests are **real** (the unclamped code cannot pass them), but under a bare `pytest` run a regression exhausts the host (or hangs) instead of reporting a red test, and it is the same shape in CI.
Fix: bound the test itself, e.g. `resource.setrlimit(RLIMIT_AS, ...)` in a forked helper or a `signal.alarm(5)` around the call, so the regression is an assertion or a timeout error. Cheaper alternative for `last_changed`: assert the iteration count by passing a region list subclass or by monkeypatching `blame.range` to a counting wrapper.

### F3 (minor) `ownedRegions` is emitted as given, the fingerprint is clamped
`assemble_bundle.py:203` writes `[list(r) for r in owned_regions(s)]` without the clamp or validity filter that `fingerprint`/`last_changed` apply. A frontend handing `(2, 10**12)`, a negative start or an inverted pair gets a record that disagrees with the fingerprint that covers it, and the S17 "narrowest interval" anchor rule (spec3, symbol row) would act on the bogus extent. Spec3 §5.3 states the field is the owned regions' line spans, so it is defensible to leave this to the frontend, but then say so: either reject (`ValueError`) a region outside `1..len(lines)` or `a > b` in `owned_regions()`'s caller, or document the frontend contract in the `Scope.owned` comment. Latent: no P1 frontend sets it.

### F4 (minor, ruling on the delegate's question) The slice test's `extract.sc` hash is read after the build
`test_whole_bundle_is_identical_with_the_ported_extract_script...` compares the header's `extractScriptHash` with `hashlib.sha256(run.EXTRACT_SC.read_bytes())` taken **after** `build_bundle`. In a tree where `extract.sc` is edited mid-run, the comparison is a time-of-check mismatch; the delegate's one-time red (mtime 23:35:39 during the run, green alone and on rerun, and green again in my run with an unchanged mtime) fits that cause, but it was not reproduced, so the attribution is inferred. Ruling: not a product defect and not a design flaw for a single-writer tree, but a hazard in this repository's concurrent-unit workflow, where it will produce false reds, which erode trust in a 105 s test. Fix: snapshot the script bytes once, immediately before the build, and compare against that snapshot (the build reads the same file, so the window shrinks to milliseconds), or have the test copy `EXTRACT_SC` into its tmp stage and build from the copy.

### F5 (nit) Import line and a stale doc comment
`assemble_bundle.py:27`: `owned_regions` is inserted out of the alphabetical order of its neighbours and pushes the line to ~140 columns. `Scope.owned`'s comment ("none in P1's frontends") is still accurate, no change needed there.

## Judgments requested (all verified unless marked read)

1. **Delta mechanism.** Sound. `DELTAS` is an ordered `(name, version, fn)` list; `apply_deltas` parses the **stored** bytes, applies each fn, pins `tools.normalizerVersion` to the entry's literal, recounts every type in `counts` and asserts equality, then re-serializes with `bundle.canonical_line`. The expected side is never regenerated from the code under test, and a positive control (`test_no_delta_at_all_reproduces...`) proves the serializer round-trips the stored bytes. The version pin is independent of the constant (literal `"0.2"` vs `NORMALIZER_VERSION`), and the delegate's `0.1`/`0.3` mutants die on the `pins` test. The delta identifies lambda targets from stored data (`kind == "lambda"` symbol ids, matched on `targetId`), not by re-running the normalizer. My script over the stored bundles: fcs `counts.decorator` 213, 213 decorator records, **3** targeting lambdas (`_read_or_absent`, `retry.call_with_retry` x2) so 213 -> 210; the targets' kinds are function 143, method 37, accessor 30, lambda 3 (nothing else is touched); sp has 0 decorators and 0 lambda ones; neither stored bundle contains `ownedRegions`; stored `normalizerVersion` is `0.1`. Unfiltered repo grep: `lambda_decos` no longer appears in code (only in prior review/plan prose); the only new reader is `report["lambdaDecoratorsDropped"]`, asserted at `test_normalize_assemble.py:91`.
2. **`ownedRegions`.** Conforms to spec3 §5.3: emitted exactly when non-empty (my mutant "always emit" is killed by the **intended** assertion `test_a_symbol_without_owned_regions_has_no_ownedregions_field_at_all`, not by the validator, which settles item (5)'s third doubt for the unit file; the delegate's validator-only kill was in the slice run), sorted de-duplicated pairs, fingerprint over the sorted de-duplicated line union, blame regions through the same `owned_regions` helper. With no regions the new code computes `set(range(ls, le+1))` and applies the same `n <= len(lines)` bound as the old slice `lines[ls-1:le]`, so the slice's fingerprints are unchanged; the slice file (20 passed) is the evidence, since fingerprints are in every stored symbol record. The clamp cannot change a legitimate region's fingerprint (a legitimate `b <= len(lines)`), subject to F1's untested upper edge.
3. **(a) non-UTF-8.** `build_bundle`-level Latin-1 tests for `.py` and `.ts` raise `SourceRefused`, name the file, assert "not UTF-8", assert no `\xe9`/`\xff`/`xe9`/`xff` spelling in the message, and assert no file under the work dir. Message is built from `e.reason` and `e.start` only (read, `core.py:107`). D12 conformance holds; no bundle field changes. No other source read bypasses `Source` (grep: `read_bytes`/`open` hits are the facts JSON, the astgen JSON and the extract-script hash, none of them source text).
4. **N1 / N3.** `blame._env()` drops every `GIT_*`, then re-adds the three isolation variables. Nothing legitimate needs to survive: every call is a local `git -C <repo> ...` (blame, rev-parse, cat-file, ls-tree), so `GIT_SSL_*`, `GIT_ASKPASS` and `GIT_TERMINAL_PROMPT` are irrelevant. Only `GIT_EXEC_PATH` could matter, for a relocated git whose helper path is not compiled in; that would also be hostile-controllable, so dropping it is the safe default. `GIT_TRACE*` loss is harmless. The redirect test (premise-checked: a bare git is redirected, `blame.git` is not) is a real test. N3: `Source.raw/text/lines` over a missing file and a directory give `SourceRefused` naming the file, test covers all three entry points; escape names still refused before any read.
