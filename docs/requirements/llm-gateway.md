# Common LLM gateway — Feature Requirements

> **Status:** Ready for design · **Owner:** `tico` · **Tracks:** — · **Supersedes:** `docs/requirements/anthropic-api-adoption.md` · **Extended by:** `docs/requirements/llm-gateway-usage-stats.md` · **Reviews:** `docs/reviews/llm-gateway.md` · **Last updated:** 2026-11-24 · **Item:** `GAL-F0046`

## Intent
One LLM gateway, common to every component in the repo, fully configurable and flexible, offered as a framework: any current or future component gets provider choice, fallback, model configuration and call records by using it, instead of building its own. The trigger: `ccg`'s local models missed AC-24, and the stakeholder wants hosted models (Anthropic) available there without a one-off integration. Phasing: **first delivery** = `ccg`; **follow-on** = falkor-chat, model-bench, decision-models (FR-14). Each FR below carries its phase. ccg adopts after its P1 gate closes, so the gated configuration is unchanged.

## Problem & current state
- `falkor-chat` has its own gateway (`ModelGateway`, `falkor-chat/docs/SERVER.md` §1.8: per-workspace resolution, fallback).
- `model-bench` talks only to LM Studio (`model-bench/modelbench/lmstudio.py`); `decision-models` has no hosted client by rule (`decision-models/AGENTS.md`) and drives `claude -p` children; `ccg` calls a local model through its egress broker (`cpg/ccg/front/interpret.py`).
- The accepted, unbuilt `docs/plans/anthropic-api-adoption.md` would copy an Anthropic adapter into three components rather than share one. This document supersedes `docs/requirements/anthropic-api-adoption.md`.
- Each new component would repeat the same work.

## User stories
- As the repo owner, I want every component to reach models through one gateway, so that provider choice, fallback and limits are configured once.
- As the owner of ccg, I want its interpreter to run on a hosted model by configuration, so that I can find out whether a stronger model meets AC-24.
- As an owner of confidential material, I want local-only (or private) scopes to be unable to reach a hosted provider, so that a configuration slip cannot leak it.
- As a builder of a future component, I want to adopt the gateway by configuration and a small call surface, so that I get routing, fallback and records for free.
- As the person paying the bill, I want each call recorded and unattended runs capped, so that spend and provenance are visible (reports: `docs/requirements/llm-gateway-usage-stats.md`).

## Functional requirements
Definitions. **Hosted** = any endpoint not on the deployment's local allow-list, for every provider kind (so a remote OpenAI-compatible URL is hosted). **Owner configuration** = configuration an LLM-driven agent, a request or a workflow definition cannot write.

- **FR-1** [first] — Any component obtains chat completions (with tool calls) from the gateway and holds no provider client of its own. Embeddings are not available at first delivery: an embeddings request is refused with a clear error.
- **FR-2** [first] — Configuration alone, with no code change in the caller, sets: provider and model per call site; an ordered fallback chain per call site; overrides per scope (a workspace, a codebase, a run). A scope override that selects a hosted model is accepted only from owner configuration, never from a request or workflow definition.
- **FR-3** [first] — Policy limits are enforced and cannot be overridden from a narrower scope. A **restricted scope** is one marked local-only or private. A restricted scope is refused hosted use with a clear error, and a marker that is unreadable or ill-typed also refuses; it is read at call time. Call sites are bound to scopes registered in owner configuration; a request may only tighten a scope, never loosen it. Hosted use requires a registered scope, and a scope name that is not registered is refused for hosted use (it is not treated as unrestricted); a registered scope carrying no marking is unrestricted and uses hosted only where owner configuration allows it (FR-6). Local-only is sticky: a call touching any local-only scope goes local even if another scope defaults to hosted. For ccg the local-only marking is ccg's system manifest, which only its owner can write; the broker's decision on it is authoritative, and the gateway reads the same manifest and does not re-declare it (FR-20). The owner of a scope sets and lifts its marking through the component's own settings, which only owner configuration reaches.
- **FR-4** [first] — Generation settings are given provider-neutrally, may be declared per provider in a call site's configuration, and are translated per provider. Every setting declared in a call site's profile is required unless the profile marks it optional; a required setting the selected provider cannot honour fails the call with an error naming it, and nothing proceeds silently changed.
- **FR-5** [first] — Every attempt yields one record, linked to its call by a call id (so a hosted attempt that falls back to local leaves two records, and reports count calls and attempts separately): the provider-reported model identity, whether a fallback or retry occurred and why, hosted or not, input and output tokens, time to answer, outcome and failure class, component, scope, call site, and the loaded-model state where the provider reports it. Metadata only: prompt and response text is recorded only for a scope that opts in, never for a private or local-only scope. No credentials, request headers, provider error bodies, or provider organization or workspace ids appear in it. (Absorbs former FR-26.)
- **FR-6** [first] — Defaults are local: with no hosted configuration nothing leaves the machine and nothing is spent.
- **FR-7** [first] — Failures are classified the same way for every provider kind. Temporary: rate limit, out of credit, outage or 5xx, timeout, connection failure, model not loaded. Permanent: missing or invalid key, permission, a rejected request (any other 4xx, including context overflow). Retry and fallback trigger only on temporary failures; a permanent one fails with a clear message.
- **FR-8** [first] — A hosted API key is held by one dedicated key-holding process that runs under its own OS account (or a rootless container owned by that account) and is the only process that reads the key, makes hosted exchanges and enforces FR-10's token ceiling; every other process, service or broker forwards to it. The holder accepts a call only with a valid per-request credential (HMAC) issued to the broker or the gateway service, and pins https and the allowed model ids. An agent running under the human's account can therefore never read the key, the holder's files, process memory or environment, or reach the holder without a valid credential. **Stated limitation:** the broker's and service's credential lives in the human's account, so an agent that obtains it can call the holder directly and spend, but only within the holder's ceiling and pinned-model/https limits; the key itself stays unreadable. The credential guards against accident and prompt-injected tool use that does not read it, not against a hostile same-account process. No caller process, library or agent ever holds a hosted key. The key never appears in the repository, config files, results, logs, graph records, fixtures (which use obviously fake keys), command lines, prompts, or error text, and can be rotated or revoked without editing tracked files. A missing key fails clearly and closed. For ccg, the broker forwards allowed hosted calls to the key holder, so the broker's egress spec is amended accordingly.
- **FR-9** [first] — A hosted result names the exact pinned model version; a moving alias is refused. It is marked hosted wherever a local-reproducibility guarantee would otherwise apply.
- **FR-10** [first] — A run, identified by a run id its caller supplies, stops at a hard token ceiling (input plus output, thinking included) that the owner sets before it starts. The key-holding process (FR-8) enforces the ceiling and owns the run ledger, reserving tokens before each hosted call so that concurrent calls cannot overshoot it. A hosted call with a missing or unmatched run id is refused, or capped by an owner-set default bound. Besides the per-run bound, the key holder keeps one owner-set rolling token ceiling (tokens per window, hosted calls) across all run ids, checked in the same reservation as the per-run bound, so a caller-chosen fresh run id cannot obtain unbounded spend. It is a safety ceiling, not accounting. Interactive use of local providers is deliberately unbounded.
- **FR-11** [first] — The gateway is usable from the calling component's own process and from another process, with the same configuration and the same record, so that components with isolation or zero-dependency rules can adopt it too. In the caller's own process only local providers are reachable; a hosted call always goes through the key-holding process (FR-8).
- **FR-12** [first] — ccg's interpreter reaches its model only through the gateway, switchable between local and Anthropic by configuration. ccg's egress broker stays its enforcement and audit point and a gateway call is a brokered call, and a ccg call the broker's policy refuses is never sent; FR-3 applies to ccg's local-only codebases, including the sticky rule. ccg on Anthropic uses its own declared sampling profile (FR-4); its hosted results are marked not directly comparable with local runs.
- **FR-13** — Dropped: ccg already treats hosted as a configurable mode (its decision-log entry of 2026-10-25), so nothing needs reconciling.
- **FR-14** [follow-on, committed] — falkor-chat, model-bench and decision-models move onto the gateway without loss of today's behavior, and embeddings join it (falkor-chat's embedder). Must-keep: falkor-chat's per-workspace resolution and fallback; model-bench's LM Studio run handling, load behaviour and fingerprints; decision-models' independent generator and labeller. The adoption requirements deferred to this phase, by reference to `docs/requirements/anthropic-api-adoption.md`: FR-2, FR-4, FR-5, FR-6, FR-7, FR-13 and FR-15.
- **FR-15** [first] — Providers: LM Studio, Ollama, Anthropic, and a generic OpenAI-compatible endpoint. A further provider can be added without changing any calling component.
- **FR-16** [first] — The gateway owns loading and residency of local models, with load settings (context length, parallelism) from configuration. Three modes: on demand (ordinary callers: it loads what a call needs); explicit (the caller directs a load; recorded); strict (benchmark and preflight callers: it never loads, and fails if the model is not already loaded). It never creates a second copy of a model already loaded, and the loaded state is in the call record. It never unloads a model it was not asked to. Where a call site configures load settings, a model already loaded with other settings fails the call naming the mismatch, in every mode, and is never reloaded silently; a call site that configures none accepts whatever is loaded and records it (as ccg does today). A call site may name no model and bind to the loaded chat model, preferring a configured one, and fails if none is loaded; it never loads (as ccg's `pick_model` does). For ccg, loads also pass through the broker.
- **FR-17** [first] — Callers needing provider-specific detail (for example LM Studio per-run stats or the decisions endpoint, or the equivalent detail another provider offers) can get it through the gateway.
- **FR-18** [first] — The gateway never adds, reorders or changes decoding parameters; `seed` and the structured-output schema (`response_format`) pass through unchanged. No separate grammar field exists: a request field `grammar` is refused, naming it as unknown. OpenAI-compatible providers receive any `response_format` unchanged; Ollama and Anthropic refuse a `response_format` type other than `json_schema`, naming it.
- **FR-19** [first] — Retry (same provider) and fallback (next in the chain) happen only where the call site's configuration lists them, and a caller can always switch either off and then gets the first failure unmasked. ccg keeps its one retry on a transport failure or 5xx.
- **FR-20** [first] — Each deployment has one source of truth for provider URLs and for key references, used by every component through the gateway: a provider URL is configured once in the gateway configuration. A consumer's own authorization list (ccg's manifest allow-list) may name it again, provided the check that the two agree runs when that consumer's adapter builds its gateway client (for ccg, when its `Gateway` is constructed) and fails that adapter's start on disagreement; the gateway itself has no knowledge of any consumer's manifest.
- **FR-21 to FR-25** — Moved to `docs/requirements/llm-gateway-usage-stats.md` as its FR-1, FR-2, FR-3, FR-4, FR-5 respectively (statistics, interface, comparison, alerts, price table).
- **FR-26** — Merged into FR-5.

## Out of scope
- Embeddings in the first delivery (FR-14).
- Per-run, per-tenant and per-user spending budgets and the usage-stats budget features. The only cross-run limit is FR-10's owner-set rolling token safety ceiling.
- Components that launch a CLI agent (`tank` via OpenCode, `mcp-monitor`, `kiro`, `claude -p` and Claude Code subagents): the model belongs to that CLI. `tank` and `mcp-monitor` stay out.
- Re-measuring AC-24 on a hosted model (ccg's own work, now able to use the gateway).
- Any UI for editing gateway configuration.
- Per-user or multi-tenant billing and authentication of gateway callers.
- Usage and statistics tooling: its own document.

## Acceptance criteria
- **AC-1** — Given ccg configured for a local model, when the interpreter runs, then the call is brokered through the gateway and its record names the local model. Given the call site's configuration for Anthropic declares only settings that provider honours, changing only configuration makes the next record name a pinned Anthropic model marked hosted, with no ccg code change. Given a required setting it cannot honour (for example `seed`), the call fails naming the setting. A hosted ccg result carries the not-directly-comparable mark. (FR-1, FR-2, FR-4, FR-12)
- **AC-2** — Given a ccg codebase set local-only, when a hosted model is configured at any narrower scope, the call is refused and nothing is sent. Given a system with one local-only and one hosted-default codebase, every call goes local. Given a restricted scope whose marker is unreadable or ill-typed, the call is refused; a marker tightened between two calls takes effect on the next call, while loosening a ccg local-only marker takes effect only after the owner reinstalls the owner-protected manifest and restarts the broker. Given a registered scope with no marking, hosted is used only where owner configuration allows it. Given a hosted call naming an unregistered scope, or a request carrying an unknown field, it is refused; no request field can express a loosening of a scope, so a request has no way to loosen one (tightening by request is allowed). Given a hosted model named by a request or workflow definition, it is refused. Given an attempt by an agent or a request to lift a marking, the marking stays. (FR-2, FR-3)
- **AC-3** — Given a fallback chain whose first provider returns rate-limit, out-of-credit, timeout or model-not-loaded, the next is used and the record shows it; given an invalid key or a rejected request, the call fails clearly with no fallback, for local and hosted providers alike. (FR-5, FR-7)
- **AC-4** — Given no hosted configuration anywhere, a run sends nothing off the machine, including through a misconfigured remote OpenAI-compatible URL. (FR-6, FR-3)
- **AC-5** — After a hosted run through a stand-in endpoint with a planted fake key, a search of the tree including untracked files, git history, results, ledgers, transcripts, logs, graph records, tracebacks, fixtures and child-process environments finds no key value. The same search finds the key where it is deliberately planted (positive control). A failing call's error text contains no key. Rotating the key needs no tracked-file edit. An agent probe run as the agents run (same account, same tools) that looks for the key in the key holder's account or container, its files, process listing, process memory and environment, finds nothing, while the same probe finds a planted marker in a place agents can reach (positive control, planted in the same kind of place as the key holder's). A direct call to the key holder with no, a wrong, stale or replayed credential is refused; with a valid broker or service credential it is served, but only within the ceiling and pinned-model/https limits (the stated limitation in FR-8: the probe can read a credential file, and this is not claimed otherwise). A hosted call attempted from a caller's own process is refused. (FR-8, FR-11)
- **AC-6** — A hosted run with a token ceiling is never allowed to start a call whose reservation would exceed it, counting input plus output with thinking tokens included, even with concurrent calls; usage a provider reports above a reservation is recorded as reported and the next call is refused, so the ceiling can be overshot by at most one call's settled excess; a hosted call with a missing or unmatched run id is refused or capped by the owner-set default bound; given 100 fresh run ids each matching a bounded pattern, total hosted tokens stop at the owner-set rolling ceiling; interactive use of local providers is unaffected. (FR-10)
- **AC-7** — A local call site works from the caller's own process and from another process, with the same configuration and the same record; a hosted call site works only through the key-holding process. (FR-11)
- **AC-8** — A provider beyond the four at first delivery is added with no change to any calling component. (FR-15)
- **AC-9** — Dropped with FR-13.
- **AC-10** — The follow-on has a recorded unit per component whose acceptance includes the FR-14 must-keep list and the deferred adoption requirements. (FR-14)
- **AC-11** — Given a request with `seed` and a JSON schema, the provider receives exactly those values and no others added; a request carrying a `grammar` field is refused naming it, and on Ollama or Anthropic a non-`json_schema` `response_format` type is refused naming it. (FR-18)
- **AC-12** — Given a call site with fallback configured and a caller that switches it off, a failing first provider yields that failure and no other model answers. A call site with no retry or fallback configured has neither. (FR-19)
- **AC-13** — Strict mode with a model not loaded: the call fails and loads nothing. On-demand mode: it loads and the record states the loaded model. Explicit mode: the caller's load is recorded. A call never creates a second copy of an already-loaded model. Given configured load settings and a model loaded with others, every mode fails naming the mismatch; with no load settings configured the call runs on what is loaded and records it; a call site naming no model on an empty endpoint fails and loads nothing. (FR-16)
- **AC-14** — Changing a provider URL or key reference in the gateway configuration changes it for ccg and every other adopting component; a consumer allow-list naming the URL again is accepted only while it agrees with the gateway configuration, and a disagreement fails the start of that consumer's adapter (for ccg, construction of its `Gateway`), one direction only. (FR-20)
- **AC-15, AC-16** — Moved to `docs/requirements/llm-gateway-usage-stats.md` as its AC-1 and AC-5.
- **AC-17** — A record from a private or local-only scope contains no prompt or response text even when text recording is on elsewhere; a scope that opts in has it. A record never contains headers, provider error bodies or provider organization or workspace ids. (FR-5)
- **AC-18** — A request naming a moving alias (such as a `-latest` model id) is refused. (FR-9)
- **AC-19** — A record carries the fields FR-5 lists, and the same fields from a local and a hosted call. (FR-5)
- **AC-20** — A call asking for LM Studio per-run stats through the gateway returns them. (FR-17)
- **AC-21** — The ccg system manifest is writable only by its owner. A ccg call the broker's policy refuses is not sent to any provider and the refusal is in the broker's audit log. The local-only decision for ccg comes from its system manifest, with no second copy of the flag in gateway configuration. (FR-3, FR-12, FR-20)
- **AC-22** — Given a call site configured with one retry and a transient failure, the retry happens once, is recorded as an attempt, and a permanent failure is not retried. (FR-7, FR-19)
- **AC-23** — An embeddings request at first delivery is refused with a clear error. (FR-1)
- **AC-24** — A hosted attempt that falls back to local leaves two records with the same call id, the first marked hosted with its failure class. (FR-5)
